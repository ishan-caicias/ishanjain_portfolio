03 · Established by this audit

Four facts the plan must not miss

GLB internals

Single static mesh

1 mesh · 1 primitive · 1 material · 0 animations · 0 skins · 31,015 vertices · 4 PNG textures. No runtime animation system needed — travel, banking, and thrusters stay procedural in the engine.

space-engine.js:421

Context has no depth buffer

WebGL1 created with depth: false — and a context's depth setting cannot change after creation. A self-occluding textured ship requires depth: true at the creation line, with depth testing enabled only during the ship pass.

constraint retired

Byte-identical era ends

The verbatim-port constraint was a PF-07 Phase 1 verification device. Ship v2 deliberately forks the engine; the file comes under ESLint/Prettier in the same change, with an ADR recording the fork point.

budget math

Page counts ≠ GLB counts

Sketchfab lists 18.2k vertices; the GLB accessor holds 31,015 (seam splitting for normals/UVs). Raw download is 43.5 MB. All budgets must be computed from the real GLB, not the model page.

04 · Rendering decision

In-engine GLB renderer, with a gated Three.js fallback

Codex recommended the Three.js hybrid (Option B). The audit refines this: the asset is one static mesh, and the realism audit's #1 fix — world-space ship placement — is native when the ship lives in the same context, projection, and frame loop as the stars.

Option A+ · In-engine GLB renderer

Chosen — primary path
  • ~200–300 lines against existing engine shader infrastructure
  • Zero new runtime dependencies
  • One GL context — ship shares projection, depth, and frame loop with the stars
  • Purpose-built loader for one known asset shape, not a general glTF parser
  • Lighting: baseColor × baked AO + emissive + directional/rim, tone-mapped

Option B · Three.js ship layer

Fallback — gated at Phase 1 exit
  • Battle-tested glTF loading and PBR out of the box
  • Costs ~150 KB gz + a second canvas/context for a single mesh
  • Per-frame camera state sync between two rendering worlds
  • Makes world-space integration with the custom starfield harder, not easier
  • Trigger: Phase 1 proof misses its visual-quality acceptance — Phase 0 output carries over unchanged

08 · Next — PF-08 Flight v3

From choreographed hero prop to a ship that truly flies

Owner direction after the v2 review: travel still reads as linear — the camera flies while the ship holds screen stations. v3 inverts the model: the ship gets orientation, thrust, and velocity in the scene's real 360° coordinate space, and the camera becomes a chase observer. Plus a realistic layered exhaust and further hull fidelity. Full plan: docs/delivery-plan/PF-08-flight-v3.md.

F0 · fidelity foundation

Hull & light

sRGB/tone pipeline ✓ shipped early as the TR-021 hotfix (the "opaque white" hull was a tone-curve bleaching bug — texture means measured 71–79/255, a dark blue-gray). Next: relight, engine-glow cast on the rear hull, star bloom.

F1 · flight state

The ship gets physics

Orientation quaternion + angular velocity, thrust vector, integrated velocity — the ship turns toward a destination's real RA/Dec direction and burns along it. Flip-and-burn happens on the true travel vector.

F2 · 360° choreography

Chase camera

During warp the camera detaches and chases with spring offset and look-ahead; free-look drag stays live mid-flight. Arrivals become decelerating orbit-ins, from any direction to any direction.

F3 · exhaust realism

Real propulsion

Noise-scrolled plume texture, white-hot core in a diesel-orange sheath, turbulence from acceleration, heat shimmer, ember particles on burn transitions. Tier-gated so mobile keeps the light version.
