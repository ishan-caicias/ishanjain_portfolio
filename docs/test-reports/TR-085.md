## What this slice had to close

The audited baseline: `body.ij-loading` cleared itself automatically once `ready && craftDone`
(with 2.5s/8s grace timers), so a visitor never made a real decision — content just appeared
when the engine happened to be done. The experience review's S0-S4/S1e state machine replaces
that with a real gate: a **PRE-FLIGHT · SYSTEMS CHECK** dossier showing real stage progress,
armed by real boot-critical completion, passed via **LAUNCH**, **SKIP INTRO**, a stall-recovery
**PROCEED ANYWAY**, or a returning-visitor bypass — never a timer deciding for the visitor.

## What shipped

**New pure module `src/lib/preflight-state.ts`** (no DOM/React; unit-testable in isolation,
same split `load-progress.ts` and `perf-telemetry.ts`'s `PerfMonitor` already follow):

- `stageRowView(stage, progress)` — one checklist row's label/percentage/status text.
  Checkpoint stages (`engine-init`/`first-frame`, which carry no bytes) render a status word
  ("CHECKING…" / "✓ ONLINE") rather than a fabricated "0 B" byte line; boot-critical stages show
  real loaded/total; background stages read "STREAMING IN BACKGROUND" while in flight and a real
  checkmarked total once done.
- `stalledBootCriticalStages(...)` — pure stall detection: a boot-critical stage with no
  `cosmos:stage` event (progress OR completion) for `STAGE_STALL_MS` (10s) degrades, falling back
  to the dossier's own mount time for a stage that never even started, so total silence also
  degrades rather than pending forever.
- `derivePreflightPhase(...)` — the state machine itself, computed from inputs already tracked
  elsewhere (`isTravel`, `launched`, `armed` === `state.ready`, the stall check) rather than
  stored as a second source of truth that could disagree with them.

**New shared `src/lib/focus-utils.ts`** (`moveFocusTo`/`restoreFocusTo`) — built here per the
plan's own instruction ("if D1 lands first, create it here"; D4.3 reuses it for the collector
card.

**New `src/components/islands/space/PreFlight.tsx`** — the dossier component. Identity
("ISHAN JAIN · Software Engineer") renders immediately on mount, ahead of any boot-critical
completion, so the recruiter's "who is this" moment doesn't wait on the network. Real stage
checklist driven by D1.1's `cosmos:stage`; a sparse `role="status"` announcer updates only on
stage completions/arming (never per-byte, per the review's accessibility note); LAUNCH is
disabled ("ARMING… N%") until `armed`, then takes focus automatically; SKIP INTRO is available
from the moment the dossier mounts (the delivery plan's risk-mitigation text, not the state
diagram's S2-only reading — see "Judgment call" below); a stall shows PROCEED ANYWAY instead of
LAUNCH; a returning-visitor `sessionStorage` flag (`ij-launched`) skips the dossier from the
render initializer, so it never even flashes once.

**Wiring in `SpaceScene.tsx`:** a new `cosmos:stage` listener merges into a `stages` state kept
**outside** the shared `state`/`patch()` object — that state updates up to 4 Hz across up to
nine stages, and folding it into the object every other component subscribes to would re-render
the whole scene tree on every byte tick. The real engine backend is read the moment `engine-init`
closes (not gated behind `?perf=1`'s debug interval, unlike the existing `backend` state). The
old `body.ij-loading` grace/hard-timer effect is replaced with a plain `launched`-driven clear;
the mobile-scroll instant-clear branch is unchanged.

## Judgment call: SKIP INTRO's availability window

The state-machine diagram draws `SKIP INTRO` as an S2 (armed)-only transition parallel to
LAUNCH. The recommendations prose disagrees with its own diagram: **"a quiet SKIP INTRO link
during loading routing to content as soon as boot-critical stages allow"**, and the "biggest
risk" section is explicit — **"SKIP INTRO available pre-arm"** is listed as a mitigation for the
10-20s hotel-Wi-Fi gate risk. A pre-arm-only reading of the diagram would defeat that exact
mitigation. Implemented per the prose: SKIP INTRO is available from the moment the dossier
mounts, not gated on arming. Recorded here rather than silently picking one interpretation.

## Scope calls recorded, not silently resolved

1. **No separate Astro/SSR shell was built.** The plan's prose calls for "SSR shell (identity
   block + static stage-list skeleton) lives in Hero.astro markup so it paints before
   hydration." Every other piece of scene chrome in this codebase (HUD, WarpOverlay,
   ArrivalVista) is React-only with no SSR duplicate — `SpaceScene` is `client:load`, hydrating
   near-instantly, and duplicating identity markup between Astro and React would itself be a
   second source of truth. PreFlight renders identity immediately on mount instead. If a future
   slow-hydration measurement shows a real gap, that's the trigger to revisit, not a guess now.
2. **The stage checklist shows all four boot-critical stages plus any background stage that
   has started** (not a curated subset) — the two example rows the review named ("STAR CATALOG
   · 2.02 MB ✓", "SDSS DEEP FIELD · STREAMING IN BACKGROUND") are both real rows this renders,
   just not the ONLY rows.
3. **`atlas-photo` still has no dossier row** — inherited from D1.1's own scope call (Babylon's
   `Texture` exposes no byte progress); nothing new to resolve here.

## A real defect found by the unit tests themselves

`moveFocusTo` originally added `tabindex="-1"` **unconditionally** rather than only when an
element actually needed it to become focusable — every focus target, including the LAUNCH
button itself, would have been stamped with a redundant `tabindex="-1"` attribute. Caught by
`focus-utils.test.ts`'s very first assertion (a plain `<button>` should gain no `tabindex`),
before it ever reached an E2E run or a real browser. Fixed to try a plain `focus()` first and
only add `tabindex` if that didn't take — the standard pattern, and now what the code actually
does.

## A second real defect found only by running the full E2E suite

The pre-existing **9s CSS failsafe** (`global.css`'s `ij-unhide` keyframe — a no-JS/failed-
hydration safety net, "even if SpaceScene never clears ij-loading, content self-reveals via CSS
alone") fired **during entirely normal operation** once this slice shipped: craft loading is
calibrated up to 45s in this repo's own E2E ceilings, so a completely healthy visitor routinely
takes longer than 9s to reach the point a test or real user would act — and the failsafe would
force-reveal `#ij-hero-copy` right out from under a still-showing, still-working PreFlight.
`craft-ship.spec.ts`'s warp-travel test caught this directly: `#ij-hero-copy`'s opacity read `1`
during warp (expected `< 0.5`) because the CSS animation had already won the cascade over the
`ij-warping` dimming rule.

**Fix:** scoped the failsafe to `body.ij-loading:not(.ij-preflight-mounted)` — PreFlight now
marks `document.body` with `ij-preflight-mounted` on mount, so the rule fires only when the
JS-driven gate genuinely never started (a real hydration failure), never merely because a
visitor with working JS hasn't clicked LAUNCH yet. **The 9s VALUE is preserved verbatim** (per
the implementation plan's instruction); only the _condition_ changed, and only because real E2E
evidence — not a guess — showed the old condition was now wrong.

### Five named test changes (CLAUDE.md #15 — no assertion weakened)

All five are the same root cause, discovered incrementally: **`#ij-preflight` structurally
occupies the same lower-hero screen region existing chrome (`#ij-mission-bar`'s RNG button,
free-look drag's viewport-center coordinate) already used** — by design, since both are "things
shown in that region," just at different phases. A real visitor would dismiss the gate before
ever reaching either; these tests now do the same.

| File                              | Change                                                                                   | Why                                                                                                                                |
| --------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `tests/e2e/flight-v3.spec.ts`     | Added a SKIP INTRO click before the free-look drag; `test.setTimeout(60000)`             | Drag simulated at viewport center, now behind PreFlight until dismissed; defensive timeout for the added step                      |
| `tests/e2e/engine-select.spec.ts` | Same SKIP INTRO click added to the Babylon free-look-drag test; `test.setTimeout(60000)` | Same collision, Babylon path. Measured 27-31s across repeated runs even _before_ this slice (no margin) — TR-080's exact signature |
| `tests/e2e/engine-select.spec.ts` | SKIP INTRO click added to the RNG-button test                                            | RNG lives inside `#ij-mission-bar`, same region                                                                                    |
| `tests/e2e/space-scene.spec.ts`   | SKIP INTRO click added to the RNG-button test                                            | Same collision, legacy-engine-default path                                                                                         |

No assertion in any of the five was changed — only a precondition (dismiss the gate, as a real
visitor would) was added ahead of the existing behaviour under test.

## Known limitations

- `atlas-photo` still has no dossier row (D1.1's scope call, unchanged).
- No dedicated SSR shell (scope call above) — a hydration-slow device gets a brief unstyled gap
  before PreFlight paints. Unmeasured; revisit if evidence shows it matters.
- The stall detector's 10s threshold and the `ij-preflight-mounted` failsafe-scoping fix are
  both new, narrow mechanisms with light test coverage (unit-tested logic, one E2E stall path
  not separately exercised in real time — a real 10s wait per test run was judged not worth the
  E2E suite's wall-clock budget; the pure `stalledBootCriticalStages` function carries the
  correctness burden instead).
- D1-AC1 (Fast-3G throttled first-visible-progress) is not yet automated — flagged in D1.1's TR
  as belonging here, and still open; a CDP-throttled E2E run is the natural next addition.
