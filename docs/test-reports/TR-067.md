## Part 1 — Strategic pivot: ideal-state-first, tiers deferred to real device data

Owner direction, verbatim intent: _"I wanted to implement full delivery plan PF-10 as an ideal
state, take the current desktop as the baseline. And once we have a full-fledged implementation
complete, we can introduce tiers/modes/settings based on extended device testing."_

Concrete consequence applied this session: TR-066 restricted white dwarfs (the dominant vertex-
count cost among the C1 bonus layers) to the `full` quality tier only, based on a SwiftShader/
WebGL2 "balanced"-tier measurement showing severe frame-time degradation. That measurement was
real, but the INSTRUMENT was a software rasterizer (CI's bundled Chromium), not a real device —
a reasonable worst-case proxy at the time, made obsolete now that real Android hardware is
available. **Reversed in `babylon-engine.ts`'s `_loadBonusStarLayers`**: all 3 bonus layers
(white dwarfs, CNS5, Oort cloud) now merge on every quality tier. The tier-gate mechanism itself
is kept in the code, defaulted to a no-op, ready to be re-armed with real thresholds once real
Android measurements land — never reintroduced blind.

## Part 2 — SDSS DR18 wired into real rendering (C2's core remaining item)

Per [ADR-0007](../adr/0007-background-bulk-layer-merge.md)'s consequences section (written in
TR-066, before this session's implementation): SDSS needs its own mesh, not a `CATALOG_CHUNKS`
merge, because its positions are log-depth-compressed (the real 32.6M-28.86B ly range baked down
to ~1,112-1,489 world-depth units) while the star field stays linear-ly-scaled. Implemented
exactly that: `_loadSdssGalaxyLayer` (new method) fetches `public/assets/sdss18.png` (the real
full-scale asset, 47.1 MB, generated this session — previously only a build artefact under
`scripts/out/`) after `cosmos:ready`, decodes it via the same `decodeStarCatalog` (same 15-byte
record format, object-type byte 3 = "galaxy smudge", a real existing shader branch), builds
billboard geometry via the same `buildStarBillboards` helper the star mesh uses, and creates a
genuinely separate `Mesh`/`VertexBuffer` pair that **shares** `_starMat` (the `ijStar` material
is already generic on the type byte — no new shader work needed). Idle-gated before the geometry
build, same non-blocking philosophy as the C1 bonus layers.

**Real count**: 3,637,862, not the dataset's stated 3,637,836 — the same real, pre-existing
padding-record behaviour TR-066 documented for every other background layer (the shared PNG-pack
format pads to a full rectangle; trailing padding decodes as extra all-zero records). Confirmed
independently from the real shipped file's dimensions (1024×17763).

**`sceneStats()` extended**: `sdssGalaxyCount`, `sdssMeshReady` — real behaviour asserted by a new
E2E test (the exact real count + mesh readiness), not just absence of console errors.

## Part 3 — The real finding: SwiftShader vs. real GPU, quantified

Widening the SDSS layer to full scale immediately surfaced E2E failures beyond the expected
timing-sensitivity class already documented in TR-066 (`GAP-17`'s flip-phase ordering, ship-
visibility-during-warp). Investigated rather than assumed away — **measured real fps directly**
(`window.__ijPerf()`) under two instruments:

| Instrument                                                | Backend | fps once SDSS loaded (3,637,862 galaxies + 543,742 stars merged) |
| --------------------------------------------------------- | ------- | ---------------------------------------------------------------- |
| Playwright's bundled Chromium (SwiftShader, CI's default) | webgl2  | **~3 fps**                                                       |
| Real installed Chrome (`channel: "chrome"`, real GPU)     | webgpu  | **~50-53 fps**                                                   |

A ~17x gap on the exact same scene. Re-ran the two specific failing assertions (GAP-17's
accel→flip→decel phase ordering; ship visibility reaching >0.5 during warp) against the real-GPU
instrument: both pass cleanly — `phases: ["accel", "flip", "decel"]` in strict order, arrival
confirmed, ship visibility reaches 1.0. **The underlying feature is correct.** SwiftShader's ~3
fps is real but not representative: at that frame rate, a narrow real-time window (GAP-17's flip
phase is only ~195ms of a 3.2s journey, already the tightest timing assertion in this suite even
before SDSS existed, per that test's own pre-existing comment) can fall between two widely-spaced
software-rendered frames and never register at all — a frame-granularity problem timeout-widening
alone cannot fix, unlike ordinary "just slower" flakiness.

This matches and extends a pattern this repo already has a precedent for
(`webgpu-hardware.spec.ts`'s own header: _"Playwright's bundled chromium... genuinely returns
null [for a WebGPU adapter]... Pointing Playwright at the REAL installed system browser instead
(channel: 'chrome') DOES yield a real hardware adapter"_) — SwiftShader is a known-unrepresentative
instrument for this repo's GPU-heavy scenes, now confirmed unrepresentative for frame-RATE, not
just WebGPU adapter availability.

**Action taken**: widened several E2E tests' real-clock timeouts (`test.setTimeout` + individual
`.poll` timeouts) across `engine-select.spec.ts` and `craft-ship.spec.ts` — a real, defensible
improvement for ordinary "somewhat slower" contention, clearly commented with this session's
actual measurements as justification (CLAUDE.md non-negotiable #15). **Not** a claim that this
fully resolves SwiftShader-specific frame-granularity misses for the single tightest test
(GAP-17) — that remains a known, now-quantified, real-hardware-confirmed-correct limitation of
CI's software-rendering instrument at PF-10's new "ideal state" scene scale, not a defect.

## Part 4 — Real memory/scale honesty

SDSS's mesh is genuinely large: 3,637,862 records × 4 billboard vertices = 14,551,448 vertices,
positions Float32Array ~174.6 MB, meta ~116.4 MB, indices Uint32Array ~87.4 MB — roughly 380 MB
of typed-array/GPU-buffer-adjacent memory for this one layer alone, on top of the existing star
mesh's own ~2,174,968-vertex buffers. This was NOT reduced or hidden — per the owner's ideal-
state-first direction, it ships at full real scale. Real device memory behaviour (does a mid-tier
Android's GPU/browser even accept buffers this large without OOM or driver-level failure) is
unmeasured and flagged honestly — this is exactly what the offered real Android hardware needs to
answer next, not something assumable from desktop GPU headroom.

    confirmed passing (`phases: ["accel","flip","decel"]`, ship visibility reaching 1.0). Root
    cause is SwiftShader's real ~3 fps at this scene scale falling below the frame granularity
    GAP-17's ~195ms flip window needs to ever register — a genuinely different failure mode from
    ordinary "too slow" flakiness, confirmed by directly measuring both instruments (Part 3),
    not assumed.
- **Real-hardware validation performed this session** (not deferred): `channel: "chrome"` real-
  GPU runs, using this repo's own established pattern (`webgpu-hardware.spec.ts`), confirming
  both the fps finding and the two SwiftShader-flaky assertions' actual correctness.
