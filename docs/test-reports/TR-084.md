## What this slice had to close

The delivery plan's **honesty contract**: the pre-flight dossier D1.2 will build must derive
every number it shows from real signals — "a timed animation is the instrument-fabrication
defect this repo already refuses." The audited baseline was worse than "no dossier": the HUD's
existing "STREAMING CHUNK" bar sat at 0% and then jumped, because **no fetch on the Babylon
path exposed byte progress at all** — every call site was a plain `fetch()`/`blob()`, no
`ReadableStream` readers, and `ImportMeshAsync.onProgress` was unused.

**Exit:** unit tests on the progress reader; an E2E asserting monotone byte progress with
totals matching asset sizes on disk.

## What shipped

**New pure module `src/lib/load-progress.ts`** (no DOM, no Babylon, fully unit-testable;
`now`/`fetchImpl` injectable, the same pattern `perf-telemetry.ts`'s `PerfMonitor` uses):

- `fetchWithProgress(url, stage, onProgress, opts)` — reads the response through the
  `ReadableStream` reader `fetch().body` already exposes, throttled to ≤ 4 Hz per stage
  (`STAGE_PROGRESS_MAX_HZ`), with the `done: true` event never throttled. Falls back to a
  plain `blob()` + single completion event when a response has no readable body, so it can
  never fail where the plain `fetch().blob()` it replaces would have succeeded.
- `StageAggregator` — **sums the several URLs one stage can span.** `star-catalog` is two PNG
  chunks and `bonus-layers` is four; without aggregation the dossier's counter visibly jumps
  backwards when the second chunk starts, which is exactly the class of lying instrument this
  slice exists to prevent. The aggregate total stays `null` while any part's total is unknown
  (an incomplete sum is not a total, and reporting it as one lets a bar hit 100% early) and
  falls back to the summed loaded bytes on `finish()`.
- `BOOT_CRITICAL_ASSETS` + `isBootCritical(stage)` — the boot-critical set is
  engine-init + star-catalog + atlas-map + first-frame, kept deliberately minimal per the
  experience review; everything else streams behind an already-interactive scene.

**New event `cosmos:stage`, strictly additive.** `cosmos:progress {loaded,total}` fires
exactly as before — and is now guarded by an E2E asserting its payload keys are still exactly
`["loaded","total"]`, because "the event bus is shared by both engines and existing shapes
never change silently" is a rule that deserves a test rather than a promise.

**Nine stages wired**, seven of them real transfers:

## Two findings — assets that no progress UI could previously have seen

**1. Havok's 2.09 MB WASM was structurally unobservable.** Emscripten fetches the binary
_inside_ the factory, where nothing outside can watch it. The fix is to stream it here and
hand over the buffer via `wasmBinary` — but that only works if the runtime honours it, so
**the vendored runtime was probed rather than assumed** (TR-081's lesson, applied
deliberately): `HavokPhysics_es.js` reads `wasmBinary=Module["wasmBinary"]` and its
`getBinarySync` returns `new Uint8Array(wasmBinary)` _before_ any network path is considered.
Confirmed: real progress, **no double fetch**.

`locateFile` is kept alongside `wasmBinary`, and that is a deliberate belt-and-braces choice
worth stating: if a future Havok bump ever stops honouring `wasmBinary`, the factory silently
falls back to fetching — which must still resolve to the same-origin Vite-emitted URL and
never a CDN. **Losing progress reporting is an acceptable degradation; losing the ADR-0005
origin guarantee is not.** The prefetch is also individually try/caught: a failure there just
returns Havok to fetching for itself, exactly as before this slice.

**2. `ImportMeshAsync` has always accepted an `onProgress`; it was simply never passed.** The
tiered craft GLB — up to 1.07 MB — was invisible to progress reporting for no reason beyond an
unused parameter. Babylon's own `ISceneLoaderProgressEvent` carries the real XHR numbers, and
its `lengthComputable: false` maps exactly onto our `null` total. One argument, no wrapper, no
second fetch.

## Stage-closing discipline (the non-obvious correctness requirement)

Several engine paths **degrade gracefully rather than throwing** — a missing deep chunk, a
404 atlas-map, a zero-count layer, a failed GLB. Each is a path where a stage could be started
and never closed, and a stage that never closes would hang D1.2's stall detector over a scene
that had already recovered and moved on. So every aggregator closes in a `finally`, `finish()`
is idempotent, and the success paths call it early with a record count so the `finally` becomes
a no-op. Two specific placements are deliberate:

- **`craft-glb` closes the moment `ImportMeshAsync` resolves**, not at the end of `_setupShip`.
  The transfer is complete there; the mesh normalisation, plume and shimmer work after it is
  local. The dossier reports downloads, not scene-graph assembly.
- **The no-WebGL branch closes all four boot-critical stages explicitly.** `createEngine`
  throwing means star-catalog/atlas-map/first-frame will never run at all — without this the
  fallback visitor's dossier would stall forever. This is the foundation D1-AC7 sits on, and it
  is verified in the manual pass below.

## Scope points recorded rather than silently resolved

All three are written additively into the [implementation plan](../implementation/PF-11-implementation-plan.md#d11-notes-as-built-2026-07-22-tr-084):

1. **The plan's prose names two `cosmos:stage` emitters its own type block omits** ("band build
   rows, mesh builds done"). Built to the type — band progress **already has a real signal**,
   `sceneStats().bandProgress`, which TR-081 explicitly handed to this slice. A band
   `LoadStage` would have created a second source of truth for one number.
2. **`atlas-photo` (atlas.jpg, 3.5 MB) is in the union but not wired** — the one named asset
   deliberately left unreported. Babylon's `Texture` fetches internally and exposes completion
   only. Wiring it means re-routing through a blob: URL — CSP-clean here (`img-src`/`connect-src`
   already carry `blob:` for exactly this path) but a real change to the GAP-02 photographic
   layer that deserves its own verification rather than a ride-along. Comment left at the call
   site.
3. **D1-AC1 belongs to D1.2.** "Some **visible** progress value changes within 2 s" is an
   assertion about a rendered surface; D1.1 ships no UI. Its throttled-CDP test lands with the
   dossier that can satisfy it.

## Known limitations

- `atlas-photo` unreported (above) — a visitor's dossier will account for ~59 MB of downloads
  and not for this 3.5 MB one until it is wired.
- The 4 Hz throttle is per stage, not global: nine concurrent stages could in principle emit
  36 events/second. In practice the boot stages are sequential and the post-ready ones overlap
  only briefly; the measured run produced 3–13 events per stage for the whole boot. If D1.2's
  React surface ever feels this, a global coalesce belongs there, not here.
- `fetchWithProgress` buffers chunks and reassembles a `Blob`, exactly as `fetch().blob()` did
  — no change in peak memory, but no improvement either. D7.3's SDSS worker is where the 47 MB
  path gets its real memory work.
- Progress reflects **transfer**, not decode. A stage reads 100% while its PNG decode and
  geometry build still run (both deliberately gated behind `_waitForWarpIdle`). Honest, but
  D1.2 should not word these as "ready".
