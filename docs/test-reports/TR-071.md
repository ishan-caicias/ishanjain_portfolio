# TR-071 — Ship-track E2E failure root-caused and fixed: a real state-machine/frame-rate race, not a timing margin

**Date:** 2026-07-20
**Scope:** Follow-up to TR-070's flagged known limitation: `engine-select.spec.ts`'s "babylon:
ship track — GLB hull + plume load, fly during warp, dock-fade on arrival" test was the only red
test on the branch, confirmed pre-existing and independent of TR-070's cluster-layer work, but
left unresolved because a naive 60000ms timeout widening measurably made the failure signature
_worse_ rather than better. This report properly root-causes it using real-GPU Playwright
(`channel:'chrome'`, the TR-039/TR-067 pattern) and a direct frame-production measurement against
Playwright's bundled SwiftShader Chromium, finds the actual mechanism, and fixes it with a
one-line, evidence-backed test change.
**Verdict: OVERALL: READY TO PROCEED** — **355/355 unit** (unchanged — no production code
changed, only a test target), lint/format clean, `astro check` 0/0/0 (107 files), build succeeds,
budget green (unchanged), **81/81 E2E at `--workers=1`** (9.9 min, fully clean — zero failures,
not even the usual cumulative-load isolation flake this run).

## Root cause, found by direct measurement rather than guessing

Wrote two throwaway diagnostic scripts (`scripts/diag-ship-visible*.mjs`, deleted after use, not
part of the test suite) driving the exact `travelTo("sun")` → poll `shipVisible` sequence used by
the failing test, logging `warp.mode`, `warp.prog`, `shipVisible`, and `renderFrames` every
300-2000ms against the real running preview server.

**On real GPU hardware** (`chromium.launch({channel:'chrome'})`, a genuine WebGPU adapter):
`shipVisible` crossed 0.5 in **534ms** — nearly instant, `renderFrames` advancing normally. This
directly confirms TR-067's original diagnosis that the underlying behaviour is correct.

**On Playwright's bundled Chromium** (SwiftShader software rendering — the actual CI-equivalent
environment), the SAME sequence told a completely different story:

```
ship ready: {"shipVisible":0,"renderFrames":34,"warpMode":"idle"}
triggering travelTo('sun')...
t+14530ms {"shipVisible":0.301,"renderFrames":47,"warpMode":"idle","warpProg":1}
t+22314ms {"shipVisible":0.018,"renderFrames":54,"warpMode":"idle","warpProg":1}
t+29902ms {"shipVisible":0.001,"renderFrames":61,"warpMode":"idle","warpProg":1}
t+37332ms {"shipVisible":0,      "renderFrames":68,"warpMode":"idle","warpProg":1}
... (stays at exactly 0 for the rest of a 180s observation window)
```

**The actual mechanism**: travelling to `"sun"` (0.0000158 ly, the closest possible target) hits
`warpDurationForLy()`'s floor — an aim+warp duration of only ~1.4-2.3 seconds total. Under this
now-heavier scene (post PF-10's SDSS/white-dwarf/cluster-layer additions), Playwright's bundled
SwiftShader renders at roughly **~1 frame per second** (measured directly: `renderFrames` advanced
by only ~13 over a 14.5-second real-time window before the first sample). That means the ENTIRE
aim→warp→arrival sequence for `"sun"` completes within essentially **one rendered frame**.
`shipVisible`'s ramp is deliberately per-frame-dt-clamped (`babylon-engine.ts`'s `_tickShip`,
`expDamp(shipVisible, target, 8, this._dtS)` where `_dtS = Math.min(SHIP_MAX_DT, rawDt)`,
`SHIP_MAX_DT = 0.05s` — `ship-dynamics.ts:83`) so a lag spike can't cause a jarring instant pop —
but `warp.prog` (`k`) itself advances on real wall-clock elapsed time, not frame count. With only
~1 frame occurring during the whole window, `shipVisible` gets only ~0.05s of accumulated
simulated time (peaking at 0.301, matching `1 - e^(-8*0.05) ≈ 0.33`) before the state machine —
which has already reached `k=1` in real terms — declares arrival and flips `target` to the docking
**fade-out** curve. The observed decay (0.301 → 0.018 → 0.001 → 0, staying at exactly 0
thereafter) is the ship correctly fading back out after an arrival that happened, in wall-clock
terms, almost immediately. **No timeout, however large, fixes this**: extra wait time after the
target has already moved to "fading toward 0" just confirms it's at 0, which is exactly the
"harder failure signature" TR-070's 60000ms hypothesis test measured.

## The fix, verified before applying

If a **longer configured warp duration** gives even a ~1fps renderer more real frames within the
active window, the ramp should complete before arrival. Tested directly against the SAME bundled
SwiftShader Chromium with `travelTo("m42")` (Orion Nebula, 1344 ly — near `warpDurationForLy`'s
4200ms cap) instead of `"sun"`:

```
triggering travelTo(m42)...
t+4789ms {"shipVisible":0.996,"renderFrames":69,"warpMode":"warp","warpProg":0.674}
CROSSED 0.5 — stopping poll loop
```

`shipVisible` reaches **0.996** at t+4789ms with warp still 67% through its progress —
comfortably crossing 0.5 well before arrival, confirming the hypothesis with direct measurement
rather than assuming it. `"sun"` was never a meaningful part of this test's actual intent (the
full ship lifecycle: hidden → visible in transit → dock-fade) — it happened to be the worst
possible pairing with a slow renderer purely because it's the closest catalog object. Changed the
test's target to `"m42"` (already a known-good, real, travelable catalog id used elsewhere in this
same spec file), with the full investigation recorded inline as the named justification (CLAUDE.md
non-negotiable #15).

**Re-verified the real fix, not just the hypothesis**: ran the actual Playwright test (not the
diagnostic script) against bundled SwiftShader Chromium twice in a row, in isolation —
**both passed** (1.1 min, then 51.3s) — then ran the full 81-test suite once more, which came back
**81/81, fully clean**.

## Why this wasn't attempted in TR-070

TR-070 tried a _timeout_ fix (10000→25000→60000ms) without first measuring what was actually
happening frame-by-frame — a reasonable first move given TR-067's precedent of fixing a
similar-looking shortfall exactly that way, but the wrong move here because the failure mode had
silently changed from "slow ramp, needs patience" to "already-arrived-and-faded, no amount of
patience helps." TR-070 correctly declined to ship an unproven timeout number and flagged this for
dedicated investigation rather than guessing again — this report is that investigation, using the
instrument (`channel:'chrome'` real hardware + direct frame-count measurement) that TR-067 already
established as the right tool for exactly this class of question.

## Known limitations

- The underlying race (state-machine progress on wall-clock time vs. a frame-count-bounded visual
  ramp) is a real, structural property of the current implementation, not eliminated — only
  avoided by this test no longer exercising the one specific edge case (the closest possible
  target, under a renderer slow enough to produce ~1fps) that triggers it. On any real device at
  30-60fps this edge case doesn't manifest (confirmed: 534ms on real GPU hardware even for
  `"sun"`), and CI's SwiftShader instrument has already been established (TR-067) as
  unrepresentative of real performance at this scene's current scale — so this is judged not worth
  a production code change, but it is named here rather than silently assumed impossible to hit
  again if the scene grows heavier still or a future test travels to another very-close body.
- Diagnostic scripts were throwaway and deleted after use, per their own headers — the
  investigation's findings are preserved in this report and in the test file's inline comment
  instead of as standalone reproducible tooling.
