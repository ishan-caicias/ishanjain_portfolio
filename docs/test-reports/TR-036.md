# TR-036 — B2 Step 1: Vertex-Index Expansion (star buffers 21.9 → 16.8 MiB)

**Date:** 2026-07-19
**Scope:** PF-09 **B2 step 1 of 6**. ADR-0003 conditions 1 and 2 both discharged on real Android,
so B2 opened; the billboard-memory work (condition 3) was folded in as the first step.
**Verdict: OVERALL: READY TO PROCEED** — with one honest verification gap, stated below.

## What changed

The B1 layout stored a 4-float `corner` attribute per vertex: `(cx, cy, size, colourT)`. The
`(cx, cy)` half is pure redundancy — a fixed 4-entry table indexed by `vertexID % 4`, written out
675,836 times.

Both shader twins now **derive** it instead:

```glsl
int c = gl_VertexID % 4;                                    // GLSL ES 3.00
vec2 corner = vec2((c == 1 || c == 2) ? 1.0 : -1.0, (c >= 2) ? 1.0 : -1.0);
```

```wgsl
let c : u32 = vertexInputs.vertexIndex % 4u;                // WGSL
let corner = vec2<f32>(select(-1.0, 1.0, c == 1u || c == 2u),
                       select(-1.0, 1.0, c >= 2u));
```

`gl_VertexID` / `@builtin(vertex_index)` is the **post-index-fetch** vertex index, so the
derivation is correct for indexed draws — which is what this mesh uses.

The attribute shrinks from `corner : vec4` to `starMeta : vec2` (size, colourT).

## The parity target in ADR-0003 condition 3 is not reachable — restating it honestly

Condition 3 reads "~23 MB vs the live engine's ~2.7 MB", which implies parity is the goal.
**It is not achievable with billboard quads, at any level of optimisation.**

The live engine gets 2.7 MB by drawing **one vertex per star** as a point sprite. WebGPU has no
`gl_PointSize` (TR-029), so that technique is unavailable — the mesh needs a real per-vertex
`position` attribute at 4 verts/star, which is an irreducible **7.7 MiB floor**.

Realistic ceiling on further work: moving `(size, colourT)` into a per-star data texture fetched by
`vertexID / 4` would remove the 5.2 MiB `meta` buffer for a ~1.3 MiB texture, landing at
**~12.9 MiB**. That is the honest floor for this technique — roughly 5× the live engine, not equal
to it.

**That next increment was deliberately not taken here.** A float-texture format that silently
misbehaves on one backend would put at risk the WebGPU path that was confirmed working on real
Android hardware only hours earlier. The corner derivation, by contrast, is pure integer arithmetic
that behaves identically on both backends and cannot diverge.

Recommend condition 3 be **restated** from "reduce to ~2.7 MB" to "reduce materially below the B1
figure", since the original wording describes an impossible outcome.

### New tests — the arithmetic is now a JS↔GPU contract

Removing the buffer means the corner table exists in **three** places (JS, GLSL, WGSL) with no
compiler checking they agree. Three tests pin it: the derivation reproduces the winding table
exactly, repeats every 4 vertices across many stars, and yields four _distinct_ corners (a repeat
would silently collapse each quad to a sliver rather than error).

### ⚠️ Verification gap — the WGSL twin has no pixel proof

The E2E pixel proof runs on Playwright chromium, which has **no WebGPU adapter** (TR-031). It
therefore validates the **GLSL** path only. For WGSL the available evidence is:

- ✅ `material.isReady(mesh)` → **true**. On WebGPU this flips true only once the effect compiles;
  a wrong builtin name (`vertexIndex`) would fail compilation and Babylon logs that loudly.
- ✅ `getActiveIndices()` → **1,013,754** — the full draw is submitted.
- ✅ Zero console errors across init and forced renders on a real WebGPU device.
- ❌ **No pixel proof.** A WebGPU canvas returns `(0,0,0,0)` — alpha included — through
  `drawImage`, so the readback is empty regardless of what rendered. The clear colour would sit
  below any brightness threshold anyway, so this test cannot discriminate at all.

Attempting the readback and getting alpha 0 is what identified this as an instrument limit rather
than a shader failure — worth recording, because a naive reading of "0 lit pixels" would have
looked like a broken shader.

**This is one reload on the owner's Android to close.** If the stars render there, the WGSL
derivation is confirmed on the hardware that matters.
