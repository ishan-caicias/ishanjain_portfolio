change in `render-layers.ts` (`status: "unavailable"` → `"live"`) plus its data pipeline."_ The
data pipeline was the real work — a sixth local Gaia Sky binary format, undocumented publicly at

## D8.1 — ADR first, per the plan's own requirement

[ADR-0012](../adr/0012-gaia-tiny-chunked-layer.md) written before code, then updated in place
with real measured numbers once the pipeline ran (its own header records both). Full derivation

### The binary format: reverse-engineered and byte-verified

`resources/gaia_datasets/catalog-gaia-dr3-tiny`'s `metadata.bin` + `particles_NNNNNN.bin` files
are Gaia Sky's OctreeLoader container — a format with **no reader anywhere in this repo** before
this slice. The public docs page (`gaia.ari.uni-heidelberg.de/gaiasky/docs/master/LOD-catalogs.html`)
documents particle-record versions 0–2 only; the real local files declare **version 3** in their
own header. Version 3's layout was derived from Gaia Sky's own source
(`codeberg.org/gaiasky/gaiasky`, MPL-2.0 — read for format reference only, no code copied:
`BinaryDataProvider`/`BinaryVersion3`), then implemented in
[`scripts/lib/gaiasky-octree-particles.mjs`](../../scripts/lib/gaiasky-octree-particles.mjs) and
byte-verified against the real local file: decoding `metadata.bin` lands `cumulativeStars`/
`starsInNode` on exactly 2,552,302 / 2,200,000 (the catgen log's own totals, to the integer), and
decoding `particles_000000.bin` consumes exactly 178,178,964 of 178,178,964 bytes, zero
remainder.

### Coordinate conversion: empirically derived, verified against SIMBAD and a precise parallax

Neither the octree's Cartesian axis convention nor its distance unit is documented anywhere.
Both were recovered by decoding real named stars and comparing against external ground truth
(not assumed, not guessed):

- **Axis mapping** — `RA = atan2(x, z)`, `Dec = asin(y / r)` — verified to 4 decimal places
  against SIMBAD for two independent stars (HIP 89341: 273.4409°/−21.0588° vs. SIMBAD
  273.4409°/−21.0594°; HIP 66768: 205.2790°/−62.4994° vs. SIMBAD 205.2789°/−62.4993°).
- **Distance unit** — 1 raw unit = 1 gigametre — verified against Sirius's precisely known
  parallax distance (2.6371 pc): decoded distance 2.6371 pc, agreement to the stated precision.
- mu Sagittarii's decoded distance (11,111.1 pc) independently matches its catalogued parallax
  (0.09 mas → 1000/0.09 = 11,111.1 pc) to 5 significant figures — a second, unplanned
  cross-check the derivation happened to reproduce exactly.

### Colour: `tEff`, not the record's own `color` field — a real finding, not an assumption

Sampling 352,302 real records found the v3 record's `color` field **100% sentinel**
(~−1.5×10³⁸, a Java "unset" marker) — never physically meaningful in this dataset, despite the
source CSV carrying real `bpmag`/`rpmag` columns per the catgen log. `tEff` (effective
temperature) IS reliably populated and physically sane (3465–5634K in the same sample, squarely
inside real K/M main-sequence range). Colour is derived from `tEff` via the Ballesteros (2012,
EPL 97 34008) blackbody T↔B-V relation — the same algorithm Gaia Sky's own renderer uses for
this exact purpose (`gaiasky.util.color.BVToTeff_ballesteros`) — inverted numerically by
bisection on the monotonic forward formula (not an algebraic solve, so a mistake expanding the
quadratic could not silently ship). Calibration: exact at the Sun (5778K → B-V 0.650, the
textbook value); Vega/Sirius A within 0.02–0.045 mag; Betelgeuse/Rigel (evolved super/giants,
where the pure-blackbody assumption is known to break down) directionally correct but off by
~0.1–0.2 mag — an honest limitation of the approximation, not a bug. **A full Astra
REALISM-AUDIT of this substitution is a recorded follow-up, not attempted this pass** —
mechanically sound and Sun-calibrated, but not yet independently reviewed for astrophysical
appropriateness the way TR-064 reviewed the white-dwarf colour range.

### Dedup: a real calibration finding overrode the original design

The plan's original design (position+magnitude crossmatch against the shipped Hipparcos base
field) assumed the base field carries _something_ to match by id. It does not —
`assets/stars-hip.png`'s 15-byte record (`x,y,z,magByte,ciByte,typeByte`) has no id of any kind,
confirmed by reading `star-catalog.ts`'s own decode contract. A 300-star calibration sample
found **300/300 (100%) sub-arcsecond position matches** (median 0.1″) — the same Hipparcos
astrometric solution in both catalogs, as expected — but the magnitude delta between the two
datasets ranged **0.07 to 4.19 mag**, not a tight cluster near 0: the base field's brightness
byte is not on a Gaia-G-band-compatible photometric scale (undocumented, vendored pre-existing
asset — no build script for it exists in this repo). The original `|Δmag| < 0.3` gate was
confirmed live to silently reject the large majority of genuine matches (32,775/117,948, 27.8%,
against the broader name-truthy candidate set). **Final design: position-only match** (< 5
arcsec), with a generous `|Δmag| < 6` kept only as a sanity backstop, never a real filter.

## D8.2 — Pipeline

[`scripts/gaia-tiny-pngpack.mjs`](../../scripts/gaia-tiny-pngpack.mjs), `npm run gaia:tiny`.
Two-pass, typed-array streaming (Float32Array sort keys, Uint8Array drop flags, one pre-sized
output Buffer) — per this repo's own C0 "wrong tool past roughly a million records" finding,
2.55M records never becomes 2.55M JS objects.

**Real run totals:** 2,552,302 source stars → 117,904 HIP-tagged candidates checked (via
`extractHipNumber`'s `"HIP <n>"` name-prefix read, not a bare name-truthy check — a real
precision fix made mid-slice, see below) → **112,847 deduped, 2,439,455 kept** → 8
magnitude-sorted chunks (304,921–304,932 records / ~4.6 MB each) → **36,792,163 bytes (35.09
MiB) total on disk**, inside the original 31–42 MiB estimate range.

**A real mid-slice correction, worth recording:** the pipeline's first draft scoped dedup
candidates to "any named record" rather than "any HIP-tagged record", which both over-counted
candidates (117,948 vs. the correct 117,904) and left an unused `extractHipNumber` import (a
real lint failure that caught it). Fixed before shipping; the final numbers above are the
corrected run's.

**Round-trip unit-tested** ([`tests/unit/gaiasky-octree-particles.test.ts`](../../tests/unit/gaiasky-octree-particles.test.ts),
16 tests): independently-constructed fixtures for both `metadata.bin` and `particles_*.bin`
(matching `gaiasky-binary-particles.test.ts`'s established pattern — fixtures never reuse the
reader's own encode logic), plus regression cases pinning the axis-mapping and distance-unit
formulas against the SAME real reference values (SIMBAD stars, Sirius) the ADR's derivation
used — a future refactor that silently breaks the coordinate conversion fails these, not just a
shape check.

## D8.3 — Runtime

**`render-layers.ts`:** `gaia-tiny`'s `status` flips `"unavailable"` → `"live"`,
`defaultByTier` becomes `{ full: 0, balanced: 0, lite: 0 }` (off everywhere — an opt-in heavy
layer, matching D9.4's "current shipped behaviour made visible" convention, not a D0.3-measured
recommendation), `maxCount: 8`, `assetBytes` reads `layerBytes.gaiaTiny`.

**`babylon-engine.ts`:** new `_setGaiaTinyChunks(scene, engine, target)` — **per-chunk meshes**,
deliberately not one growing mesh with `_applyDensity`-style index-trim as the plan text
literally described (ADR-0012 §4 explains why: per-chunk meshes solve both grow-without-refetch
and shrink-without-rebuild with less bookkeeping and no requirement to keep ~200+ MB of merged
CPU-side vertex data resident). Growing re-enables any already-fetched chunk instantly and
fetches only the still-missing ones through the existing `_decodeCatalogInWorker` path (the same
worker `_loadSdssGalaxyLayer` uses — chosen over `belt-visual`'s main-thread decode because
gaia-tiny's per-chunk size, ~4.6 MB / ~305K records, is close to SDSS's scale, not belt-visual's
smaller one). Shrinking is a pure `setEnabled(false)` on the tail chunks — zero network, zero
rebuild. Disabling entirely (count → 0) disposes every chunk mesh, matching D7.1/D7.2's "disable
actually releases GPU/CPU geometry" discipline the other D9 layers already follow.

**A real bug found and fixed during this slice's own verification, not by inspection:**
`setLayers()` only calls `_applyLayerToggle` for values that CHANGE from the already-resolved
boot state — the INITIAL resolved value (from `?layers=`/localStorage/tier default) was never
acted on for gaia-tiny, exactly like the three layers above it in the boot sequence
(`bonus-stars`/`sdss-field`/`belt-visual` each get their own explicit boot-time kick). Missing
this made `?layers=gaia-tiny:3` a complete no-op at boot — caught by this slice's own new E2E
tests (3 of 5 failed on the first isolated run with `gaiaTinyEnabledChunks` stuck at 0), not by
code review. Fixed by adding the same explicit boot-time trigger the other three layers already
have.

**A second real bug found and fixed, in the panel, not the engine:** `RenderConsole.tsx`'s
`EVERYTHING` preset special-cased `belt-physics` by id (`l.id !== "belt-physics"`) to avoid
sending it a bare `true` instead of a count. Once `gaia-tiny` — the only OTHER count-type layer
in the registry — went live, that same hardcoded check would have sent it `true` too, decoupling
the panel's numeric input (which falls back to displaying `0` for a non-number value) from the
engine's real chunk-prefix state. Generalized to check the SHAPE of `defaultByTier.full` (`number`
= count layer) instead of a hardcoded id, so a future count layer is covered automatically. New
regression test pins `typeof call["gaia-tiny"] === "number"` under `EVERYTHING`.

**Panel UI required zero new code** — D9.1/D9.2's registry-driven numeric-input rendering
already generically handles any `number`-typed `defaultByTier` layer; the only visible change is
the row leaving its permanently-disabled "COMING IN A FUTURE UPDATE" state. Confirmed live on
the built preview (`npm run preview`): opened RENDER ▸, set the gaia-tiny input to `2`,
`sceneStats()` read back `{"layers":{"gaia-tiny":2},"gaiaTinyCount":609894,"gaiaTinyEnabledChunks":2}`
— a real fetch, decode, and mesh build triggered by the real panel input, zero console errors.

## What this proves, and what it does not

**Proven by automated coverage + a live manual check:** the OctreeLoader binary format decodes
byte-exact; the coordinate conversion is astronomically correct (verified against SIMBAD and a
precision parallax, not assumed); the dedup crossmatch runs and its match rate is measured, not
guessed; the chunk-prefix layer fetches, grows, shrinks, and disposes correctly through the real
panel UI and the real engine; two real bugs (the missing boot-time trigger, the EVERYTHING-preset
count-layer regression) were caught by this slice's own new tests before shipping, not left for a
later remediation report.

**NOT proven here:**

- **Real-device heap/VRAM measurement has not run.** Fully enabling gaia-tiny's ~2.44M stars
  (10.2M vertices — "15.1× the vertex stage" the delivery plan's own inventory flagged) is
  unmeasured on real hardware. D0.3 owns this, same as every other D9 layer's default.
  `defaultByTier: 0` everywhere means no device pays this cost unless a visitor opts in.
- **A full Astra REALISM-AUDIT of the `tEff`-derived colour substitution has not run.** The
  Ballesteros conversion is Sun-calibrated and mechanically sound but not yet independently
  reviewed for astrophysical appropriateness across the dataset's full temperature range, the
  way TR-064 reviewed the white-dwarf colour range specifically.
- **The residual 4.3% dedup gap (5,057 of 117,904 HIP-tagged candidates unmatched) is
  unexplained**, plausibly a slightly different Hipparcos edition/cut between the two datasets'
  origins — quantified and recorded, not investigated further this pass.
- **Owner-eyes visual confirmation on a real phone/tablet is still owner-pending**, same as
  every other D9.4 default.
