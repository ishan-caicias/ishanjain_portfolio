# TR-106 — CI E2E model change: curated smoke subset (first green CI run — VERIFIED)

**Date:** 2026-07-25
**Slice:** (1) Fix the e2e-shard Git-LFS gap that broke `load-progress.spec.ts` in TR-105's
verification run; (2) replace the 4-shard full-suite CI matrix with a curated smoke subset,
per owner decision, since the full suite has never passed on GitHub's free runners.
**Predecessor:** [TR-105](TR-105.md) (Git-LFS root-cause fix; first-ever partial-green CI run,
run 30156141504 — Build/Lint/Unit/Typecheck green, shard 4/4 green, shards 1-3 red).

## What the first correct-build CI run actually showed

TR-105's LFS fix produced [run 30156141504](https://github.com/ishan-caicias/ishanjain_portfolio/actions/runs/30156141504) —
the first CI run ever built from real assets. Result: **137/150 passed**, 13 failed, split into
two distinct causes:

**Category A — an LFS gap I missed (2 failures, fixed here).** `load-progress.spec.ts:105/164`
does `fs.statSync("public/assets/stars-hip.png")` etc. directly against **the e2e job's own
checkout**, not the downloaded `dist/` artifact. TR-105 added `lfs: true`-equivalent fetching to
`build` and `lint` only — the e2e job's checkout was still un-LFS'd, so this one test's disk-read
comparison got pointer-stub sizes (263 bytes) while the live served page (correctly built from
the LFS-fixed `dist`) reported real bytes (2,891,934). Not a hardware issue — this job's checkout
just needed the same fix. Grepped all 9 smoke-set files for direct fs reads; only this one does
it.

**Category B — a real hardware ceiling (11 failures, NOT fixed here — see decision below).**
`ascent`, `camera-zoom`, `craft-ship`, `d64-owner-bugfixes` (all 4 of its tests),
`engine-select` (3 of 29), `frame-ladder` — every failure a timeout/margin miss.
`d64-owner-bugfixes.spec.ts:254` exceeded its own 150-second **test** timeout mid-arrival, not
just an assertion's poll budget. GitHub's free `ubuntu-latest` runners (2 vCPU) cannot
software-render this scene's real travel/arrival sequences fast enough to hold timing margins
calibrated on the owner's 16-core development machine.

**A scan of the last 20 CI runs on this repo found E2E had failed on every single one**, back
through weeks of history, predating this session entirely. TR-104's sharding didn't cause this
and didn't fix it — CI E2E was never once green before shard 4's 34/34 in this run.

## Decision: CI runs a smoke subset; the local machine is the real gate

Presented to the owner as an explicit choice (build a fully CI-hardware-viable full suite vs. a
curated fast subset vs. drop E2E from CI). **Chosen: curated smoke subset.** Full reasoning and
the exact file list: [docs/cicd/2026-07-25-e2e-ci-smoke-subset.md](../cicd/2026-07-25-e2e-ci-smoke-subset.md).

Summary: the 4-shard matrix (TR-104) is removed — it existed only to fit 150 tests inside CI's
practical time budget, a problem that doesn't exist for a ~39-test subset. Replaced with a single
`e2e-smoke` job running the 9 files that had **zero failures** in the real run above:
`accessibility`, `craft-assets`, `page-load-console`, `navigation`, `perf-budgets`,
`webgpu-hardware` (fails open/skips in CI already), `funnel`, `planet-pixels`, and
`load-progress` (once its Category A gap is fixed). The `e2e-summary` aggregator job is removed
too — it existed to preserve a `"E2E Tests"` required-status-check name for branch protection,
but `gh api repos/.../branches/main/protection` returns 404: **`main` has no branch protection
configured at all**, so that concern was moot from the start (noted as a correction in the
superseded doc, not silently dropped).

The full 150-test local suite remains the required pre-push gate (CLAUDE.md #25 unaffected) —
this is a CI-scope decision, not a coverage or quality-bar decision. The 6 excluded files keep
running locally in full on every gate.

job's real tally was **35 passed, 3 skipped (webgpu-hardware, fails open as designed), 1
FLAKY, 0 failed** — `accessibility.spec.ts:104` ("scene chrome stays keyboard-operable on the
Babylon path") lost a focus race on its first attempt
(`expect(rng).toBeFocused()` → `"Received: inactive"`, 5000ms timeout) and passed on CI's
pre-existing `retries: 2` (`playwright.config.ts`, unrelated to this slice). This is real,
measured flakiness, not swept under "1 flaky test, ignore it" — a focus call immediately
followed by asserting it landed is exactly the class of timing-sensitive check that can lose a
race under CI's slower software rendering; if it recurs, the fix is almost certainly a
`.poll()`-style wait for the focus state to settle rather than a bare synchronous assertion, not
a retry-count increase. Not fixed in this pass (one occurrence, passed on retry, not a pattern
yet) — flagged below as a watch item.

## Known limitations / follow-ups

- **Watch item: `accessibility.spec.ts:104`'s focus-race flake.** One occurrence this run,
  passed on retry. If it recurs on a future CI run, replace the bare
  `await expect(rng).toBeFocused()` with a poll-based wait — not a retry-count increase — since
  the underlying issue is a timing race, not flappy infrastructure.
- **A pre-existing doc inconsistency, found while checking this:** the 2026-07-19 Node-runtime
  doc's index row claims `main` has "a ruleset with self-approval rationale," but
  `gh api repos/.../branches/main/protection` returns 404 today. Either protection was removed
  since then or that row is stale — flagged for the owner to check in GitHub's settings; not
  investigated further here (out of scope for this slice).
- **Category B files need Lever B, not a CI fix.** If the test-boot flag (TR-105 Part 3) lands
  and lightens `ascent`/`camera-zoom`/`craft-ship`/`d64-owner-bugfixes`/`engine-select`/
  `frame-ladder`'s per-boot cost, some may become CI-viable again — worth re-checking then, not
  assumed now.
- **LFS bandwidth**: the smoke job still pulls the full LFS object set on a cache miss (`git lfs
pull` doesn't filter to only what the 9 files need) — a further optimization (`--include=`)
  is possible but not applied this pass.
