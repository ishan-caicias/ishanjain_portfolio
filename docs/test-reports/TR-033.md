## Finding 1 — `displayHz` was my bug (fixed)

`displayHz` used the **minimum** frame delta with a 4 ms floor. A single pair of coalesced rAF
callbacks yields a sub-4 ms delta, which latched the estimate to the 250 Hz ceiling — visible in
the table as 250 Hz on a phone and 217–238 Hz elsewhere. **No such panel exists.**

Fixed to the **10th-percentile** delta, which ignores one-off outliers. Verified: the same steady
60 Hz stream containing one pathological 1 ms frame now reports **60 Hz**, not 250. On the
production build the estimate dropped from a phantom 106–250 Hz to an honest **13 Hz** (matching
the 12 fps SwiftShader actually achieves).

Also relabelled honestly: because `displayHz` derives from the same rAF stream as `fps`, it is a
**weak** self-check, not an independent panel probe.

## Finding 2 — the iPhone rows are physically impossible

`RENDER FPS` **135** and **144** on an iPhone. Both engines drive their render loops from
`requestAnimationFrame`, which is vsync-locked, and iPhone panels top out at **120 Hz**
(ProMotion) or 60 Hz. Neither figure is achievable on any iPhone.

Combined with all six rows landing in a 135–144 band across three supposedly very different
device classes, the most probable explanation is that the mobile rows came from **DevTools device
emulation rather than physical hardware**. Emulation changes viewport and user-agent but still
runs on the desktop GPU at the desktop refresh rate — which would produce exactly this signature.
That is an entirely reasonable thing to have done; it simply cannot answer this gate, whose whole
purpose is to measure real mobile GPU, thermal and memory behaviour.

**This is not yet a confirmed conclusion** — it is the leading hypothesis, and the owner can
settle it in one step (below).

## Fix — make device identity impossible to omit

The overlay previously showed no hardware information, so a recorded row carried no evidence of
its origin. It now ends with a device signature line:

```
ENGINE webgl · TIER high
STARTUP 1264ms
▶ RENDER FPS 12   ← RECORD THIS
   host rAF 12 / 13Hz
   rendered 85
   Windows · 1280x720 · dpr1 · 16c
```

`deviceSignature()` also flags a likely-emulated row: a UA claiming Android/iPhone while reporting
≥12 CPU cores earns `⚠LOOKS EMULATED`, since no phone reports a desktop core count.

## What settles it

Re-read one Babylon row on the actual iPhone and paste:

```js
JSON.stringify(window.__ijPerf().device);
```

- A real iPhone reports `iOS`, a phone-sized `screen`, `dpr` 2–3, and a low `cores` count.
- Emulation reports the desktop's UA-adjacent fields — most tellingly a desktop `cores` value
  (16 on this machine) — and now self-flags `⚠LOOKS EMULATED`.

If the mobile rows were emulated, the desktop row still stands and only the two mobile classes
need re-running on hardware.

## Process note

Third consecutive round in which the instrument, not the owner, was the limiting factor
(TR-032 host-rAF over-report; TR-032 addendum overlay patch silently no-opping; this report's
refresh estimator + missing device identity). Each was caught only by checking physical
plausibility against the numbers. The lesson worth carrying into B6's CI perf budgets: a
measurement harness needs plausibility assertions **inside** it — a number that cannot physically
occur should be rejected by the instrument, not by a reviewer noticing later.
