## The DPR/fill-rate hypothesis, and why it doesn't need a code change to test

`src/lib/babylon-engine.ts` creates the Babylon engine with `adaptToDeviceRatio: true` and no
device-pixel-ratio cap — the canvas renders at the display's full native resolution. The S24
Ultra's screen is substantially higher-resolution than the S20 FE's; at uncapped DPR the flagship
would need to shade proportionally more physical pixels per frame than the mid-tier phone for
_identical_ scene content, regardless of which GPU is faster in the abstract. This is a plausible,
common, and non-buggy explanation — flagship phones with QHD+ panels routinely lose raw fps to
lower-resolution phones on fill-rate-bound content.

This was flagged as an open hypothesis in TR-068, with the recommendation to capture the
`ENGINE`/`TIER` overlay lines to test it. Re-reading the code this pass found the confirming data
is _already collected and already displayed_ — no instrumentation gap exists:

- `src/lib/perf-telemetry.ts`'s `PerfSnapshot.device` already carries `dpr`, `screen`, and
  `viewport`, and `deviceSignature(d)` already formats them as
  `` `${os} · ${d.screen} · dpr${d.dpr} · ${d.cores}c` ``.
- `src/components/islands/SpaceScene.tsx`'s `?perf=1` overlay already renders this as its
  **last line**, below the `ENGINE ... · TIER ...`, `STARTUP`, `RENDER FPS`, and `host rAF` lines
  already being reported.

Neither round of measurements so far has included the `ENGINE`/`TIER` line or the device-signature
line — only the three numbers explicitly called out with "← RECORD THIS" in the overlay were
reported. That's a reporting gap, not a missing feature; **no code change is required** to close
it, only reading one more line already on screen.
