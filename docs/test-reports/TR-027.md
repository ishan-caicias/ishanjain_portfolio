# TR-027 — PF-09 B0: Dual-Engine Scaffold + Perf Telemetry

**Date:** 2026-07-18
**Scope:** [PF-09-babylon-havok-realism.md](../delivery-plan/PF-09-babylon-havok-realism.md)
Phase B0 — add Babylon behind a flag, stand up the dual-engine switch and the perf-telemetry
harness that the B1 go/no-go gate will use. No visual parity (that is B1).
**Verdict: OVERALL: READY TO PROCEED**

## What changed

1. **Engine selector** ([engine-select.ts](../../src/lib/engine-select.ts)) — pure
   `resolveEngine(?engine, stored)` → `'webgl' | 'babylon'`, default `webgl` (URL param wins,
   then stored override). Mirrors `craft-tier.ts`.
2. **Perf telemetry** ([perf-telemetry.ts](../../src/lib/perf-telemetry.ts)) — engine-agnostic
   `PerfMonitor`: times mount → `cosmos:ready` for startup, samples rAF deltas for a rolling
   fps (outlier-guarded, bounded window), classifies device tier. Host-side, so **no change to
   either engine's internals**. Reports on demand via `window.__ijPerf()` and the `cosmos:perf`
   event; a visible readout is opt-in via `?perf=1`.
3. **Babylon engine** ([babylon-engine.ts](../../src/lib/babylon-engine.ts)) — a self-registering
   `<babylon-scene>` custom element (mirrors `<space-engine>`) rendering a minimal Babylon WebGL2
   scene, emitting `cosmos:progress`/`cosmos:ready` so the loading overlay + HUD behave. Travel
   contract present as stubs (B2 wires it). No-WebGL fallback parity (never blanks the page).
4. **SpaceScene wiring** — first render is always `<space-engine>` (matches the `client:load`
   SSR HTML — resolving synchronously would risk a hydration mismatch); a post-hydration effect
   swaps to `<babylon-scene>` only when `?engine=babylon`. The Babylon branch carries no `ref`, so
   the host's `querySelector("space-engine")`-based calls no-op and the preview self-runs.

The `?engine=babylon` E2E asserts `startupMs !== null`, which only becomes true after the scene
emits `cosmos:ready` — i.e. after a real rendered frame — so a passing spec is proof Babylon
initialized and rendered in headless Chromium, not merely that the element mounted.

**Interactive browser-pane check:** attempted but blocked by pane↔dev-server connectivity
(`chrome-error://`) and the slow 5 MB unbundled Babylon dev-compile under E2E load — an
environment issue, not a page defect. The deterministic production-build E2E is the authoritative
proof and is green.

## Key measured finding (feeds B1)

The barrel import `@babylonjs/core` produced a **1.1 MB gz** chunk (5 MB raw) — over the plan's
~900 KB engine budget — because Babylon's barrel does not tree-shake. **B1 must switch to
tree-shaken subpath imports** (`@babylonjs/core/Engines/…`) and `WebGPUEngine`, and re-measure
against the budget. Logged here so the B1 gate starts from a real number, not a vendor estimate.
