## Part 1 — The cluster background layer, built and wired

**Source data**, all 3 confirmed real VOTable 1.3 BINARY2 files this session (MWSC was already
known from TR-061; Hunt-Reffert 2023 and OCDR2 were assumed but unverified — both checked and
confirmed BINARY2, not the TABLEDATA variant CNS5/GD-1 turned out to be):

| Source            | Records | Distance field                                 | Real range check                                                 |
| ----------------- | ------: | ---------------------------------------------- | ---------------------------------------------------------------- |
| MWSC              |   3,006 | `distance` (pc)                                | Same field TR-061 already sanity-checked (Pleiades/Praesepe/M38) |
| Hunt-Reffert 2023 |   7,167 | `dist50` (pc, median of a 3-quantile estimate) | All rows carry `Ndist>=1`                                        |
| OCDR2             |   2,017 | `dist` (pc)                                    | —                                                                |

All 12,190 raw rows decoded with **zero nulls** across ra/dec/distance in every source — no
skip-for-missing-data path was needed (unlike CNS5/white dwarfs, which had real parallax gaps).

**New code:**

- [`scripts/lib/cluster-dedup.mjs`](../../scripts/lib/cluster-dedup.mjs) — great-circle angular
  separation + a combined angle+distance dedup predicate, extracted into its own testable module
  (not inlined in the pack script) specifically so a unit test can exercise it without executing
  the pack script's `main()`, which reads real local dataset files and writes a PNG asset.
- [`scripts/gaia-clusters-pngpack.mjs`](../../scripts/gaia-clusters-pngpack.mjs) — reads all 3
  VOTables via the already-proven `votable-binary2.mjs` reader, converts ra/dec/distance to the
  same `raDecToDir` + light-year convention every prior PF-10 pack script uses, and writes the
  shared 15-byte-record PNG format via `writeRecordsAsPng`.
- `public/assets/clusters-bg.png` — the real shipped asset, 1024×59, 163 KB, 12,065 real records.

**Dedup against the 35 already-curated named clusters** (`celestial-clusters.js`): those are
hand-verified against modern literature, not raw pipeline pulls (see that file's own header), so
their ra/dec/ly never byte-matches a raw catalog row exactly, and cross-catalog name matching is
unreliable here anyway (MWSC uses underscore names, Hunt-Reffert ships pipe-delimited cross-match
compounds, OCDR2 uses yet another convention) — and irrelevant besides, since a background layer
carries no per-object name. Deduped instead by real sky position: angular separation <1.0° AND
distance within 30% relative difference (angle alone is treated as sufficient when a raw row
carries no usable distance). **12,190 raw → 125 excluded as duplicates → 12,065 background
records** — close to but not exactly the plan's "~12,155" estimate, a real measured number rather
than the original approximation.

**Photometry**: none of the 3 source VOTables carry a per-object apparent-magnitude field (checked
the real FIELD schema of each, not assumed). This is the same "no real photometry in the source"
situation the Oort cloud script (TR-066) already flagged and explicitly named this cluster layer
as sharing ("the same honest label already accepted for the bulk MWSC background cluster layer" —
written in `gaia-oortcloud-pngpack.mjs`'s header before this script existed). A uniform
magnitude/colour byte pair is used rather than fabricating brightness/colour the data doesn't
contain.

**Object-type byte: 1** ("cluster: soft glow, no PSF core") — a real shader branch in both
GLSL/WGSL twins of `ijStarFragmentShader`, reserved and documented by TR-066's type-byte legend
audit but never used by any shipped asset until now.

**Wiring** (`babylon-engine.ts`): appended `"assets/clusters-bg.png"` to `BONUS_CATALOG_CHUNKS`,
the exact same `_loadBonusStarLayers` mechanism ADR-0007 already established for CNS5/Oort/white
dwarfs — no new rendering code, matching the plan's own C0 exit-criterion intent (the pipeline and
mechanism generalize, they don't need reinventing per dataset). Per TR-067's ideal-state-first
pivot, this layer ships unconditionally on every quality tier (no tier gate), same as the other 3
bonus layers.

## Part 3 — E2E fallout, diagnosed honestly

The full-tier and balanced-tier bonus-layer merge tests hardcode the exact total record count —
this is a REAL, expected consequence of adding a 4th chunk, not a defect. Both updated
543,742 → **555,825** (+12,083 — 12,065 real records + 18 phantom padding records, the same
rectangular-padding behaviour TR-066 already documented for every other PNG-pack chunk), with the
new total's derivation named inline exactly as the original comment's convention required.

**A separate, real, honestly-diagnosed finding**: the first full-suite run this session showed 5
additional failures beyond the count assertions. Investigated each rather than assumed:

- **4 of the 5** (`GAP-03/04/05` console-clean, `B5 quality tiers`, `nebula gas destination-gated`,
  `distance-scaled travel`) reproduced **passing cleanly in isolation** immediately after — the
  same documented cumulative-long-run SwiftShader class this repo has tracked since TR-018/052,
  reconfirmed in TR-064/065/066/067. Not a regression; no code or test change needed.
- **The 5th (`ship track`)** did NOT reproduce passing in isolation — it failed consistently
  across 3 separate re-runs. Before treating this as caused by the cluster layer, checked directly
  via `git stash`: reverted to the clean pre-session baseline, rebuilt, and re-ran the SAME test —
  it failed **identically** (`shipVisible` stuck near 0 after the poll window). **This proves the
  failure predates this session's change and is not caused by it.**

Attempted to resolve the pre-existing failure anyway, since a red test on the branch is a real
problem regardless of who caused it. TR-067 previously diagnosed a similar-looking shortfall in
this exact test as a SwiftShader frame-granularity artifact and confirmed the underlying behaviour
CORRECT on real GPU hardware (`channel:'chrome'`), fixing it at the time by widening the poll
10000ms→25000ms. That margin is no longer sufficient. Tried widening further to 60000ms as a
hypothesis test — it **still failed, with a different and harder failure signature**:
`shipVisible` landed at exactly **0** (not a small nonzero value like the 0.001–0.012 range seen
at 25000ms), which does not read as "just needs more time." An attempt to reproduce this
interactively in the Claude Code Browser pane (`npm run preview` + `javascript_tool`) hit a
**different**, already-documented environment quirk first: `renderFrames` stayed at 0 and
`warp.mode` never advanced past `"aim"` in that Electron-embedded pane — matching PF-09's TR-040
finding ("Claude Desktop's own Electron shell... reports a real WebGPU adapter but its render loop
doesn't advance in this scene, an environment quirk of that embedded browser, not a code defect"),
so that environment could not be used to confirm or deny the real root cause here either.

**Left the poll at TR-067's last CONFIRMED-correct value (25000ms) rather than shipping an
unproven, larger number** — CLAUDE.md's rule against modifying a test without a named, justified
reason cuts both ways: a timeout bump I can't show actually fixes anything is not a justified
change. The test file's inline comment records this investigation in full. A follow-up
investigation task has been flagged (real-GPU Playwright launch needed, not another guess) rather
than left to silently rot.
