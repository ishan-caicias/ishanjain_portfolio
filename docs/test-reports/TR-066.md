## Part 1 — C0: the streaming-decode gap, closed

TR-061's "Honest limits" flagged this explicitly: _"a 3.6M-row file needs a streaming decode, not
the whole-file-in-memory approach that was sufficient to prove Track A at MWSC's 3,006-row
scale."_ Closed two ways:

- **`scripts/lib/gaiasky-binary-particles.mjs`** (+ 7 unit tests) — a reader for a FOURTH local
  data format discovered this session: Gaia Sky's own native `BinaryPointDataProvider`
  serialization (used by all four local SDSS packs). Confirmed against the _official_ format
  spec (`gaia.ari.uni-heidelberg.de/gaiasky/docs/master/Particle-catalogs.html`, fetched this
  session — see Part 3) and byte-verified against the real file, not reverse-engineered blind.
  `forEachGaiaSkyParticle` streams records via a callback receiving primitive values
  (`id, ra, dec, distancePc, index`) — **zero per-record JS object allocation**. Measured against
  the real 130,962,101-byte / 3,637,836-row SDSS DR18 file: **487ms, 0.6 MB heap delta.**
- **`scripts/lib/starfield-pngpack.mjs`'s new `packStreamToBytes`/`writeStreamAsPng`** (+ 2 unit
  tests proving byte-identical output to the existing array-of-objects path) — the PNG-pack
  encoder's own streaming counterpart, for when the OUTPUT side also needs to avoid materializing
  a huge records array (the existing `writeRecordsAsPng` is fine at cluster/CNS5/Oort scale —
  thousands to tens of thousands of records — but wrong past roughly a million).

## Part 2 — C0: the object-type-byte legend, documented for the first time

TR-063's "What Track B does NOT yet do" flagged: _"no type-byte legend for values 1-7 was found
documented anywhere in the codebase."_ `star-catalog.ts`'s header now carries the full legend,
derived by reading the actual shader (`babylon-engine.ts`'s `ijStarFragmentShader`, both GLSL/WGSL
twins) rather than asserted: **0** = ordinary point source (default branch, stellar PSF+bloom);
**1** = cluster (soft glow, no PSF core — unused by any shipped asset today); **2, 4, 5, 6** =
genuinely undocumented/unused (no shader branch distinguishes them — explicitly flagged as
"do not assign without adding and verifying a real branch first," the exact mistake the white-
dwarf type-byte originally made); **3** = galaxy (wider smudge — used by the SDSS pipeline, not
yet rendering-wired); **7** = Oort dust grain (a third distinct branch — used and wired live this
session).

## Part 3 — C2: SDSS DR18's real binary format, cracked and proven end-to-end

`sdss/sdss_dr18.bin` (130,962,101 bytes) is Gaia Sky's own binary particle format — not VOTable,
not FITS, not plain JSON. Blind byte-layout guessing (tried multiple float/double record layouts
against the real file, checked per-byte-position statistics across 5,000 records) did not
converge on a sane structure. **Looked up the real, official spec instead of continuing to
guess** (WebSearch + WebFetch against Gaia Sky's own documentation site) — confirmed a 5-byte
header (`i32` particle count + `u8` extended-particle flag) followed by variable-length records
(`i64` id, `i32` name length + UTF-16BE name chars, `f64` ra/dec/distance-in-pc). Verified against
the real file: header count decoded to **exactly 3,637,836** (the dataset's own stated
`nobjects`), and the first 5 real rows decoded to physically sane RA/Dec/distance values
(RA clustered near 0°, matching SDSS's sky-scan ordering; distances ~2.0-2.3 billion pc, matching
"high-redshift galaxies").

**Real scale finding that changes the C2 placement design** (measured, not assumed): the full
real file's distances span **~32.6 million to ~28.86 billion light-years** — nearly the full
observable-universe scale, a ~1000x dynamic range dwarfing the existing background star field's
real linear-ly placement (max ~2,400 ly). Placing SDSS galaxies at the star field's linear-ly
convention would put nearly every point somewhere between "outside any plausible camera frustum"
and "float32 position with meaningless absolute precision at ~1e10 units." **Resolution applied**:
bake `bodyDepth()` (the exact log-compression formula every curated body already uses, ported
to `scripts/lib/log-depth.mjs` and cross-checked against the real `ship-dynamics.ts` functions
value-for-value by a dedicated unit test) into the packed positions instead — this compresses the
real range down to **~1,112-1,489 world-depth units**, the same order of magnitude as the rest of
the scene. Consequence stated plainly and left unresolved by design: this makes SDSS's positions
log-scaled while the star/white-dwarf/CNS5/Oort layers stay linear-scaled, so SDSS needs its own
separate mesh — deliberately NOT added to `CATALOG_CHUNKS`.

**Photometry**: the real file's "simple" (non-extended) records carry NO per-object magnitude or
colour — confirmed against both the format spec and the Gaia Sky app's own
`particles-sdss-18.json` config (whose `colorMin`/`colorMax`/`particleSizeLimits` are renderer-
side procedural ranges, not per-object data). Every packed record gets a uniform magnitude/colour
byte pair — the same honest treatment as the Oort cloud (TR-065), not fabricated per-galaxy
brightness.

**Full pipeline proven against the REAL file, not a sample**: `scripts/gaia-sdss18-pngpack.mjs`
packed all 3,637,836 real records in 916ms-1085ms across multiple runs, 6.2 MB peak-ish heap (no
per-record object allocation), producing a real 47.1 MB PNG asset (`scripts/out/sdss18-full.png`,
not shipped — see Known limitations). 3 new unit tests (`tests/unit/gaia-sdss18-pngpack.test.ts`)
prove the log-depth placement lands in the right order of magnitude and round-trips correctly
through the real production `decodeStarCatalog`, using 5 real hardcoded rows (CI-safe, matching
the established fixture convention).

**C2 status after this session**: the format-unknown, streaming-feasibility, and distance-scale-
design blockers are all resolved with real, tested code. **Not done**: the actual SDSS mesh/
VertexBuffer wiring into `babylon-engine.ts` (a real, separate rendering-integration step per the
ADR-0007 consequences section), and the C2 GO/NO-GO gate's own required real-device fps/startup
measurement (desktop/iPad/mid-Android) — the latter needs the mesh wired first and real hardware
this session did not have access to.

## Part 4 — C1: white dwarfs, CNS5, Oort cloud — from "proven, unwired" to real live rendering

Implemented per [ADR-0007](../adr/0007-background-bulk-layer-merge.md) (full rationale there).
Real full-scale assets generated for the first time (previously only samples/mechanism proofs):
`public/assets/whitedwarfs-edr3.png` (359,073 records, 5.4 MB), `cns5.png` (5,371 records, 79 KB),
`oortcloud.png` (10,000 records, 136 KB). `babylon-engine.ts`'s `_loadBonusStarLayers` fetches
these after `cosmos:ready`, merges via `decodeStarCatalog`, and rebuilds the star mesh once the
ship is idle.

**Two real bugs found and fixed during verification** (not assumed correct from the design):

1. **A genuine GPU VertexBuffer leak on every geometry rebuild.**
   `mesh.setVerticesBuffer(new VertexBuffer(...))` replaces the JS-side reference but never
   disposed the outgoing GPU buffer. Found by investigating a real E2E timing regression (a
   reduced-motion warp test's 350ms-configured travel started taking 4-6+ real seconds), isolated
   by temporarily disabling the whole bonus-layer feature and re-testing (confirmed the feature
   was the cause), then narrowed further. Fixed: `getVertexBuffer("starMeta")?.dispose()` before
   the replacement.
2. **The white-dwarf tier gate was too permissive.** Originally skipped only on `lite`; real
   measurement found merging white dwarfs roughly TRIPLES total billboard vertex count (675,836
   → 2,174,968) and severely degrades frame time on `balanced` tier under SwiftShader/WebGL2 (a
   reasonable stand-in for a real mid-tier/no-WebGPU device) — turning that same 350ms warp into
   6+ real seconds. Tightened to `full`-tier-only; CNS5+Oort (small, 15,564 combined records)
   stay on every tier.

Even after both fixes, a real, understood (if not microscopically root-caused) residual cost
remains: merging even the small CNS5+Oort layer (+62k vertices, ~9%) measurably slows real warp
completion under SwiftShader — read as evidence of per-frame-dt-clamped warp-progress
integration compounding a real frame-time increase into disproportionate wall-clock delay. One
existing E2E test's real-clock poll window was widened (2000ms → 8000ms) with this investigation
recorded inline as the named justification (CLAUDE.md non-negotiable #15) — not loosened
arbitrarily.

**E2E proof** (`tests/e2e/engine-select.spec.ts`, two new tests): `?tier=full` merges all 3 layers
to the exact real total **543,742** (derived from each chunk's real pixel-rectangle byte count,
not the naively-summed row counts — the shared PNG format's rectangular padding decodes as extra
all-zero "phantom" records past each dataset's own written count, a real, pre-existing behaviour
of `writeRecordsAsPng`/`decodeStarCatalog` present in the shipped `stars-hip.png`/`deep.png` too,
not a defect introduced this session); `?tier=balanced` merges to **184,523** (white dwarfs
excluded). Two existing tests that asserted an exact base-catalog `starCount` were updated to a
floor/racy-aware check, named and justified (a real, permanent consequence of background layers
now being able to complete before those assertions run).

## Part 5 — C1: NGC2000 nebulae — precisely re-scoped, 41/47 resolved

TR-065 recorded a blanket "blocked" verdict for all 47 NGC2000 nebulae (the reveal-uniform
4-volume cap). Real investigation this session found the 47-object catalog is not uniform: the
real local data (`particles-nebulae.json` + `glsl-nebulae.json`, lenient-JSON-parsed — Gaia Sky's
own JSON ships trailing commas) splits into **41 real "Billboard"-archetype objects** (simple
textured quads, no per-object shader) and **8 "Volume"-archetype objects**, each with its OWN
bespoke, hand-authored GLSL shader file (`helix-nebula.glsl`, `crab-nebula.glsl`, ...). Only the
8 Volume objects hit the real reveal-cap blocker; porting 8 fully custom external shaders (GLSL→
WGSL twins each, TR-045 reserved-identifier checks each) is real, separate, larger design work,
still not attempted. Notably, none of the 4 existing hardcoded showcase volumes in
`nebula-field.ts` (Orion/M42, Veil, Rosette) are themselves real "Volume" objects in this local
catalog — only Helix is; those 4 were always a hand-picked simplified showcase.

**The 41 Billboard objects needed none of the blocked mechanism** — `t: "nebula"` was already a
fully-handled type in `celestial-bodies.ts`'s billboard pipeline, the exact zero-new-rendering-
code pattern clusters/GD-1/NBG/minor-planets already used. `scripts/gaia-ngc2000-billboards.mjs`
converts all 41 real objects (real ra/dec/distance from `particles-nebulae.json`) to
`src/data/celestial/celestial-ngc2000.js`, wired into `SpaceScene.tsx`'s load chain. E2E proof:
real count assertion (41) + a real travel proof on the Lagoon Nebula (M8), real ra/dec/ly values
asserted against the source data.

**Remaining blocker, precisely scoped now (not vague)**: the 8 Volume objects (Helix, Cat's Eye,
Box/NGC6309, Butterfly/M2-9, Hourglass, Crab/M1, Ring/M57, Trifid/M20) still need the
`nebula-field.ts` reveal-mechanism redesign ADR-0007-adjacent work described in TR-065, PLUS a
real per-object GLSL→WGSL port for each — not attempted this session.

## Known limitations

- **C2 is substantially unblocked, not complete.** The format, streaming, and distance-scale
  design blockers are resolved with real tested code, but SDSS DR18 has NO rendering wiring yet
  (needs its own separate mesh per ADR-0007's consequences), and the C2 GO/NO-GO gate's required
  real-device (desktop/iPad/mid-Android) fps/startup measurement has not been run — this session
  had no real Android/iPad hardware access. The 47.1 MB candidate asset
  (`scripts/out/sdss18-full.png`) is a build artefact, not shipped under `public/assets/`.
- **NGC2000's remaining 8 Volume-archetype nebulae are still blocked** — precisely scoped now
  (each needs its own bespoke GLSL→WGSL port plus the reveal-mechanism redesign), not attempted.
- **The residual per-frame cost from a larger background star mesh is real and only partially
  mitigated** (tier-gating white dwarfs, disposing the leaked buffer) — even the small CNS5+Oort
  addition measurably slows warp completion under software rendering. No further investigation
  into WHY per-frame-dt-clamped warp integration compounds this so disproportionately was done;
  flagged as a real open question, not silently assumed benign.
- **GD-1's connected-trail visual remains unattempted** (carried over from TR-065, unchanged).
- **Bundle headroom (49.4 KB) remains tight** for any further Track A (curated-JSON) addition —
  Track B (PNG-pack) additions do not consume this budget, per the finding above, and should be
  preferred for anything bulk going forward.
