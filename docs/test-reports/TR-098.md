## What this pass is

D4.1 of the four audited D4 defects (delivery plan's "Audited baseline" note): the arrival vista
had **no real dismiss input at all**. The only thing that ever closed it was a 5.5s auto-timeout
(D1.4's stopgap, explicitly named as temporary in its own code comment); a click meant to dismiss
it could fall straight through to the canvas and start an unrelated new warp, because the vista's
root was `pointer-events-none` and even its own button row sat **below** `#ij-mission-bar` in
z-index (60/61 vs. 62 — TR-086 found this, flagged it, and handed it here rather than fixing it
out of scope). D4.2 (field-object travel parity), D4.3 (card polish/focus trap), and D4.4
(content pass) are untouched — out of this slice's scope by the owner's own D4 breakdown.

## What shipped

**`ArrivalVista.tsx`** is now a real `role="dialog"`: `pointer-events-auto`, `aria-label`, focused
on mount and restored on unmount (`moveFocusTo`/`restoreFocusTo`, D1.2's existing focus-utils),
`z-[65]` — above `#ij-mission-bar`'s 62, so the whole subtree now paints above the mission bar
regardless of its own internal 61 (stacking contexts nest; only the ROOT's z mattered for the
TR-086 bug). Click anywhere except the "OPEN COLLECTOR CARD" button dismisses (the button
`stopPropagation`s so opening the card doesn't also double-fire dismiss); Space at the dialog
level dismisses, but Space on the focused button keeps its native activate-the-button behaviour
(`e.target === e.currentTarget` gate). The dead-on-touch "HOVER THE BODY FOR VITALS" line is
replaced with a pointer-media-queried pair: `CLICK ANYWHERE OR PRESS SPACE TO RESUME FLIGHT`
(fine pointer, the default) / `TAP ANYWHERE TO RESUME FLIGHT` (coarse pointer).

**`SpaceScene.tsx`:** the 5.5s `vistaTimeoutRef` auto-dismiss is gone entirely — no code path
schedules one anymore. A new `dismissVista(via)` is the ONE path that closes the vista (click,
Space, and Escape all funnel through it), recording the funnel event, clearing `state.vista` only
(`arrivedId`/camera untouched — the ship stays parked exactly where it landed), and setting a
sr-only `role="status"` announcement (`Resumed flight at {name}.`) that lives outside the vista
so it's still there for assistive tech to read after the vista unmounts. A 300ms **click-swallow
window** (`VISTA_CLICK_SWALLOW_MS`) guards the D4-AC2 double-click case: a capture-phase
`pointerdown` listener on `document`, scoped to targets inside the engine element, calls
`stopPropagation()` for 300ms after any dismissal — swallowing `pointerdown` rather than `click`
or `pointerup` means the engine's own `_dragStart` (set on `pointerdown`, read on `pointerup` to
decide whether a click-to-travel happened) is never armed, while the engine's `pointerup` handler
still runs normally and resets `_dragging` — a rapid second click can never launch a warp, but a
legitimate drag-release right after dismissal isn't left in a stuck state either. Implemented in
SpaceScene, not either engine (implementation plan's explicit split), so it applies uniformly to
both `space-engine.js` and `babylon-scene` without touching either.

**New `useEscapeStack` (`focus-utils.ts`):** a generic priority dispatcher — exactly one `active`
layer's `onEscape` fires per press, first-match in caller-supplied order — replacing the old
blanket `if (Escape) patch({cardId:null, mcOpen:false, sectionOpen:null})` that closed everything
at once regardless of what was actually open. SpaceScene calls it once with four layers in the
delivery plan's specified order: card → vista → suggestions (`!!state.cmd`) → sectionOpen. `card`
and `vista` never actually coexist in this codebase's state machine today (every path that opens
one nulls the other), so that ordering is currently defensive rather than load-bearing; `vista`
and `suggestions` genuinely CAN coexist right now, because D4.3's focus trap for the card hasn't
landed yet and nothing yet prevents Tab from reaching the search input while a vista is still
shown — the four-layer stack is real protection against that specific interim state, not
speculative scope. `mcOpen` (dead state — nothing in the codebase currently sets it `true`) rides
along wherever it's already inert rather than being investigated/removed, which is out of scope
here.

## Deviation from the implementation plan, recorded rather than silent

The implementation plan's D4.1 bullet says Escape is handled "at the dialog level" alongside
Space. It isn't — `ArrivalVista` handles click and Space locally (both need component-local
nuance: click needs the "not on the button" check, Space needs the "not when the button is
focused" check) but Escape is handled EXCLUSIVELY by `useEscapeStack` at the `SpaceScene` level.
Reason: focus lands inside the dialog on mount, so a native `window`-level Escape listener and a
React `onKeyDown` on the dialog root would BOTH fire for the same keypress if the dialog also
handled Escape itself — harmless in final state (both paths converge on the same `patch`) but a
duplicate funnel record and a needless second dispatch. Single-owner-per-key beats matching the
plan's literal phrasing here.

## Legacy engine / reduced motion

No `space-engine.js` changes — this slice is SpaceScene's shared React chrome plus a
document-level listener, not engine code; the archived engine keeps working through the same
`cosmos:*` contract unmodified (CLAUDE.md #3/#17). `prefers-reduced-motion` is unaffected: the
vista's own CSS animations (`ij-fadein`/`ij-land`) are pre-existing and untouched by this slice.

## Named test change (CLAUDE.md #15)

`tests/e2e/funnel.spec.ts` — the existing "RNG travel ... records vista-dismissed" test's own
comments documented the exact two things this slice fixes (the 5.5s timeout race it worked around
by clicking the instant the button appeared, and the z-index overlap it worked around with
`.evaluate((el) => el.click())` instead of a real Playwright click). Both workarounds are now
unnecessary and were removed; the test asserts the same outcome via a real `.click()`, which now
lands correctly because the z-index bug is fixed.

### Gate-run incident, root-caused rather than accepted (CLAUDE.md #14/#27)

The first full-suite run showed 2 failures, both in the new `vista-dismissal.spec.ts`, both the
same root cause: the new tests never called `test.setTimeout(...)`, so Playwright's default 30s
per-test ceiling could land mid-poll on a real Sirius journey in this environment (other specs in
this suite already budget 45–180s per test for the same reason — SwiftShader rendering here is
measurably slower and more variable than typical CI, documented repeatedly in TR-032/033/081/094/
096/097). Compounding factor, later confirmed: a Browser-pane manual-regression attempt was
running concurrently with that same background E2E run (see Known limitations), the same
CPU-contention class TR-096 already diagnosed. Fixed by adding `test.setTimeout(90000)` to all
seven tests (matching this suite's existing convention, e.g. `funnel.spec.ts`'s 45000/60000,
`mid-warp-input.spec.ts`'s 150000/180000) — **not** a timing/assertion loosened, a missing budget
added. Isolation, per CLAUDE.md #27 (never re-run the full suite to characterize one failing
spec): `vista-dismissal.spec.ts` alone, 3 separate passes (7/7, 7/7, then 14/14 on
`--repeat-each=2`) — 21/21 clean after the fix, with no concurrent process this time.

The subsequent full-suite re-run (the actual gate, reported above) then hit ONE unrelated failure
— `ascent.spec.ts`'s `LAUNCH plays the ascent...` test, a 6000ms poll on `ascentMode` timing out.
This slice's diff touches none of the ascent/launch cinematic path (`beginAscent`, `AscentSkip`,
`PreFlight`, `ascentMode`) at all. Isolated per the same discipline: `ascent.spec.ts` alone, 3
passes (5/5, then 10/10 on `--repeat-each=2`) — 15/15 clean. Same intermittent-timing-under-load
class as the repo's own documented GAP-17 flake, confirmed unrelated to this slice by both the
diff scope and the clean isolation reruns, not asserted from the diff scope alone.
