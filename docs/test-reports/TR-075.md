## Part 1 — The belt now orbits, and it costs zero bytes per vertex

**The constraint that made this a limitation in the first place.** The shared `ijStar` vertex
shader carries only `position: vec3` and `starMeta: vec2`, and four other layers use it (stars,
SDSS galaxies, Oort cloud, white dwarfs). Storing a per-asteroid angular rate would cost ~2.5 MB
of GPU memory for this layer alone — against exactly the billboard-memory budget ADR-0003 still
lists as the open Babylon adoption condition. That is why TR-074 declined to "smuggle" it in.

**The resolution: derive the rate instead of storing it.** Kepler's third law fixes mean motion
from orbital radius alone, n = sqrt(GM/a³). The shader already knows each speck's distance from
the Sun — it is the position it is drawing — so:

```
rOrb = length(vec3(position.xy, position.z - ORBIT_SUN_Z))   // true heliocentric distance
ang  = ORBIT_OMEGA_K * inversesqrt(rOrb³) * uTime            // Kepler's third law
```

then a prograde rotation about world Z, the declared ecliptic pole. **Zero new attributes, zero
new buffers, one uniform.** This is not a stand-in for the physics; it _is_ Kepler's third law,
the same law the offline pipeline's full state solution obeys.

**The constant is derived, not tuned.** Substituting GM with the radius in world units gives
`KEPLER_K = TIME_ACCEL × sqrt(GM_sun / (KM_PER_AU/AU_TO_WORLD)³)` = **39.823416**, and it is
identical at every radius (checked at r = 100, 170, 250, 328), exactly as Kepler's third law
requires — a tuned fudge factor would not have that property, which is what makes it worth
asserting in a test.

A first draft hard-coded **39.807**, back-solved from the science brief's _rounded_ 3.053
world-units/s figure. Astra measured that as 0.041% off and recommended computing it from the
constants instead, because three separate places already encode the AU→world scale and the time
acceleration and a magic number would silently desynchronise from all of them. Taken.

**Astra's refinement, also taken: measure from the Sun, not the world origin.** The first draft
fed the rate law the _planar_ radius `length(position.xy)`. The Sun sits at the belt plane's
centre, (0, 0, −13). Using the planar projection overstates the rate by a median of only 0.47% —
but **11,074 real objects exceed 5% error, 471 exceed 20%, and the worst is +189%**: the 94 real
asteroids inclined past 40°, which spend most of their orbit far above or below the plane. One
extra term in the shader fixes every one of them.

### What this buys, in real astronomy

**Keplerian differential rotation** — the belt is visibly _not a solid disc_. Astra's measured
numbers over 60 seconds of wall clock:

| Location                 | r (world units) | rotation in 60 s | lag behind inner edge |
| ------------------------ | --------------: | ---------------: | --------------------: |
| inner edge, 2.06 AU      |           129.8 |            92.6° |                  0.0° |
| spine, 2.70 AU           |           170.1 |            61.7° |                 30.9° |
| 2:1 outer edge, 3.28 AU  |           206.6 |            46.1° |                 46.5° |
| Jupiter Trojans, 5.20 AU |           327.6 |            23.1° |                 69.5° |

The inner edge gains **46.5° of longitude on the outer edge every minute** — a quarter-turn of
relative twist inside the main annulus, and it is the correct amount. Full relative wrap takes
7.7 minutes. This is the same physics as Saturn's rings and accretion discs, and it is the
mechanism that _makes_ belts axisymmetric.

**The Kirkwood gaps survive, exactly.** Rotation about Z maps every vertex to a new azimuth at
_identical_ r, so the set of radii present in the scene is unchanged frame to frame, forever. The
gaps, belt edges, Hilda island and the 4.05–5.00 AU void are time-invariant to machine precision.
Astra notes this is in fact a _stronger_ guarantee than reality, where the true ensemble radial
histogram drifts up to 10.1% per bin over the same 60 s.

**No tearing between the two layers.** The animated visual layer stays within **1.74° of the real
Havok rocks over 60 s** (median 0.49°) — an accident of the physics subset's own e < 0.10 / i < 5°
selection cut landing exactly where the r^−3/2 approximation is most accurate.

### Declared, not hidden

- **SIMPLIFIED — rate from instantaneous r rather than semi-major axis a.** For an eccentric orbit
  these differ. Astra derived the closed form: ω_shader/ω_true = 1/√(1 + e·cos ν), which at the
  catalog's median e = 0.1334 is **−6.1% at perihelion to +7.4% at aphelion** — centred on zero,
  not biased. Measured median error **4.89° per 60 s** against a median **61.5° actually swept**,
  about 8% of the object's own travel.
- **SIMPLIFIED — rigid rotation discards real radial breathing and vertical bob** (median 13.4 and
  13.1 world units per 60 s). Both are _incoherent_ across 154,662 independent orbital phases, so
  the ensemble appearance is unchanged.
- **DECLARED LICENSE — Jupiter Trojan clumps smear.** The L4/L5 clumps are genuine azimuthal
  structure and this model does wind them, at 2.2°/minute. Invisible over a 60 s look, real over
  half an hour. Confining them properly needs libration about the equilibria, which is not
  expressible as a rate law.
- **ACCURATE — prograde is right for the whole catalog.** Astra confirms **0 retrograde objects in
  154,662** (max inclination 72.156°), 0 in both auxiliary packs, and all **64/64 shipped Havok
  bodies have L_z > 0**, checked against the shipped file.

### Reduced motion

`uTime` shares `bodyT`, the existing reduced-motion-gated clock, so it pins to exactly 0 — which
the shader reads as "do not rotate." The belt then holds still **at its real snapshot positions**:
the contract is "no motion," not "no belt," and reduced motion returns precisely the
already-validated TR-074 static scene. Asserted as behaviour by a new E2E test, not only as
shader source text, because the rotated positions live on the GPU where JS cannot see them.

## Part 2 — The Trojan/NEA packs: the limitation was wrong

TR-074 recorded this as "not merged; merging needs a dedup pass." **There is nothing to merge.**

Astra checked, and this session then verified independently by streaming all three real files and
comparing names and orbital elements directly:

| Pack   | Elements | With orbit | Found in main catalog | Not in main | Elements bit-identical |
| ------ | -------: | ---------: | --------------------: | ----------: | ---------------------: |
| trojan |    1,545 |      1,544 |      **1,544 (100%)** |       **0** |              **1,544** |
| NEA    |      393 |        392 |        **392 (100%)** |       **0** |                **392** |

Both packs are **exact pre-filtered subsets** of the 154,662-object main catalog — the same
records, re-serialised, agreeing to floating-point identity. The main catalog has 154,662 unique
names and no duplicates. A naive merge would add **zero new objects and create 1,936 exact
duplicates**.

The extra element in each file is an `OrbitalElementsGroup` container node, not an asteroid, which
is where 1,545→1,544 and 393→392 come from.

**A correction to the parent brief, which Astra volunteered against its own earlier work:** its
count of "108 NEOs in the main catalog" used the cut a < 1.3 AU. The NEA pack actually spans
a = 0.662–2.853 AU, because the real NEA definition is on _perihelion_ q = a(1−e) < 1.3, not on a.
That was the criterion being wrong, not the packs holding extra objects.

**So this closes by disproof, and the shipped belt was already complete.** The one thing the
auxiliary packs genuinely offer that the main catalog cannot is a curated _classification label_
(~25 KB as a name list) if Trojans and NEAs should ever be tagged or coloured distinctly. Recorded
as a possible future enhancement — it is a new feature, not the merge this item asked for.

## Part 3 — The docs-drift checker had the defect, not the docs

The owner tested the flagged link and confirmed it resolves, along with the image it links on to.
Investigated properly rather than deleting the warning.

The checker's link pattern was:

```
/\[[^\]]*\]\(([^)#\s]+)(?:#[^)\s]*)?\)/g
```

which cannot see CommonMark's **angle-bracket destination form**, `[text](<url>)`. That form is
not exotic — it is the _required_ syntax when a URL contains parentheses, and Prettier emits it
automatically. So this correct link:

```
[Wikimedia Commons](<https://commons.wikimedia.org/wiki/Category:Pleiades_(star_cluster)>)
```

captured as `<https://…Category:Pleiades_(star_cluster`, truncated at the inner `)`. That string
then failed the `^https?:` external-URL test — it starts with `<` — so the checker fell through to
resolving it as a **relative file path** and reported a broken link. Two bugs, one cause.

Fixed by extracting the parsing into `scripts/lib/markdown-links.mjs` (the checker runs its checks
at module top level and so cannot be imported by a test) with both destination forms supported.

**The important half of the fix is the tests that keep the check armed.** Loosening a checker until
a false positive disappears is the easy failure mode and silently disarms it, so
`tests/unit/markdown-links.test.ts` pins that real broken links are _still_ caught — in both
destination forms, including relative links inside angle brackets, which the lazy fix
(skip anything bracketed) would have stopped checking entirely.

A false positive in a drift checker is a defect in the drift checker: it guards a documentation
contract this repo treats as load-bearing, and a checker that cries wolf trains its readers to
ignore it.

## Part 4 — A measured performance cost, found by refusing to call it a flake

The first full E2E run after the animation landed came back **80/85** — the same 5 failures TR-074
had, all in the established fragile warp-timing set, with all three new C3 specs passing. The easy
read was "same count as before, known flake class, move on."

**Re-running those 5 in isolation broke that story.** TR-074's flake signature is that failures
_pass_ on re-run and the failing set rotates. Here **4 of the 5 reproduced** in a small batch. That
is not the flake class; that is a signal.

**A/B, disabling only the belt's orbital clock** (`uTime` pinned to 0, everything else identical):

| Configuration             | Same 5 tests |
| ------------------------- | -----------: |
| belt orbiting             |     1 passed |
| belt frozen (`uTime = 0`) |     3 passed |

So the animation was really costing frame time on SwiftShader — enough to push frame-rate-sensitive
warp-timing assertions over their limits. Worth knowing, and it would have been invisible behind
"same failure count as last time."

**The cause was not the asteroids.** It was every _other_ vertex paying for their branch. The
first draft wrote the gate as `floor(starMeta.y) > 5.5 && floor(starMeta.y) < 6.5`, and the shader
already computed `float ty = floor(starMeta.y)` further down — three `floor()` calls per vertex,
on a material shared with the SDSS layer's **14.5M vertices**. Hoisting `ty` to a single
computation reused by the orbital block and the existing size/colour branches recovered a test
immediately:

| Configuration                          | Same 5 tests |
| -------------------------------------- | -----------: |
| belt orbiting, `floor()` ×3 per vertex |     1 passed |
| belt orbiting, `ty` hoisted (shipped)  |     2 passed |
| belt frozen (floor for comparison)     |     3 passed |

A unit test now pins `ty` to exactly one computation per vertex in each twin, and pins that it is
hoisted above the block consuming it — a performance property, asserted because it was measured to
matter, not because it reads tidier.

**The residual — one test's worth — ships, deliberately, and here is the reasoning.** This is a
software rasterizer that renders this scene at ~3 fps against ~50 fps on real GPU hardware
(TR-067's measurement, a ~17× gap). A per-vertex sin/cos is close to free on a real GPU and
expensive on a CPU rasterizer, so SwiftShader is precisely the instrument that _over_-weights this
change. Tier-gating a feature from a SwiftShader measurement is the exact move PF-10 already made
once and then reversed on owner direction (TR-066's white-dwarf gate, undone in TR-067), and doing
it again from the same kind of evidence would repeat that mistake.

**But this is now a measured, named cost rather than a hypothetical**, and it makes the pending
real-device pass more urgent, not less. If real hardware shows a real regression, `uTime` is one
line from a tier gate — the mechanism is already in place and the belt degrades to exactly the
TR-074 static scene, which is already validated.

**Where the optimisation stopped, and why.** The obvious next step — giving the asteroid layer its
own `ShaderMaterial` so the other layers never evaluate the gate at all — was considered and
rejected. After the hoist, that gate costs three float comparisons; the real remaining work is the
`length`/`inverseSqrt`/`sin`/`cos` on the belt's own 619k vertices, which a separate material
cannot avoid because those vertices genuinely have to do it. The SDSS layer deliberately shares
`_starMat` precisely so uniform pushes cannot diverge between two copies, and splitting it to save
three compares would trade a measured-marginal gain for a real class of bug. Stopping here is a
proportionality call, recorded rather than left implicit.

## Part 5 — Real-GPU shader validation

New WGSL in a shader four layers depend on is exactly the TR-045 class of risk (WebGPU validates
shader modules _asynchronously_; a bad module surfaces only as console output, and
`materialReady: true` proves nothing). The real-hardware spec — `channel: "chrome"`, real GPU,
asserting **zero console output** — passes **3/3** against a fresh build.

One process note worth recording: the first attempt at this ran against a **stale `dist`**. `npm
run build` is `lint && check && astro build`, and a Prettier failure short-circuited it, so
Playwright served the previous build while reporting 3 passed. Caught by reading the command's
full output rather than its last line. This is the failure mode CLAUDE.md's "E2E always needs a
fresh build" warning describes, arriving by a slightly different route than expected.

**New coverage (+27 unit).** The orbital-motion tests check the arithmetic against _outside_
references rather than against itself: the constant against a first-principles re-derivation from
GM (deliberately recomputed in the test rather than imported), the rate against the **real
Keplerian velocities of the 64 shipped physics bodies** (0.77% mean, 2.28% worst — the moving dust
and the moving rocks must agree or the belt reads as two populations sliding past each other), and
the differential shear against the exact 2^1.5 ratio. Plus both shader twins asserted to carry the
orbital block, the same interpolated constants, and the type-6 gate — that last one guarding the
failure where an ungated rotation sets the entire sky spinning.

**Bundle impact +1.1 KB gz**, all of it the new shader source and the derivation.

**E2E, stated with the ambiguity intact.** Final run **79/85**, 6 failed; all three new C3 specs
passed (belt renders and drives the physics tier · orbital clock advances · clock freezes under
reduced motion). Across four full runs this session and last, the headline has sat at 5–6 failures
out of 83–85 with the failing SET rotating every time — this run newly failed `craft=1k` and
`warp travel P2`, which passed before, while `free-look drag` passed, which failed before. That
rotation is TR-052's documented cumulative-load signature and it is still the dominant effect on
the headline number.

**Both of these are true at once, and the report says so rather than picking the flattering one:**
the isolated A/B in Part 4 proves this change carries a real frame-time cost on SwiftShader, and
the full-suite number is too noisy to measure that cost with. The honest position is that the
verdict rests on the fragile set being pre-existing and documented (TR-018/052/064/065/066/067/
070/071/072/073 lineage), on every new assertion passing, and on the real-device pass being the
actual arbiter — not on the E2E count having improved, because it did not.

## Part 7 — What is still open

Unchanged from TR-074 and not addressed here, because neither belongs to these three items:

- **The real-device frame-budget gate.** C3 is code-complete, not budget-cleared. CI's SwiftShader
  renders this scene ~17× slower than real GPU hardware (TR-067), and this session _added_
  per-vertex work to 154,662 billboards — a trigonometric rotation in the vertex stage, gated on
  type but branch-evaluated for every vertex the shader touches. That makes the real-device pass
  more necessary than it was, not less. It should still run in one session with C2's.
- **The belt's 23.44° frame offset**, still an open owner decision recorded in the delivery plan.

**Owner-eyes still outstanding**, and now more interesting than it was: the automated suite proves
the clock advances, freezes under reduced motion, and that the shader compiles clean on real
hardware. It cannot show whether a sixth of a revolution per minute reads as _alive_ or as _too
fast_. That is a taste judgement on a number (`TIME_ACCEL`) that is trivially adjustable — the
shear is physically correct at any value of it, so this is a dial, not a defect, if it looks wrong.
