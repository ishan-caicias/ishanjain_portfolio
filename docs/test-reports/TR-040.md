# TR-040 — PF-09 B2 step 3: flight model port (damped spring + quaternion slerp)

**Date:** 2026-07-19
**Scope:** PF-09 B2 step 3 of 6 — wire `ship-dynamics.ts`'s pure spring/quaternion math to a
Babylon camera for real `travelTo`/`goHome`/`randomBody` navigation, and fix a blocking prerequisite
gap that made the prior two steps unreachable from the real UI.
**Verdict: OVERALL: READY TO PROCEED** — 113/113 unit · 55/55 E2E · build/lint exit 0, including a
new end-to-end test that drives travel through the real button, not the engine's internals.

## Prerequisite bug found during INSPECT: nothing was reachable

Before writing any travel code, tracing how the UI drives the engine surfaced a blocker:
[SpaceScene.tsx](../../src/components/islands/SpaceScene.tsx)'s `engineEl()` queried
`document.querySelector("space-engine")` **unconditionally** — never `babylon-scene`. On the
Babylon path this always returned `null`, so every host-driven call (`travelTo`, `goHome`,
`randomBody`, HUD sync, station sprites) silently no-op'd. The comment at the render call site said
as much: _"no ref — the host drives via querySelector('space-engine') (null here), so its engine
calls no-op while this preview self-runs."_

This meant B2 steps 1–2 (vertex expansion, real catalog) were correct in isolation but **entirely
unreachable from the actual site** — only `<babylon-scene>`'s own self-running preview ever
exercised them. Wiring `ship-dynamics.ts` to a camera would have produced the same outcome: correct
code nothing could drive. Fixed with the smallest surgical change — `engineEl()` now queries
`"space-engine, babylon-scene"`; exactly one is ever mounted at a time (the ternary in
SpaceScene.tsx picks by `engineKind`), so the combined selector is safe and the default (webgl)
path is byte-identical in behaviour.

## What shipped

**New pure math**, [ship-dynamics.ts](../../src/lib/ship-dynamics.ts) (unit-tested, pinned against
space-engine.js's private formulas since they aren't importable — it's a plain script, not a
module):

- `raDecToDir(ra, dec)` — sky-to-xyz, matching the live engine exactly so a body computed here sits
  in the same coordinate space as the star catalog (both engines decode the identical PNG assets).
- `bodyDepth(ly)` — the log-compressed world-space depth, matching `_buildBodies` exactly.
- `bodyWorldPosition(ra, dec, ly)` — the composed placement.
- `ARRIVE_STANDOFF = 38` — matches the live engine's parked distance.

**Travel wiring**, [babylon-engine.ts](../../src/lib/babylon-engine.ts):

- `this.bodies` populated from `window.CELESTIAL` (2,525 named entries on this build — every
  catalog layer, not just the 101 curated ones) at boot; `setStations()` mirrors the live engine's
  fixed 420-unit station depth (a real, deliberate difference from catalog bodies' log depth — not
  an oversight, called out explicitly in code).
- `travelTo`/`goHome`/`randomBody` implement the same `idle → aim → warp → idle` state machine
  shape as the live engine and emit the identical `cosmos:select` / `cosmos:warp` / `cosmos:arrive`
  / `cosmos:home` event contract (including `quiet` mode for scroll-driven silent travel), so the
  entire React UI layer (HUD, WarpOverlay, ArrivalVista) needs zero engine-specific branching.
- Camera **position**: three independent `springStep`s (one per axis) toward the target, reusing
  `SHIP_SPRING_OMEGA`/`SHIP_SPRING_ZETA` as-is. Worth recording why that's sound and not just
  convenient: a linear damped spring's **settle time is independent of distance** — the same
  constants tuned for the live engine's on-screen ship-sprite (~1.5 s settle) work unchanged at
  world-space scale. This also means travel currently takes roughly the same wall-clock time
  regardless of target distance — which is _exactly_ what step 5 ("distance-scaled travel —
  velocity profile keyed off `ly`") is staged to add. Not a gap here; a deliberate sequencing.
- Camera **orientation**: `camera.rotationQuaternion` set to `new Quaternion()` once (switching
  Babylon out of Euler mode), then quaternion-slerped each frame via `quatDamp` toward
  `quatFromUnitVectors(BABYLON_FORWARD, travelDirection)`.

## The handedness gotcha, verified rather than assumed

`ship-dynamics.ts`'s header states its conventions match the live engine: _"view space is
right-handed with the camera at the origin looking down −Z."_ Babylon's default is
**left-handed**, forward **+Z**. Given this session's pattern of catching exactly this class of bug
late (`gl_PointSize`, `ImageBitmap.close()` ordering), this was checked against
`@babylonjs/core`'s actual source rather than assumed:

```
node_modules/@babylonjs/core/Cameras/targetCamera.js:
  this._referencePoint = Vector3.Forward(this.getScene().useRightHandedSystem);
node_modules/@babylonjs/core/Maths/math.vector.js:
  static Forward(rightHandedSystem = false) { return new Vector3(0, 0, rightHandedSystem ? -1 : 1); }
```

Confirmed: `(0, 0, 1)` at an identity `rotationQuaternion` on this scene's default left-handed
setting — `BABYLON_FORWARD` in the code, with the derivation and the "don't reuse the live engine's
−Z" warning left as a comment at its definition. `quatFromUnitVectors`/`quatSlerp`/`quatDamp`
themselves are plain vector-to-vector rotation math with no baked-in handedness assumption, so
reusing them is safe as long as this constant — not the live engine's — is the reference forward.
Verified empirically too: the E2E test below checks the camera actually lands within 2 world units
of the real target position after a real click-driven travel, which would fail on a sign error.

## A debugging detour worth recording: Claude Desktop's Electron shell is a THIRD Chromium

Manual verification in this session's interactive Browser Pane showed `renderFrames` stuck at 0
after wiring travel — looked like a real regression. Investigation (temporarily wrapping the
render-loop callback in try/catch, rebuilding, re-testing) found **no exception ever thrown**, and
a fresh Playwright run against the identical build showed travel working perfectly end-to-end
(`renderFrames` climbing from 255 to 654, camera converging on Sirius within 0.4 world units of the
computed target). The Browser Pane's `navigator.userAgent` revealed why:
`Claude/1.22209.0 ... Electron/42.5.1` — **a third, distinct Chromium build**, neither Playwright's
bundled binary nor a real system Chrome (the two TR-039 characterized). It reports a real WebGPU
adapter (`hasGpu: true, adapter: true`) yet its render loop doesn't advance in this scene — an
environment-specific quirk of that embedded browser, not a code defect. Recorded so a future
session doesn't re-diagnose the same false alarm from scratch.

## Deliberately deferred to B2 step 4 ("the PF-08 choreography")

- **Chase-camera waypoint choreography.** `ship-dynamics.ts` already has the full behind-the-
  thruster waypoint table (`chaseOffsetAt`, `travelFrame`, `CHASE_LOOK_LAMBDA`) — unused here by
  design. This step drives the camera directly at the spring/quat target; step 4 layers the actual
  chase framing on top.
- **Launch-at-click ship turn, arrival framing.** No ship mesh exists in the Babylon path yet
  (craft loading is a separate track); step 3's "ship" is the camera itself.
- **Screen-space station projection** (`sx`/`sy`/`ex`/`ey`). Station sprites stay hidden — verified
  safe rather than assumed: `SpaceScene.tsx` reads `b.vis ? b.sx : b.ex`, and
  `undefined != null` is `false`, so the DOM markers simply don't render instead of crashing or
  showing at `(0,0)`.
- **Distance-scaled pacing** — step 5, as covered above.
- **Free-look drag/orbit controls** — not mentioned in the delivery plan's step 3 wording; the
  Babylon camera doesn't yet respond to pointer drag.
- **Field-star hover/picking** (`fieldInfo()` stays a stub) — that's the live engine's screen-space
  projection pipeline, not reachable from named travel.

## Honest limits

- Travel currently has no distance-scaled pacing (by design — step 5) and no chase-camera framing
  (by design — step 4), so a click-driven journey right now is a direct camera glide, not yet the
  cinematic behind-the-thruster experience the live engine delivers. This is an intentional
  intermediate state, not a regression — the live WebGL engine remains the shipping default
  throughout.
- Station sprites and field-star hover are inert on the Babylon path until step 4's screen
  projection lands; verified safe (no crash), not yet functional.
- The Electron-Chromium WebGPU quirk noted above is unexplained beyond "different browser build" —
  not investigated further since it's not part of the shipped test/CI matrix.
