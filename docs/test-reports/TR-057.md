## What shipped

Three new pure modules (`milky-way.ts`, `constellations.ts`, `star-trails.ts`),
wired into `babylon-engine.ts`. `space-engine.js` untouched (`git diff` empty).

**GAP-03 — Milky Way band.** Ported `_buildMilkyWay`'s CPU procedural
equirect texture (disc+bulge glow, patchy fBm star clouds, three named bright
clouds, the Great Rift dust lanes, the Coalsack) term-for-term into pure,
testable functions (`galacticLB`, `milkyWayPixel`, `buildMilkyWayRow`).
`galacticLB` verified against two independent references (Sagittarius A* →
l≈0,b≈0; the North Galactic Pole → b=90), not just re-derived from the
formula. **Rendering technique changed, result didn't**: instead of porting
the archived engine's fullscreen-triangle + manual view-ray reconstruction
(a WebGL1 necessity — raw WebGL has no skybox primitive), this uses Babylon's
own `mesh.infiniteDistance = true` on a textured sphere — the exact mechanism
`scene.createDefaultSkybox()` uses, so it renders behind everything with no
depth-write or rendering-group special-casing. The same class of platform-
appropriate substitution as the star billboards replacing point sprites.
Benchmarked at ~250-400ms for the full 1024×512 grid on this machine — a
single synchronous build would stall several frames, so it's chunked 20
rows/frame (matching the archived engine's own pacing) via a new render-loop
tick, followed by one texture upload and a slow fade-in.

**GAP-04 — constellation figures.** Ported `_buildConstellations` (line
segments from each catalog entry's `.fig` data, radius 720) directly, reusing
`ship-dynamics.ts`'s `raDecToDir` rather than a third copy of that transform.

**GAP-05 — warp star trails.** Ported the trail-buffer build (every 3rd
field star, matching billboard positions exactly since both come from the
same decoded `StarField`) and the camera-lag EMA (`camPrev += (cam-camPrev)
*0.1`) that drives both the streak length and the `warpSpeed>0.4` visibility
gate. **A real technique gap had to be solved, not just translated**: the
archived engine's trail shader selects between two camera references
(`uCam`/`uCamPrev`) inside a rotation-only view matrix with manual camera
subtraction; Babylon's `view` matrix bakes in the real camera translation, so
swapping cameras per-vertex the same way is a no-op there. Fixed by offsetting
the already-view-transformed position by the ROTATED delta between the two
cameras (`viewPos.xyz += mat3(view) * (uCam - uCamPrev)`) — algebraically
equivalent to the archived engine's per-vertex camera subtraction, derived
and verified before writing the WGSL twin.

All three: GLSL+WGSL shader twins, reserved-identifier-guarded, line-list
draw mode (`Material.LineListDrawMode`) for constellations/trails.

## Two real bugs caught before reaching a browser

1. **Milky Way build cost.** A synchronous full-grid build benchmarked at
   250-400ms — confirmed via a standalone Node benchmark before committing to
   an implementation, not assumed. Forced the chunked-build design.
2. **The star-trail shader was a no-op in its first draft.** The expression
   `position minus cam plus cam` algebraically cancels to just `position` —
   a literal copy-paste of the archived engine's per-vertex camera-selection
   idea without accounting for Babylon's different view-matrix convention.
   Caught on inspection before any test or visual check ran; the corrected
   `mat3(view)`-based offset is what shipped, and both GLSL/WGSL twins are
   pinned by a unit test asserting the correction technique appears in both.

## Descoped, named

- Relativistic aberration/Doppler on the band, constellations, and trails —
  the same GAP-06 dependency named throughout TR-056 (not yet wired to
  stars or bodies either on this path).
- The constellation figures have no visibility toggle exposed on
  `<babylon-scene>`'s public API (the archived engine's `constellations`
  attribute); they render unconditionally. No current UI drives that toggle
  on either engine's chrome, so this is not a functional gap today.

engine's own understated depiction, not a functional defect. Zero console
output on both the WebGPU (Browser pane, real hardware) and WebGL2
