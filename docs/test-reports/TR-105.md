## Part 1 — The CI failures were Git LFS, not test performance (FIXED)

TR-104 sharded the CI `e2e` job. The first real CI run of that matrix (PR #6, run 30151830432)
came back **63 of 150 tests failed** across all four shards, in two signatures:

- `starSource: "procedural"` (star catalog never loaded) — vista-dismissal (all 7), engine-select's
  real-catalog test, others.
- `shipState: "failed"` (GLB parse threw) — camera-zoom, collector-card, craft-ship, engine-select,
  d64; plus `planet-pixels` luminance 6.7 vs required >8 (sphere textures blank).

**Root cause (confirmed both directions):** `.gitattributes` tracks every
`*.png/*.glb/*.jpg/*.jpeg/*.webp/*.obj` via **Git LFS** (2,806 objects). No `actions/checkout`
in `.github/workflows/ci.yml` set `lfs: true`, so CI checked out **~133-byte pointer stubs**, not
real bytes. Proof:

- CI: the `build` job's `dist` artifact downloaded by each e2e shard was **2.8 MB** (shard-4 log
  line 222) — ~2,700 pointer stubs × ~130 bytes, not the real ~281 MB.
- Local: `public/assets/sdss18.png` = 47 MB, `asteroids-dr3.png` = 2 MB — real bytes (LFS smudged
  on clone), which is why the identical suite passes locally. `git cat-file -s` on the committed
  blob returns 133 bytes (the pointer), confirming the working-tree bytes come from the LFS
  smudge filter, absent in CI.

The star-catalog PNG decode, the ship GLB parse, and the planet-sphere textures all got text
stubs → fell back / threw exactly as observed. The `lint`/`build` asset gates
(`assets:verify`, `budget:check:assets`) had been passing **vacuously** the whole time — a
133-byte "image" is trivially under budget.

**Fix:** `lfs: true` on the `build` and `lint` job checkouts
([.github/workflows/ci.yml](../../.github/workflows/ci.yml)). The e2e shards consume the real
assets via the `build` job's `dist` artifact, so they need no LFS fetch themselves. YAML
validated (`yaml.safe_load` OK).

**⚠ Bandwidth cost, flagged not hidden:** `lfs: true` pulls ~281 MB per job that sets it
(build + lint = ~560 MB/run). GitHub's free LFS bandwidth is **1 GB/month** — this exhausts it
in ~2 runs. Mitigations (not applied this pass, owner's call — recorded so the choice is
conscious, per ADR-0008's "retire a gate by decision, never by drift" culture):

1. **LFS object caching** via `actions/cache` keyed on the LFS file hashes — the standard fix,
   pulls from GitHub LFS only when assets change.
2. **Fetch LFS in one job only** — move `assets:verify`/`budget:check:assets` from `lint` into
   `build` (where LFS is already fetched), halving the per-run pull to ~281 MB. TR-034's
   branch-protection concern is satisfied because both are STEPS, not required-check names.
3. **A paid LFS data pack** if runs are frequent.

**Correction to TR-104:** that TR presented the 4-shard CI times (40/40/21.5/18 min) as if they
measured shard balance. They did not — they measured 2 retries × 20–30 s timeouts on the
LFS-caused failures. **The CI sharding change has never run against a working build**, so its
~42→~11-15 min estimate remains entirely unverified; shard balance must be re-measured once this
LFS fix lets a real suite run in CI. TR-104's local-only changes (consolidation, poll-interval)
are unaffected by this correction.

## Part 2 — Workers re-measurement (audit rec #2 / CLAUDE.md #16 re-validation)

The owner flagged the **local** suite at **48.4 min** as the core pain. That is `workers: 1` on
a **16-core / 50 GB** machine — 15 cores idle for 48 minutes. Audit recommendation #2 (re-measure
the `workers: 1` constraint before trusting it) had been open since the audit; discharged here
with three full-suite runs on the unchanged build (same `dist`, same machine, back-to-back), per
CLAUDE.md #4 "measure, don't assert":

| Config                  | Wall-clock        | Pass/Fail    | Speedup vs w=1 |
| ----------------------- | ----------------- | ------------ | -------------- |
| **workers=1** (current) | 48.4 min          | 150 / 0      | —              |
| **workers=2**           | 36.9 min (2217 s) | 137 / **13** | 24%            |
| **workers=4**           | 22.5 min (1355 s) | 126 / **24** | 54%            |

**Finding: parallelism alone is unsafe at every level tested.** Failures scale monotonically
with worker count (0 → 13 → 24) — a textbook resource-contention signature, not real
regressions (every failing test passes at workers=1). The failing set is the timing-sensitive
"near-zero-margin ceiling" class this repo keeps recalibrating (chase-camera choreography,
craft-ship tier resolution, planet-pixels, frame-ladder, ship-track): N concurrent
**software renderers** (SwiftShader — bundled Chromium has no GPU accel even locally) each
render slower, stretching every arrival/settle poll past margins calibrated for workers=1.

This **re-confirms CLAUDE.md #16 with fresh 2026-07-25 data** and reproduces the
`playwright.config.ts` comment's "2 workers still flaked" observation on this specific 16-core
machine. `workers: 1` stays. Recommendation #2 is now **closed: do not raise workers on the
current scene weight.**

The measurement-validity checks (CLAUDE.md #26) hold: all three runs used the same build, the
same machine, `--retries=0 --reporter=line` (non-blocking; two earlier attempts were voided — an
HTML-reporter hang risk and a `time`-not-a-binary shell error — neither produced a number, so
neither is reported as data).

## Part 3 — The real local-runtime fix, scoped (NOT yet implemented)

Since parallelism is blocked by per-boot cost, the lever is to **reduce per-boot cost**, which
_also_ reduces the contention that broke workers=2/4 — making parallelism safe to re-measure
afterward. The mechanism:

The three heavy background layers — `_loadBonusStarLayers` (≈555 k stars),
`_loadSdssGalaxyLayer` (3.64 M galaxies / 47 MB → 14.5 M+ vertices), `_loadAsteroidVisualLayer`
(154 k) — fire **unconditionally** after first frame
([babylon-engine.ts:2406-2411](../../src/lib/babylon-engine.ts:2406)), with **no flag to skip
them**. They don't gate `cosmos:ready`, but once built the software renderer rasterizes all those
extra millions of vertices **every frame for the rest of each test's life** — which is why the
long travel-sequence tests dominate.

**Measured: ~25.5 min of the 48.4-min suite comes from 7 files that make ZERO real assertions on
those layers:**

| File               | Suite time | Heavy-layer assertions                                                                       |
| ------------------ | ---------- | -------------------------------------------------------------------------------------------- |
| d64-owner-bugfixes | ~5.9 min   | none                                                                                         |
| earth-home         | ~4.8 min   | none                                                                                         |
| camera-zoom        | ~4.2 min   | none                                                                                         |
| collector-card     | ~3.5 min   | comments only (would _benefit_ — a background SDSS galaxy is a hover hazard it works around) |
| mid-warp-input     | ~3.1 min   | none                                                                                         |
| craft-ship         | ~2.3 min   | comments only (timeout-rationale)                                                            |
| ascent             | ~1.7 min   | none                                                                                         |

Only `field-travel` (14 real refs — field objects use the log-depth/SDSS coordinate path), the
~7 PF-10 data tests in `engine-select`, `planet-pixels`, and `frame-ladder` genuinely need the
heavy layers.

**Proposed slice (Lever B):** gate lines 2406-2411 behind a test-only URL flag (e.g. `?bg=off`,
default off — production and the ~10 tests needing the layers are byte-for-byte unchanged, so
**no CLAUDE.md #16 reversal and no ADR**). Apply the flag to the 7 files above. Design points to
settle at IMPLEMENT time: the flag must keep `cosmos:ready`/`cosmos:progress` firing normally
(boot-critical stages are unaffected — only the post-first-frame background fetches are skipped);
the heavy-layer `sceneStats` fields (`sdssGalaxyCount`, `asteroidVisualCount`, etc.) must return
0/false rather than undefined so no skipped-layer test crashes; and each file must be verified in
isolation for **implicit** heavy-layer dependence (a travel target that only exists in a bonus
layer, a hover expecting a background object) beyond the grep-confirmed absence of explicit
assertions. Once per-boot load is down, **re-run the workers=2/4 measurement** — contention may
have dropped enough to make a modest parallelism bump safe, at which point an ADR to revise #16
would be justified by data.
