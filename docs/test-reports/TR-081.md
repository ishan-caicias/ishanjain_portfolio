# TR-081 — PF-11 D0.1: frame-production liveness — the band build is deadline-paced, not frame-coupled

**Date:** 2026-07-22
**Slice:** PF-11 **D0.1** (delivery plan
[Phase D0](../delivery-plan/PF-11-cinematic-journey-and-scale-honesty.md#phase-d0--trustworthy-instruments-first-because-everything-else-is-measured-through-them)
· implementation companion
[D0.1](../implementation/PF-11-implementation-plan.md#d01-frame-production-liveness-band-build-decoupling--ready-ceiling-recalibration))
**Predecessor:** [TR-080](TR-080.md), which root-caused the two owner-reported failures and
promoted the remaining cumulative-load class to this slice.

## What this slice had to close

The Milky Way band's 1024×512 texture was built at a fixed 20 rows per **rendered frame**
(~26 frames), so total build wall-time scaled with 1/fps. Under a loaded SwiftShader run at
1–3 fps that is tens of seconds, which is the "bandReady never true" E2E signature. Exit
criterion from the delivery plan: **build wall-time must not scale with 1/fps**, plus three
consecutive full-suite runs green under deliberate load.

## The measurement that redirected the implementation

The implementation plan's step 1 prescribed time-budgeted slices driven by the render loop
**plus a `setTimeout(0)` chain between frames**, on the theory that the chain would bound the
build by CPU rather than by frame delivery. Implemented exactly as written, it made things
**worse**: a 6 ms slice builds ~7 rows where the old chunk built 20, and the chain did not
make up the difference.

Rather than tune blind, the scheduling slack itself was measured on the built preview under
Playwright's chromium/SwiftShader — the same environment the failure class lives in:

| Probe (5 s window, scene rendering)         | Result |
| ------------------------------------------- | ------ |
| self-rescheduling `setTimeout(0)` callbacks | **10** |
| `requestAnimationFrame` callbacks           | **12** |

The page main thread is saturated by the render loop, so a timer chain gets roughly **one slot
per frame**. Timers cannot decouple anything on this page — a real finding that invalidates the
prescribed mechanism, and one that reads across to every later "get this off the render loop"
idea (D7.3's SDSS decode, D7.4's sweep): go to a Worker or to deadline pacing, and measure the
slack before designing around it. Recorded additively in the implementation plan as a
[D0.1 correction](../implementation/PF-11-implementation-plan.md#d01-correction--step-1s-settimeout0-chain-cannot-carry-the-build-measured-2026-07-22-tr-081).

## What shipped instead — deadline-paced slicing

`MilkyWayBandBuilder` (`src/lib/milky-way.ts`) owns the row cursor and the RGBA buffer and is
driven by both the render loop and the timer chain (the shared cursor makes double-driving
safe — neither driver repeats the other's rows). Each slice:

1. measures the gap since the previous slice — the cadence the build is _actually_ being
   driven at, whatever the fps;
2. computes the rows still owed to land the whole grid by `MILKY_WAY_BUILD_DEADLINE_MS`
   (8000 ms) at that cadence, and builds at least that many;
3. otherwise stops at `MILKY_WAY_BUILD_MS_PER_SLICE` (6 ms), and never exceeds
   `MILKY_WAY_BUILD_MAX_SLICE_MS` (50 ms).

So a slow driver gets **bigger slices instead of a longer build**, and the frame-health cap
outranks the deadline (TR-059's frames-keep-producing contract wins; a pathologically slow
driver gets a later band, never a stalled frame). On a healthy machine the deadline never
binds: the 6 ms budget finishes the grid in ~1 s and the required-rows term stays at 1.

**The deadline also yields to an in-flight warp.** Deadline pacing spends _more_ frame time the
slower the machine is — precisely the wrong trade during the one sequence the visitor watches
frame by frame. `_buildBandSlice` therefore passes `paced = (warp.mode === "idle")`: warping
frames get the plain 6 ms budget and the band lands slightly later. This is the same priority
`_waitForWarpIdle` already applies to the three bulk layers, and it keeps a slow-machine band
build from bidding against the flight model for frame time.

The single `RawTexture.CreateRGBATexture` upload, the placeholder-then-swap discipline
(TR-059, CLAUDE.md #9), and the fade-in are unchanged. The timer chain is cleared in
`disconnectedCallback` so a callback can never build rows for a disposed scene.

## Measured before/after (built preview, Playwright chromium/SwiftShader)

Wall-clock from `page.goto` to `sceneStats().bandReady === true`, probed by a throwaway
Playwright script driving the built preview. **Load recipe** (reproducible, no committed
harness): fork N node children each running
`const end = Date.now() + ms; let x = 0; while (Date.now() < end) for (let i = 0; i < 1e6; i++) x += Math.sqrt(i);`
— self-terminating on a deadline so a killed parent can never leave the box spinning — started
3 s before the probe. This box has **16 logical cores**.

| Build pacing                             | Load       | bandReady  | frames rendered |
| ---------------------------------------- | ---------- | ---------- | --------------- |
| Baseline (20 rows/rendered frame)        | 16 workers | **16.4 s** | 31              |
| Step-1-as-written (6 ms slices + timers) | none       | **65.1 s** | 71              |
| Shipped (deadline-paced)                 | none       | **12.4 s** | 25              |
| Shipped (deadline-paced)                 | 16 workers | **14.0 s** | 25              |

The shipped row's insensitivity to load **is the point**: the band now lands in
deadline-bounded time (~8 s of build after boot) whether the page is delivering 6 fps or 2 fps,
where the baseline's cost is a fixed 26 frames — 26 s at 1 fps, unbounded as fps falls.

## Control experiment — is the loaded-suite failure set mine or the load's?

The first liveness attempt used a heavy load (**8** busy workers on 16 logical cores) and the
suite was not green: 85/87, 82/87, 84/87 with **rotating membership** — TR-052's documented
signature — except `engine-select.spec.ts:927` (GAP-17 flight sequence), which failed all three
times. A constant failure demands a control rather than a shrug, so the failing specs were run
twice per arm under the identical 8-worker load, rebuilding `dist/` between arms:

| Arm                                 | Pass 1                         | Pass 2                                         |
| ----------------------------------- | ------------------------------ | ---------------------------------------------- |
| **New code** (deadline-paced band)  | 1 passed, 2 failed (GAP-17 ×2) | **3 passed**                                   |
| **Baseline** (`git stash`, rebuilt) | **3 passed**                   | 1 passed, 2 failed (free-look, reduced-motion) |

**Symmetric.** At 8 workers the load itself starves SwiftShader and both builds flake on the
same GPU-heavy specs — so that recipe measures rasteriser starvation, not band liveness, and
the constant-looking GAP-17 failure was the load class after all. The verification below
therefore uses a **moderate 4-worker load** (closer to TR-080's "10 concurrent agents"
condition) plus one quiet run for the headline count. The mid-warp yield described above was
added before these runs, on its own merits.

**Session total: six full-suite runs — 87/87 ×3** (two quiet, one 4-worker loaded) **and
86/87 ×3.** Each single failure was identified, controlled against the pre-D0.1 build, and
attributed: two to a spec with no explicit ceiling (fixed here, named above) and one to the
flight model's missing screen-time floor (D3.2's scope — evidenced below).

**The two loaded failures were the same spec twice, so they got a control rather than a
shrug.** Run in isolation ×3 per arm under the identical 4-worker load: current build
**29.6 s / TIMEOUT / 37.0 s**, pre-D0.1 build (stashed and rebuilt) **30.5 s / 33.5 s /
27.8 s**. The failure text is `Test timeout of 30000ms exceeded`, not an assertion — the spec
carried no explicit ceiling and so ran against Playwright's 30 s default, which PF-10 scene
scale had already eaten on BOTH builds. Fixed the way TR-080 fixed its siblings: an explicit
`test.setTimeout(90000)` with the measurements in the comment, assertions untouched
(recorded in the named-test-changes table above). Re-run ×3 under the same load afterwards:
**28.2 s / 35.3 s / 25.9 s, 3/3 green.**

**The GAP-17 failure is a missing screen-time floor in the flight model, not a timeout.** Its
error is `expect(phases.indexOf("flip")).toBeGreaterThan(...)` **received -1** — the `flip`
phase was never _emitted_. `cosmos:warp` fires once per rendered frame, and the flip window is
k∈[0.47,0.53] of polaris's ~3.2 s journey ≈ **195 ms of wall clock**, so any single frame
longer than 195 ms steps over the entire window and the phase is skipped. That is the exact
defect **D3.2 is already scoped to fix** (widen to k∈[0.44,0.56] _with a duration floor
≥1.5 s_ — "duration floor logic, not just a k-window"), and fixing flight behaviour here would
be out of this slice. Evidence it is not caused by this change:

- **In isolation, quiet: 4/4 green** (14.8 s / 13.8 s / 13.2 s / 13.4 s).
- Across full-suite runs after the mid-warp yield landed, it passed 4 of 5 (quiet 87/87, all
  three 4-worker runs) and failed once.
- **Mid-warp, this build does strictly less per-frame work than the baseline it replaced:**
  measured ~0.9 ms per row, so the old fixed 20-row chunk cost ~18 ms per warping frame; the
  yielded slice costs ≤6 ms. The three 8-worker failures happened _before_ the yield existed,
  when an idle-paced slice could reach 50 ms — which is what prompted the yield.

The band's own specs — the TR-059 frames-keep-producing regression and GAP-03/04/05's
`bandReady` poll — passed in **every** run of this slice, quiet and loaded, at both load
levels.

## Known limitations

- The deadline is **best-effort under the 50 ms slice cap**, and on the SwiftShader/WebGL2 CI
  renderer the cap does bind: the manual-regression pass measured the band landing ~11 s after
  the first frame rather than the nominal 8 s. That is the correct priority order (frames
  outrank the band) and it is **bounded** — unlike the old behaviour, where the cost was a
  fixed 26 rendered frames and therefore unbounded as fps fell. If a future slice needs the
  band sooner on slow devices, the honest lever is a Worker, not a bigger slice.
- The mid-warp yield means a visitor who launches a warp during the first seconds of boot
  gets the band a little later still. Deliberate: the flight is the thing being watched.
- The `setTimeout(0)` chain is kept for the rAF-suspended case (backgrounded tab, where it is
  the only driver — verified: progress advanced with `renderFrames` pinned at 0) but
  contributes little under load. If a later slice needs the band _earlier_ on slow devices,
  the honest next step is a Worker, not a bigger budget.
- `bandProgress` is now exposed on `sceneStats()` (additive). D1.1 should read it rather than
  re-deriving band progress.
- The delivery plan's exit wording — "3 consecutive full-suite runs green under load" — turned
  out to be **under-specified**: "under load" has no defined level, and at 8 workers the
  pre-D0.1 build fails too. Read as written it measures the box, not the code. What this TR
  claims instead, and what the evidence supports: the band build is no longer frame-coupled
  (measured), the suite is green quiet and at a moderate load, and every remaining failure has
  a named non-band cause. If the owner wants the literal criterion, the load level has to be
  pinned first — and D3.2's screen-time floor should land before it is attempted again.

## Run audit (owner-requested, same session)

This slice took **3h01m** (15:18 → 18:19). Reconstructed from command timestamps: **~122 min
(67%) was the E2E suite running**, ~25 min targeted runs and probes, ~15 min builds/unit, and
~19 min of actual code and documentation authoring (most of it written while suites ran).

No result in this TR was asserted without a command behind it. Two wrong assumptions, priced
honestly: the **inherited** one (the plan's `setTimeout(0)` mechanism) cost ~10 min to disprove
and redirected the implementation — a good trade, and the most valuable output of the slice.
The **self-inflicted** one — treating an 8-worker load as a valid instrument without
calibrating it — cost **~45 min** across three full suites and the control that invalidated
them. Smaller leaks: three rebuild cycles lost to running `npm run build` before Prettier, and
a detour discovering that this environment's browser pane keeps its tab backgrounded (rAF
suspended), so manual regression must go through a scripted chromium.

**Avoidable: ~50-55 min (≈30%). Realistic floor for this slice: ~105-120 min**, dominated by
the ~4 full-suite runs the exit criterion demands at ~13 min each. The lessons are now
repo-durable as **CLAUDE.md #26 (calibrate a harness before it gates anything)** and **#27
(three full-suite runs per slice; never characterize one spec with the full suite)**, under a
new "Verification economics" heading that cites this TR.
