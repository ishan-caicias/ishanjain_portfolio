## What this slice had to close

Handoff B4 (PF-10 C4 closeout): **"engine state is provably correct — mesh visible, scale 26,
camera at exactly the documented 38-unit standoff, ultra tier, VT tiles bound — but no pixel
confirmation exists." Five sessions running, a different mechanism each time** (TR-079 Part 8b
named this the project's single largest verification gap). Exit criterion: a committed screenshot
per sphered body class, plus one pixel assertion wired into CI.

## Root cause

Every prior harness kept the camera's **initial bearing**. On arrival, `travelTo`/`_beginWarp`
place the camera at the correct **standoff** (`this.cam = w.to`, exactly `ARRIVE_STANDOFF = 38`
along the Sun-body line — this part was always right). But `_tickWarp`'s idle branch
unconditionally re-derives camera _orientation_ from `_yaw`/`_pitch` via `freeLookDir` —

```ts
this._camQuat = quatFromUnitVectors(
  BABYLON_FORWARD,
  freeLookDir(this._yaw, this._pitch),
);
```

— and nothing had ever pointed those two fields at the arrived body. `_yaw`/`_pitch` sit wherever
free-look last left them (0/0 on a fresh page), so the sphere sat outside the frame on the
programmatic path **and** through the real UI, for as many sessions as this was attempted with a
different guess at the mechanism each time.

## What shipped

**`aimAt(bodyId)`** (`src/lib/babylon-engine.ts`, next to `travelTo`/`goHome`/`randomBody`/
`setStations`) — a harness-only method, gated behind `?testhooks`
(`new URLSearchParams(location.search).has("testhooks")`, checked inside the method so a caller
that forgets the param gets a safe no-op, not a silent product-feature leak). It looks up the
body's already-computed world position (`this.bodies[].pos` — the same field `travelTo` reads),
computes the unit direction from the camera's current position (`this.cam`) to it, and inverts
`freeLookDir`'s parametrization (`pitch = asin(dy)`, `yaw = atan2(dx, dz)`) to set `_yaw`/`_pitch`.
No new rendering path: the render loop's existing idle-orientation tick picks the new bearing up
on its very next pass, because that tick already recomputes `_camQuat` from `_yaw`/`_pitch` every
frame. The fix is exactly two field writes, once the root cause was found.

Computing from **position difference** rather than reusing the body's stored `dir` (which,
un-aimed, is trivially aligned with the camera's arrival bearing) was deliberate: it aims
correctly from free-look, mid-aim, or at a body other than the one just arrived at, not only in
the one geometry every previous harness assumed.

**`tests/e2e/planet-pixels.spec.ts`** — new spec. Per body (Mars, Moon): wait for the catalog to
load, `travelTo(body)`, poll `arrivedId`/`planetSphereVisible`, `aimAt(body)`, screenshot the
`babylon-scene canvas` element (CLAUDE.md #11 — a Locator screenshot goes through the real
compositor, never `drawImage`/`getImageData` on the canvas), decode with `sharp` (already a repo
dependency), and assert both **mean luminance** and **luminance variance** above conservative
floors on a centred 30% crop. Both together are the actual non-blank-region assertion: deep space
is near-black (fails both), a flat placeholder ball would pass the luminance floor but fail
variance, and a lit, textured sphere passes both. The crop size is sized from the fixed geometry
(`ARRIVE_STANDOFF=38`, `PLANET_SPHERE_RADIUS=26` → ~69° angular diameter once aimed), not tuned to
pass.

Reference screenshots are committed **once, by hand** (`docs/test-reports/assets/pf11-d0.2-{mars,
moon}.png`) rather than regenerated by every CI run — a test silently rewriting files under
`docs/` on each pass would be its own defect. The spec supports re-capture via
`PF11_CAPTURE_REFERENCE=1` for a genuine future visual change; it is a no-op otherwise.

Earth-via-`goHome` is **not** captured this slice — Earth is unreachable until D6.4's home-orbit
reveal lands (handoff B1); the delivery plan names this explicitly ("Earth-via-goHome once D6.4
lands").

### The one full-suite failure is pre-existing and out of scope

`engine-select.spec.ts:937` — "GAP-17 — the flight sequence runs accel → flip → decel in strict
order" — failed with `phases.indexOf("flip")` returning `-1`. This is **exactly** the flake TR-081
named and attributed to **D3.2** (not this slice): polaris's flip window is ~195 ms of wall clock,
so any single rendered frame longer than that skips the `flip` phase entirely — a flight-model
duration-floor defect the delivery plan already scopes to D3.2, evidenced in TR-081's own
isolation runs (4/4 green there) and full-suite history (passed 4 of 5 runs in that session).
Confirmed not caused by this slice: `git diff` on `babylon-engine.ts` for this slice touches only
a new method appended after `setStations` (`aimAt`) — nothing in `_tickWarp`'s phase/HUD emission
logic. This slice's own new spec (`planet-pixels.spec.ts`) passed in the same full run.

## Known limitations

- `aimAt` is a harness hook, not a product feature — a visitor never gets a "look at" affordance
  from this slice. If a future slice wants a genuine "recenter on target" UX, that is new scope
  with its own design, not a repurposing of this guard.
- The variance/luminance thresholds are conservative floors sized off the sphere's known angular
  size at the fixed arrival geometry, not tuned per-body — if a future body ships with an
  unusually dark or low-contrast texture, the floors may need revisiting (not expected for the
  current 16-body manifest, all of which have real photographic surfaces).
- Only Mars and Moon are captured. Earth is deliberately deferred to D6.4 (home-orbit reveal);
  the other 14 sphered bodies are not separately captured — the pixel-proof _mechanism_ (aimAt +
  the assertion shape) is what this slice closes, not exhaustive per-body coverage. Extending to
  more bodies is cheap (the spec is a `for` loop over an id list) if a later slice wants it.
- The one-off cumulative-load timeout (Moon, capture run) was not reproduced on demand and is
  therefore recorded, not root-caused further — consistent with the existing C7/TR-080/TR-081
  finding that this repo's SwiftShader CI environment has a residual load-sensitive flake class
  that D0.1 reduced but did not eliminate.
