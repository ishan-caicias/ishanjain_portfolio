## Critical caveat: this is NOT a clean B6-only baseline

**This build includes everything shipped through TR-067** — the B6 Babylon cutover itself, plus
all of PF-10 C1 (star clusters, minor planets, NEARGALCAT, GD-1, white dwarfs, CNS5, Oort cloud,
41 NGC2000 nebulae) and, critically, **PF-10 C2's SDSS DR18 galaxy field** — 3,637,862 real
galaxies on their own mesh, loaded on **every** quality tier per TR-067's "ideal-state-first"
pivot (no tier gating). Real measurement earlier in the same session (TR-067), on this exact
desktop via real Chrome/GPU: **~50 fps with SDSS loaded**, vs. CI's unrepresentative ~3 fps under
SwiftShader. The 40 fps desktop reading here is in the same real ballpark, not an outlier.

**This matters for how to read these numbers**: B6's original §A budget table (60/60/40/30 fps
by device class) was set against the B6-era feature set, before PF-10 added ~14.5 million extra
billboard vertices unconditionally. These 5 readings are honest, real, and valuable — but they
are answering "does the CURRENT full ideal-state build hit the ORIGINAL fixed budgets," not "did
the B6 cutover itself regress." Those are different questions. Conflating them would either
unfairly blame B6 for PF-10's scope, or unfairly wave through a real budget miss as "B6 passed."

## The real anomaly, not smoothed over: flagship underperforms mid-tier

The Galaxy S24 Ultra (2024 flagship) scored **worse** than the Galaxy S20 FE (2020 mid-tier) —
28-35 fps vs. 45-49 fps, on hardware that should comfortably out-render an older mid-tier phone.
This is backwards and unresolved. Plausible real causes, **none confirmed** — the data needed to
distinguish them wasn't captured this pass:

- **Resolution/DPI**: the S24 Ultra's native display resolution is substantially higher than the
  S20 FE's; if the canvas renders at full device-pixel-ratio, the flagship may simply be shading
  more real pixels per frame regardless of GPU class — a genuine, explainable cost, not a bug.
- **Backend divergence**: the perf overlay's `ENGINE babylon (webgpu|webgl2)` line was not
  captured for either device this pass. If one device landed on WebGPU and the other fell back to
  WebGL2, the two readings aren't measuring the same rendering path and shouldn't be compared
  directly.
- **Quality-tier divergence**: the resolved `TIER` line (full/balanced/lite) was also not
  captured. Different tiers change asteroid count, halo amplitude, nebula step count — real,
  independent variables this data doesn't isolate.
- Real thermal throttling on that specific unit, or a genuine driver/GPU issue — can't be ruled
  out or confirmed from fps alone.

**Also flagged, lower severity**: two internal inconsistencies worth a second look, not
necessarily instrument bugs — (1) render FPS slightly exceeds host rAF on the S24 Ultra (28 vs 25)
and S20 FE battery-saver (49 vs 48) readings, which is unusual (rendered frames shouldn't exceed
the callback rate that drives them) but not conclusively wrong without more samples; (2) the S20
FE's reported `displayHz` differs between its two rows (66Hz vs. 64Hz) for the same physical
screen — plausibly real (some phones do drop refresh rate in battery saver) but also consistent
with sampling noise in how `displayHz` is estimated. Neither rises to CLAUDE.md's explicit
instrument-rejection bar (`renderFps > displayHz`, `startupMs < 300`, `renderFrames` 0/null,
identical device blocks across rows) so none of these 5 readings are discarded — they're recorded
as-is, with these caveats attached rather than silently smoothed over.

## Recommendation (not closing B6 unilaterally)

The owner asked to close B6 on this data; the data itself doesn't support a clean close, so this
report records the real numbers and a real recommendation instead of rubber-stamping the gate:

1. **Desktop (A1) misses its budget** — most plausibly explained by SDSS's unconditional full-
   scale load (TR-067's own real-GPU measurement was already ~50 fps, below 60, before this
   confirms ~40 fps on a second real desktop run). This is the expected, useful signal the
   "ideal-state-first" strategy was built to surface: real data now exists to make a real
   tier-gating decision for SDSS specifically, not a preemptive guess.
2. **The flagship-underperforms-midrange anomaly needs one more data point before acting on it**
   — specifically the `ENGINE`/`TIER` lines from the overlay on both phones, to rule out a
   backend or tier mismatch before concluding it's a genuine GPU/thermal issue.
3. **A2 (iPad) and A4 (WebGL2 fallback) remain untested** — B6's own checklist has always listed
   these as open; this pass didn't change that.

**Suggested next step**: re-run the S24 Ultra and S20 FE checks, this time reading back the full
overlay (`ENGINE ... TIER ...` line, not just startup/fps/rAF), to isolate whether the anomaly is
backend/tier-driven or a real hardware issue — then decide, with that fuller picture, whether SDSS
(and/or the other bonus layers) need real tier gating before B6 can close.
