## Step 5 — distance-scaled travel: new math, not a port

Checked before designing anything: `space-engine.js`'s `travelTo` hardcodes `warpDur: 2400`
regardless of target distance — the live engine has **no** existing distance-scaled pacing to
carry over. The delivery plan's own wording ("near hops are quick; multi-hundred-ly journeys spend
longer at cruise ... so speed communicates distance") describes new intended behaviour, not a port,
so this is genuinely new pure math designed for Babylon.

**`warpDurationForLy(ly)`**, [ship-dynamics.ts](../../src/lib/ship-dynamics.ts): log10-scaled and
bounded to `[WARP_MIN_MS=1400, WARP_MAX_MS=4200]`. Checked against the shipped catalog before
picking bounds — `ly` ranges from ~0 (solar system) to **13 billion** (a distant SDSS galaxy,
confirmed by grepping every `celestial-*.js` file, not assumed). A linear mapping would make a
single deep-catalog click either absurd or force every near hop to instant; log10 keeps the whole
practical named-body range (Sirius 8.6 ly → Orion Nebula 1,344 ly) spread across most of the
duration band, then clamps everything beyond ~10,000 ly to the same ceiling.

The **shape** of the journey is unchanged — the same `warpEase` accel-flip-decel curve from step 4,
just stretched over a longer duration for far targets. No new easing curve was invented; an
ease-in-out-quad's velocity already peaks near its midpoint, so stretching it over more wall-clock
time reads as a longer cruise without touching the existing phase-threshold logic (`k < 0.47` etc.,
which key off the fraction, not the duration).

`goHome` always uses `WARP_MIN_MS` (the floor) regardless of current position — returning home
should feel snappy, matching intuition rather than any live-engine precedent (there isn't one).

## Step 6 — reduced-motion parity: a direct port

Read `space-engine.js`'s `reduced` handling in full before implementing (not assumed from memory,
consistent with this session's established discipline after the WebGPU-claim correction). Three
branches ported exactly:

1. **Fixed short durations, NOT distance-scaled.** `AIM_DUR_REDUCED_MS=200`,
   `WARP_DUR_REDUCED_MS=350` — same values as the live engine's own reduced branch. Reduced motion
   overrides step 5's formula entirely; it means "get there fast," not "get there fast,
   proportionally to distance." Verified directly: traveling to Orion Nebula (the single longest
   non-reduced journey in the catalog) still resolves to exactly 350 ms under reduced motion.
2. **`CHASE_OFFSET_REST` instead of the waypoint table.** No behind-the-thruster sway when motion
   is reduced — a fixed astern offset.
3. **Snapped orientation, not damped.** `this._camQuat = targetQ` directly instead of
   `quatDamp(...)`, matching the live engine's `if (this.reduced) { this.yaw = toYaw; ... }`.

`_reduced` is a one-shot snapshot taken once in `_boot()`
(`window.matchMedia("(prefers-reduced-motion: reduce)").matches`) — deliberately the same pattern
as `space-engine.js`'s own `this.reduced` (no live-updating `MediaQueryList` listener either
engine has), not a gratuitous improvement.

## Honest limits

- `warpDurationForLy`'s bounds (1400–4200 ms, log range 0–4) are a first design pass, not tuned
  against owner feedback on how the pacing actually feels — unlike steps 1–4, there was no live
  engine behaviour to match against, so "correct" here means "matches the plan's stated intent and
  is bounded sanely," not "verified against a reference."
- Reduced-motion coverage is state-level (durations, offset, snap) — not a visual/perceptual check
  that the reduced journey actually reads as calmer, which would need a human or a pixel-diff
  harness this report doesn't attempt.
