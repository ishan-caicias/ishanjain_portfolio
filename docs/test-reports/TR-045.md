# TR-045 — Regression: reserved WGSL identifiers blanked the entire scene on real WebGPU hardware

**Date:** 2026-07-19
**Scope:** Owner report against the live demo server: `?engine=babylon` showed a flat dark
background — no stars, no shooting stars — on desktop Google Chrome. TR-044's shooting-star WGSL
twin used `meta` and `ref` as identifiers, both **reserved WGSL keywords**. Chrome's WGSL compiler
rejected the shader module; the resulting invalid pipeline blanked the entire frame's draw
submission, not just the shooting-star mesh. This shipped in TR-044 as "READY TO PROCEED" — that
verdict was wrong, and this report says so plainly rather than softening it.
**Verdict: OVERALL: READY TO PROCEED** (post-fix) — 140/140 unit · 61/61 E2E · build/lint exit 0.
The regression is fixed and the specific verification gap that let it through is closed.

## How this shipped as "verified"

TR-044's real-hardware check asserted `shootMeshReady: true` and `shootMaterialReady: true`, both
of which were genuinely `true` — and the scene was still completely broken. The reason: **WebGPU
shader-module creation does not throw synchronously on invalid WGSL.** The browser accepts the
`createShaderModule()` call immediately and validates asynchronously, reporting failures via an
"uncaptured error" device event — which surfaces **only as a console message**, never as a thrown
JS exception or a Babylon-level readiness flag going false. TR-044's test checked the one signal
(`materialReady`) that this exact failure mode doesn't affect, and never listened to the console.

```
warning: BJS - [Frame 3] WebGPU uncaptured error (1): [object GPUValidationError] -
Error while parsing WGSL: :10:14 error: 'meta' is a reserved keyword
@location(2) meta : vec4<f32>,
             ^^^^
```

Once one pipeline in a frame is invalid, Babylon's single command-buffer submission model means
the **entire frame's draws are rejected together** — the star field (a completely separate,
correctly-written mesh and shader) went dark too, not because it was broken, but because it shared
a submission with something that was.

## Why my own live debugging nearly reached the wrong conclusion too

Diagnosing this live, my first instinct was to sample canvas pixels via `drawImage()` +
`getImageData()` — the same method the project's WebGL2 pixel-proof test uses. It returned zero
lit pixels **both before and immediately after the fix**, which would have wrongly suggested the
fix hadn't worked. The actual cause: **a WebGPU canvas cannot be reliably read back via
`drawImage()`** — a limitation this project already documented in
[TR-036](TR-036.md)'s honest-limits section ("a WebGPU canvas cannot be read back via drawImage
locally") and then didn't apply here under time pressure. Switching to `page.screenshot()`
(browser-compositor level, not a JS canvas API) settled it immediately: the pre-fix screenshot
matched the owner's report exactly (flat background, badge showing `168,959 STARS` with nothing
visible), and the post-fix screenshot showed the full photometric star field rendering correctly.

## The fix

Renamed the two reserved identifiers, consistently across both shader twins (not just the WGSL one
that failed — GLSL doesn't reserve these words, but keeping the names identical avoids exactly this
class of divergence in the future):

- `meta` (vertex attribute) → `shootMeta`, in the GLSL twin, the WGSL twin, and the JS-side
  `VertexBuffer`/`attributes` wiring.
- `ref` (local variable) → `refAxis`, in both twins.

`shoot.meta` — the pure `shooting-stars.ts` module's own returned field name — was **not**
renamed; it is a plain JS object property, not a compiled shader identifier, and was never the
problem.

## The verification gap, closed

`webgpu-hardware.spec.ts`'s real-hardware test now listens to the browser console throughout the
test and asserts zero error/warning messages, in addition to the existing readiness checks. This is
the assertion that would have caught TR-044's regression — `materialReady` alone provably does not,
confirmed by the fact that it reported `true` on the broken build. Verified the new check passes
clean (zero console issues) against the fixed build; not verified against the broken build directly
(the broken code is no longer in the tree to re-test against), but the console output captured
during live diagnosis, quoted above, is the same class of message the assertion checks for.

## What this changes about TR-044's verdict

TR-044 is **not** being silently amended — its "READY TO PROCEED" verdict was wrong, and that's
recorded here rather than edited away. The shooting-star feature itself (geometry, lifecycle math,
GLSL twin) was and remains correct; the WGSL twin had a real, scene-breaking defect that TR-044's
verification did not have the tooling to catch. TR-044's own honest-limits section said "no
visual/perceptual confirmation" was performed — that caveat undersold the actual risk: it wasn't
just "unconfirmed how it looks," it was "unconfirmed whether it renders at all on the real WebGPU
path," which is a materially different and more serious gap.

## Process note

This is the second time this session a "compiles/reports ready" signal has been trusted past what
it actually proves (the first: TR-040's Electron-pane `renderFrames: 0` investigation, a false
alarm in the _other_ direction — that time the code was fine and the environment was misleading;
this time the code was genuinely broken and the readiness check was misleading). The lesson from
both, now encoded as a standing check rather than a one-off fix: **for this project's WebGPU path,
neither "no exception thrown" nor "materialReady: true" is sufficient evidence of correctness —
console output must be checked, and pixel evidence must come from `page.screenshot()`, not
`drawImage()`.**
