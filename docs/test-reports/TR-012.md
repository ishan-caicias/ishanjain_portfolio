# TR-012 — Strict LF Enforcement (.gitattributes)

**Date:** 2026-07-17
**Scope:** Follow-up to [TR-011](TR-011.md) — replace the `endOfLine: "auto"` accommodation with repo-enforced LF
**Verdict: OVERALL: READY TO PROCEED**

## Purpose

TR-011 fixed the Prettier/CRLF conflict by letting Prettier accept whatever line endings the
working tree had (`endOfLine: "auto"`). That accommodated the symptom. This change eliminates the
cause: the repository now mandates LF in every working tree, on every platform, regardless of each
clone's `core.autocrlf` setting.

## What Was Changed

| File              | Change                                       | Effect                                                                                                                 |
| ----------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `.gitattributes`  | Added `* text=auto eol=lf` (above LFS rules) | Checkout produces LF everywhere; attributes override `core.autocrlf`. Binaries unaffected (`text=auto` + LFS `-text`). |
| `.prettierrc`     | Removed `"endOfLine": "auto"`                | Prettier reverts to its default (`lf`), now consistent with what git checks out.                                       |
| Working tree      | 74 tracked files converted CRLF → LF         | Script-converted only files git reported as `i/lf w/crlf` — stored-LF text files with CRLF working copies.             |
| `docs/analysis/*` | 6 untracked Codex-generated docs prettified  | Were CRLF/unformatted; now pass the strict check.                                                                      |

## Safety Checks Performed

- **No content drift:** before conversion, every affected file was `i/lf` (stored as LF); after
  conversion and `git add --renormalize .`, the staged diff was exactly the two config edits —
  the 74 converted files produced **zero** staged changes.
- **Binary safety:** conversion ran only over git's own `w/crlf` text-file list; LFS patterns
  (`jpg/jpeg/png/webp/obj`) carry `-text` and were never candidates.
- **Fresh-checkout simulation:** deleted and re-checked-out `README.md` on this machine
  (`core.autocrlf=true`) — git produced LF (`i/lf w/lf`), proving the attribute wins.

**OVERALL: READY TO PROCEED.** LF is now enforced repo-side. Any contributor's clone — regardless
of platform or `core.autocrlf` — checks out LF, and Prettier's default expectation matches
reality. This closes the follow-up recorded in TR-011.
