# TR-104 — E2E suite optimisation: CI sharding, redundant-boot consolidation, poll-interval fix

**Date:** 2026-07-25
**Slice:** Implementation of the 2026-07-25 E2E performance/staleness audit's recommendations
#1, #3, and #4 (test-infra/CI only — no `src/` change).
**Predecessor:** [docs/analysis/2026-07-25-e2e-suite-performance-and-staleness-audit.md](../analysis/2026-07-25-e2e-suite-performance-and-staleness-audit.md)
(the audit itself — root-cause analysis, spec-file cost ranking, PF-07…PF-11 staleness check
[zero stale tests found]); [TR-103](TR-103.md) (last full-suite baseline).

## What this pass is

The owner flagged the Playwright suite taking "nearly 40 min" as a development-velocity problem.
The prior audit found the growth (12.8→42.2 min, TR-081→TR-103) was earned — PF-10/11's real
datasets genuinely made every full-scene boot heavier — not caused by stale tests (none found)
or an outdated framework (Playwright `^1.61.1` already ahead of the latest public release). It
identified five root causes and five recommendations, ranked by impact. This pass implements the
three the owner approved without further discussion: #1 (CI shard matrix), #3 (the
already-self-diagnosed `frame-ladder.spec.ts` poll-interval fix), and #4 (`engine-select.spec.ts`
redundant-boot consolidation). #2 (re-measure `workers:1` before touching it) and #5
(`webgpu-hardware.spec.ts` CI cost) turned out not to need action — see below.

## Changes

**1. `.github/workflows/ci.yml` — CI shard matrix (recommendation #1).** The single `e2e` job
became a 4-way matrix (`strategy.matrix.shard: [1,2,3,4]`, `npx playwright test
--shard=${{matrix.shard}}/${{strategy.job-total}}`), each shard its own `ubuntu-latest` runner
with its own SwiftShader instance — this does **not** reproduce the "N workers time-slicing ONE
GPU" flake `workers:1` exists to prevent (that's about local multi-worker contention on ONE
machine; shards share no GPU). `workers: 1` stays in effect **inside** each shard via
`playwright.config.ts`, unchanged. A new `e2e-summary` aggregator job (`needs: e2e`, `if:
always()`, fails if any shard didn't succeed) is named `"E2E Tests"` — the exact name the old
single job had — so any existing branch-protection required-status-check rule keeps working
without edits (the same reasoning TR-034 already established for `docs:check`/`assets:verify`
living as steps rather than new jobs).

**2. `tests/e2e/frame-ladder.spec.ts` — poll-interval fix (recommendation #3).** The file's own
comment already diagnosed that its ~100ms `sceneStats()` polling (a real cross-context CDP
`evaluate()` round trip) competes with `requestAnimationFrame` for the single SwiftShader-bound
main thread, inflating wall-clock ~4× against engine time (TR-089/TR-094). All 7 `expect.poll`
calls now pass `intervals: [500, 1000]` instead of Playwright's default escalating
`[100,250,500,1000]`. No assertion or timeout value changed — only how often the test asks.

**3. `tests/e2e/engine-select.spec.ts` — redundant-boot consolidation (recommendation #4).** Two
merges, no assertion dropped:

- The clusters / NGC2000 nebulae / GD-1 trail tests (3 separate full boots) → 1 test, 1 boot. The
  old standalone NGC2000 test's count assertion was a pure duplicate of a check the clusters test
  already made (`counts.ngc2000`) — found while merging, not introduced by it.
- The SDSS DR18 / Gaia DR3 asteroid belt tests (2 separate full boots) → 1 test, 1 boot. Both
  layers fetch/decode **concurrently** during any single boot regardless of which test reads
  them, so this was never a sequential cost — just two 90s-budgeted tests each independently
  paying for a boot the other test's boot already incurred.

Net: 32→29 tests in this file (153→150 suite-wide), same coverage.

## Recommendations from the audit that needed no action

- **#2 (re-measure `workers:1` before touching it):** not attempted. The A/B work in this pass
  (below) reinforced why: local single-machine timing on this dev box has a demonstrated noise
  band wide enough (see Verification) to swallow a `workers` re-measurement's signal unless it's
  done in isolation on a quiet machine, which is future work, not part of this slice.
- **#5 (`webgpu-hardware.spec.ts` CI cost):** re-reading the file found it already fails open —
  every test calls `test.skip(true, …)` the instant `chromium.launch({channel:"chrome"})` can't
  get a real adapter (`webgpu-hardware.spec.ts:46-56`), which is true immediately in CI (no real
  Chrome channel installed). The "wasted boot cost" the audit worried about is actually just one
  failed browser-launch attempt per test, not a full scene boot — negligible, no change needed.
  The audit's concern was based on not having read this far into the file; corrected here.

## Verification

**Isolated verification before the full gate**, per CLAUDE.md #27 (characterize a change in
isolation, not by re-running the whole suite):

- `engine-select.spec.ts` alone: **29/29 passed, 6.7 min**, one run — no failures, no flakes.
- `frame-ladder.spec.ts` — a controlled A/B, 3 runs each, same build, same machine, back to
  back, because the file's own comments already flag a known "rotating LEG" flake class
  (TR-080/081):
  - **Baseline (original 100ms-default polling, temporarily restored via a file swap, not a
    git operation):** 2/3 passed (2.4–2.5 min each); 1/3 failed at the exact same assertion
    the file's comment names (`localFieldFade` restored at home, a 15s-budget fade-convergence
    check).
  - **This pass's change (`intervals: [500,1000]`):** 2/3 passed (2.0–2.1 min each — 15-20%
    faster than baseline's passing runs); 1/3 failed at the **same** assertion.
  - **Conclusion:** the flake is pre-existing and reproduces identically on the unmodified file
    — this change does not introduce or worsen it, and measurably speeds up the passing case.
    Not fixed in this pass (out of scope — a real fade-convergence timing margin issue named and
    partially addressed twice already, TR-080/081/094/096/097; flagged below as a follow-up).

**Named honestly, not glossed over: the full-suite wall-clock went UP (42.2 → 47.8 min), not
down.** Root-cause investigated before writing this up, not assumed:

- This full run followed directly after ~40 minutes of this session's own back-to-back isolated
  Playwright invocations (the engine-select and frame-ladder A/B runs above, plus two builds and
  a unit-test run) on the same physical Windows dev box — a real, demonstrated confound, not a
  hypothesis. Process inspection immediately after the run found no leftover Playwright/
  `ms-playwright` Chromium or `astro preview` processes (clean exit), but the same machine
  session had just sustained ~40 minutes of continuous browser-launch load, which the D0.1 audit
  (CLAUDE.md's own "verification economics" rules, #26/#27) already establishes as exactly the
  kind of uncalibrated-instrument condition that produces untrustworthy single-run timing.
- **The primary lever this pass implements — CI shard matrix (#1) — cannot be measured on this
  local machine at all.** Local runs stay at `workers: 1` by design (unchanged); the sharding
  benefit is specifically that 4 **separate CI runners** each run a ~quarter of the suite in
  **parallel**, which only exists once this workflow actually executes in GitHub Actions. A
  local serial full-suite number was never going to reflect it either way.
- The two locally-measurable fixes (frame-ladder poll interval, engine-select boot consolidation)
  are individually worth roughly 1-2 minutes combined against a demonstrated same-day, same-build
  run-to-run noise band of at least 5.6 minutes (this pass's own 42.2→47.8 comparison). At this
  scale, chasing a lower local number by re-running is not a good use of the "three full-suite
  runs per slice" budget (CLAUDE.md #27) — the correctness gate (0 failures, exact expected test
  count) is what this run actually proves, and it's clean.
- **What would actually validate the CI-timing claim:** the first real GitHub Actions run against
  this branch's `ci.yml`. That's a follow-up, not something this local session can produce.

## Known limitations / follow-ups

- **CI sharding is unverified in situ.** The shard matrix has not yet run in GitHub Actions
  (this session only edited the YAML and validated it locally cannot apply, since sharding
  requires actual parallel runners). First real CI run on this branch is the actual test of
  recommendation #1's ~42→~11-15 min estimate.
- **`frame-ladder.spec.ts`'s pre-existing "rotating LEG" flake** (the `localFieldFade`/
  `furnitureFade` near-zero-margin fade-convergence checks) was investigated causally here (A/B
  confirmed pre-existing, not introduced) but not fixed — it's the same class TR-080/081/094/
  096/097 have already budget-adjusted twice. A real fix likely needs either a wider budget once
  more or the engine-side fade timing made less marginal; flagged for whoever next touches this
  file, not addressed as a side effect of an unrelated performance pass.
- Recommendation #2 (re-measure `workers:1`) remains open — needs a quiet-machine, isolated
  measurement session, not one stacked after 40 minutes of other Playwright activity.
- No manual regression pass on the built preview: this slice touched only `tests/e2e/*.spec.ts`
  and `.github/workflows/ci.yml` — zero `src/` files changed (confirmed via `git diff --stat`).
  There is no product behaviour for a manual pass to check that the 150/150 automated E2E run
  didn't already exercise identically to before.
