## What shipped

New pure module [shooting-stars.ts](../../src/lib/shooting-stars.ts), unit-tested (13 tests):
`buildShootingStars(count, radius, seed)` builds a merged indexed mesh of tapered quads (same
quad-not-line-primitive choice the star billboards already established in TR-029 — thin GPU
primitives don't render consistently across WebGL2/WebGPU). Each particle spawns on a shell around
the origin with a **tangential** direction (perpendicular to its own radial vector, reusing
`travelFrame` — the same pure function the chase camera uses — so it streaks across the sky rather
than flying straight at/away from wherever the camera happens to sit).

**Genuinely GPU-driven, unlike the live engine's ember pattern.** Every particle's current
head/tail position and fade are computed **in the vertex shader** from a single `uTime` uniform:
`age = (uTime + seed·cycle) mod cycle` gives each of the 24 particles a distinct, endlessly-
repeating phase from one shared cycle length. Zero per-frame CPU cost after the initial buffer
upload — no stepping function, no re-upload, no CPU-side particle array.

Shader twins `ijShootVertexShader`/`ijShootFragmentShader` (GLSL + WGSL) added to
[babylon-engine.ts](../../src/lib/babylon-engine.ts), following the codebase's established
convention (line-for-line parallel twins, corner-from-vertex-ID derivation, `uniforms.` prefix in
WGSL). **The WGSL twin caught a real bug during review, before it ever ran**: a first draft wrote
`vertexInputs.uTime` (a vertex-input attribute reference) where it needed `uniforms.uTime` (a
uniform reference) — caught by re-checking the star shader's own established `uniforms.X` pattern,
fixed before the real-hardware test ran, and the corrected version compiled clean on the first
real-adapter run. Recorded because it's exactly the class of error a type-checker can't catch (WGSL
lives in a template string) and the project's own TR-029/TR-039 history shows this codebase has hit
before.

`sceneStats()` extended with `shootMeshReady`/`shootTotalVertices`/`shootTotalIndices`/
`shootMaterialReady` — the same diagnostic pattern already used for the star mesh, not a new
convention.

## Honest limits

- **No visual/perceptual confirmation.** Verified that the mesh is ready, both shader twins
  compile, and the pure geometry math is correct — not that the particles actually _look_ like
  shooting stars on a real screen. Consistent with this plan's established pattern (TR-037: a
  procedural placeholder that compiled and rendered fine still needed the owner's own eyes to catch
  it read 6× too dense) — a screen check from the owner is the next honest step, not claimed here.
- **Tuning values (24 particles, 5 s cycle, 60–150 unit/s speed, 220-unit spawn shell) are a first
  design pass**, same caveat as `warpDurationForLy` in TR-042 — there is no live-engine behaviour to
  match against since this feature doesn't exist there, so "correct" here means "a reasonable
  default," not "validated against a reference or owner feedback."
- **Thrusters, heat-shimmer, and docking-approach polish remain fully blocked** on Babylon
  ship-mesh loading, which is unscoped, separate work — not silently deferred, named explicitly
  here and in the delivery plan.
