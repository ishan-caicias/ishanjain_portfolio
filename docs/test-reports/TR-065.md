## Part 1 — Track A: 3 datasets wired live (2,225 new real entries)

### 1a. Base-pack minor planets (Vesta, Ceres, Pallas, Hygiea) — `celestial-minorplanets.js`

New: `scripts/gaia-minorplanet-position.mjs`. Unlike every other C1 item, these 4 bodies orbit
the Sun — a fixed catalog ra/dec (the pattern every other body in this repo uses) is wrong for
them on principle, not just imprecise. Real Keplerian elements
(`resources/gaia_datasets/default-data/orbits-asteroid.json`) are propagated to a stated epoch
(2026-07-20) via Kepler's equation (Newton-Raphson), converted heliocentric ecliptic → geocentric
equatorial via a real low-precision solar ephemeris (Meeus, _Astronomical Algorithms_ ch. 25, for
Earth's own heliocentric position) and the mean obliquity rotation, then to ra/dec/distance.
Sanity: computed distances (2.1–4.3 AU) land inside each body's real perihelion/aphelion range
once Earth's own position is accounted for. Real content authored (Dawn mission findings,
discovery history) — not `[[TODO]]` markers, since these are among the most well-documented
bodies in the solar system, unlike the bulk populations below.

### 1b. NEARGALCAT (NBG) nearby galaxies — `celestial-nbg.js`, 856 entries

New: `scripts/gaia-bulk-catalog-convert.mjs` (`convertNbg`), reading the real
`catalog-nbg/nbg/nbg.vot` via `readVotableBinary2` (confirmed BINARY2 by inspecting the file's
own `<STREAM>` tag, not assumed). **Real count discrepancy found, a THIRD number for this
dataset**: the source webpage says 869, the local `dataset.json` says `nobjects: 875` (already
flagged in `docs/datasets/README.md`'s discrepancy table, "Minor drint, use 875"), but the actual
`.vot` file's `<TABLE nrows="...">` — and the real row count this script decoded — is **856**.
Recorded here rather than silently picking one of the other two; `docs/datasets/README.md`
updated in the same turn (corrections-are-additive: the existing row's "use 875" verdict is
superseded, not edited away). Mechanical bulk conversion: every row becomes a `t: "galaxy"`
entry with real ra/dec/distance(pc→ly)/magnitude; no per-object dossier text (`[[TODO]]` marker,
same honesty convention as the deferred cluster entries).

### 1c. GD-1 stellar stream — `celestial-gd1.js`, 1,365 entries

## Part 2 — Track B: mechanism proven, not rendering-wired (2 more datasets)

Same discipline TR-063 established for the white dwarfs: real source decode → the exact shipped
15-byte record format (`star-catalog.ts`) via `writeRecordsAsPng` → a real PNG written and
readable. **Neither is wired into any render path** — that requires a second background-layer
chunk merged into the existing `CATALOG_CHUNKS`/fetch/decode path in `babylon-engine.ts` /
`space-engine.js`, real shipped assets under `public/assets/`, and (for CNS5) a tier/budget
decision, none of which is pipeline work — this is genuinely separate, larger rendering-
integration effort, the same open item TR-064 already flagged for the white dwarfs.

### 2a. CNS5 nearby stars — `scripts/gaia-cns5-pngpack.mjs`

5,930/5,931 real rows encoded (1 skipped, non-positive parallax) via the TABLEDATA reader.
Colour byte from real `bp_mag - rp_mag` (both real Gaia bands present in this catalog, unlike a
precomputed `bp_rp` column). **Real population difference from the white dwarfs, worth
recording**: only 3,103/5,371 magnitude-eligible CNS5 stars saturate the format's dimmest byte —
most CNS5 stars (58%) fall inside the format's actual naked-eye-calibrated range, unlike the
white-dwarf population where TR-063 found the entire sample saturated. CNS5 does not need the
same magnitude-remapping fix white dwarfs will.

### 2b. Oort cloud — `scripts/gaia-oortcloud-pngpack.mjs`

**Real finding that changes this sub-item's assumed scope**: verifying Astra's white-dwarf
type-byte recommendation against the actual shader (§3 below) surfaced that both shader twins
(`babylon-engine.ts`'s `ijStarFragmentShader`, GLSL and WGSL) **already reserve object-type byte
7 for "oort dust grain"** (`ty > 6.5` branch, a soft non-PSF treatment distinct from ordinary
stellar PSF). The delivery plan assumed Oort cloud needs a new GPU-instanced particle system; it
does not — the existing star-record format already has a slot built for exactly this population.
10,000/10,000 real simulated particles encoded (a THIRD local plain-text format: `X Y Z` header,
no VOTable/FITS wrapper). Source data has no per-object photometry (a position-only dynamical
simulation) — uniform dim/cool byte values used rather than fabricating variation. Units
unlabeled in the source; treated as AU, checked against real astronomy: the sample's radial
distribution (1,789–157,267 raw units) matches real Oort-cloud distance estimates (inner
Hills-cloud boundary ~2,000 AU; outer edge commonly cited 100,000–200,000 AU) closely enough to
be strong circumstantial confirmation, flagged honestly as an assumption rather than a documented
guarantee.

## Part 3 — Astra's TR-064 white-dwarf calibration recommendations, applied and verified

TR-064 recorded two Astra REALISM-AUDIT recommendations as advisory/unapplied, one explicitly
caveated as needing verification against the real shader before applying. Both applied this
session in `gaia-whitedwarf-pngpack.mjs`:

- **Colour range tightened `[-0.5, 2.0]` → `[-0.6, 1.2]`** (Astra: main-sequence-shaped range
  wastes dynamic range on a bluer, narrower real population; colour is the only surviving
  differentiator since the magnitude byte already saturates for every white dwarf, TR-063).
- **Object-type byte `1` → `0`.** Verified first, per TR-064's explicit caveat ("Astra doesn't
  have visibility into what the shader's type-byte branches on... Procyon must verify"): read
  `babylon-engine.ts`'s `ijStarFragmentShader` directly (both GLSL/WGSL twins) and confirmed
  `type=1` renders as `"cluster: soft glow, no PSF core"` — a diffuse gaussian blob, not a point
  source. The original provisional `1` would have drawn every white dwarf as an extended
  cluster-glow shape. `type=0` falls through to the shader's default stellar-PSF-plus-bloom
  branch, the physically correct treatment for a point source. This same read also surfaced the
  `type=7` "oort dust grain" branch reused in §2b.

Both changes re-run against the real 359,073-row FITS file after editing — encode still succeeds,
byte-clamping (already present in `starfield-pngpack.mjs`) absorbs any value outside the new
tighter range without new code.

## Part 4 — NGC2000 nebula wiring: a real architectural blocker, not "pure data-wiring"

The PF-10 delivery plan's C1 table describes NGC2000 as "pure data-wiring — the rendering path
already exists," reusing the existing volumetric raymarch pipeline
(`babylon-engine.ts:1172-1211`, "currently hardcoded to 4 showcase spots"). **This is not
correct as stated.** Reading `nebula-field.ts` (the actual module backing that pipeline, per
ADR-0004) before writing any code: the reveal mechanism is architecturally capped at exactly 4
volumes, not by convention but by a hard runtime throw:

```ts
const REVEAL_SWIZZLE = ["x", "y", "z", "w"] as const;
function revealComponent(i: number): string {
  const c = REVEAL_SWIZZLE[i];
  if (!c) throw new Error("uReveal carries at most 4 volumes");
  ...
}
```

Every volume's reveal state (the destination-gated fade-in/swell/fade-out amount driving how
visible a nebula is) rides in one `vec4 uReveal` uniform, one component per volume, with the
swizzle baked as a literal string per volume at shader-generation time (`nebulaGlslFragment`/
`nebulaWgslCompute`, both call `glslVolumeCalls`/`wgslVolumeCalls` which unroll one raymarch call
per `NEBULA_VOLUMES` entry with no uniform arrays — a deliberate ADR-0004 constraint: "constants
baked, not uniforms"). Expanding `NEBULA_VOLUMES` from today's 4 hand-picked showcase nebulae to
NGC2000's real 47 would hit `revealComponent`'s throw on the 5th volume and crash shader
generation outright — not a perf-degradation risk, an immediate build-time failure.

**This is real, scoped rendering-architecture work, not data-wiring**: the reveal mechanism needs
redesigning to scale past 4 volumes before any NGC2000 data can land. Because the reveal state is
inherently destination-gated (at most one nebula is ever the active travel target, plus perhaps
one fading out of a just-left destination), the natural fix is likely 2 small uniforms — an
active-volume index and its reveal amount, plus a previous-volume pair for the fade-out — rather
than continuing to unroll every volume's raymarch into the shader per frame regardless of
visibility (47 unconditional ray-sphere tests per fragment even when only one nebula could ever be
visible). This is a genuine DESIGN-then-IMPLEMENT unit of work, not attempted this session; the
delivery plan is corrected below rather than silently re-describing NGC2000 as trivial.

  with every other "real data, not simulated," but will visibly drift from the true position over
  a period of months to years, unlike a star's effectively-fixed catalog ra/dec. No re-computation
  schedule exists; flagged, not solved.
