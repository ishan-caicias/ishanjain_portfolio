## What was built

- **`scripts/lib/fits-bintable.mjs`** — a minimal FITS binary-table reader. Real finding, not
  assumed going in: the eDR3 white dwarf catalog
  (`catalog-whitedwarfs-edr3/catalog/wd/edr3/wd_edr3.fits`) is a **third** real astronomical
  binary format among this repo's local datasets (distinct from plain JSON and TR-061's VOTable
  BINARY2) — its own `particles-wd-edr3.json` is Gaia Sky app config pointing at the `.fits`
  file, same pattern as the VOTable packs. Confirmed by walking the file's actual bytes: a
  VOTable-metadata-carrying primary HDU (STIL/TOPCAT's `VOTMETA=T` convention) that must be
  skipped by its declared byte length, not parsed as more header cards, followed by the real
  `XTENSION='BINTABLE'` extension holding 359,073 rows × 111 bytes/row across 15 columns
  (name, source_id, ra, dec, parallax, pmra, pmdec, radial_velocity, Pwd, phot_g_mean_mag,
  phot_bp_mean_mag, phot_rp_mean_mag, bp_rp, bp_g, g_rp). Column-width arithmetic
  (23+8+8+8+8+8+8+4+8+8+4+4+4+4+4 = 111) verified against the header's own `NAXIS1` before
  trusting the reader on real rows — a self-check the reader throws on if TFORM parsing is wrong.
- **`scripts/lib/starfield-pngpack.mjs`** — generic PNG-pack encoder/decoder-mirror, reusing the
  **exact** byte layout `src/lib/star-catalog.ts` already decodes in production (`RECORD_BYTES =
15`: f32 x/y/z, u8 mag, u8 colour, u8 type), not a new format. The 1024px-wide, minimum-height
  packing convention was reverse-engineered from the shipped assets themselves (not assumed):
  `stars-hip.png` is 1024×576 for 117,964×15=1,769,460 bytes (12 bytes slack), `deep.png` is
  1024×249 for 50,995×15=764,925 bytes (3 bytes slack) — both match `height =
ceil(ceil(totalBytes/3)/1024)` exactly.
- **`scripts/gaia-whitedwarf-pngpack.mjs`** — CLI tying both together: real FITS rows → real
  Cartesian positions → packed PNG.

## Position convention — verified against real shipped bytes, not assumed

Decoded 8 real records straight from `assets/stars-hip.png` before writing any encoder code:
position-vector magnitude varies per star (34.8 ly to 2,399.6 ly across the sample) rather than
sitting on a fixed shell radius — i.e. the background field stores **real linear light-year
distance** (`raDecToDir(ra,dec) * distanceLy`), not the logarithmic `bodyDepth()` scale curated
destination bodies use. Distance for the white dwarfs comes from real parallax
(`ly = 1000/parallax_mas × 3.26156`), matching the standard trigonometric-parallax relation.

## Real finding: the shared magnitude byte format cannot represent white-dwarf-faint magnitudes

Every one of 5 real sample white dwarfs (G ≈ 18.4–20.2) computes a **negative** raw magnitude
byte under the shipped formula (`mag = 12.5 − byte/255×14`, calibrated for the naked-eye
Hipparcos+Gaia-deep population) — the format's floor is exactly magnitude 12.5, and these are
all fainter. All 5 clamp to byte 0, which decodes back to 12.5, not their real magnitude. This
is the format doing its documented job (clamping out-of-range input), not a pipeline defect —
Track B's scope was "follow the proven pattern exactly," which this does. **Consequence flagged
for C1, not silently absorbed:** white dwarfs sharing this byte format would render at the
format's single faintest bucket, indistinguishable from each other by brightness, unless a
future per-population magnitude remapping is designed. That's a rendering-integration decision,
not a pipeline-mechanism one. Proven both ways in the test suite: the 5 real (out-of-range)
magnitudes correctly saturate to byte 0, and a synthetic in-range magnitude (5.0) round-trips
faithfully — the arithmetic itself is correct; the real population's dynamic range is the limit.

## Proof against real data, twice

1. **In-memory round-trip through the actual shipped decoder** (`tests/unit/starfield-pngpack.test.ts`,
   6 tests, all passing): 5 real FITS rows (hardcoded as fixtures — `resources/` is gitignored,
   not present in CI, so a test reading the 40 MB FITS file directly would pass locally and fail
   everywhere else; copying real values keeps the test CI-safe without fabricating data) packed
   and decoded via `decodeStarCatalog` — the **actual production decoder**, not a mirror
   reimplementation. Positions match to 2 decimal places; the magnitude-saturation finding above
   is asserted explicitly rather than worked around.
2. **Full file-to-file run against the real 40 MB FITS file**: `node
scripts/gaia-whitedwarf-pngpack.mjs --sample 2000` decoded 2,000/359,073 real rows in 23ms,
   wrote a real PNG (`1024×10`, 30,000 bytes), which was then read back via `readPngAsRgbBytes`
   and manually spot-checked — record 0's position magnitude (1,058.5 ly) matches the
   independently-computed parallax-derived distance (1,058.9 ly, small float32-precision delta,
   expected) for the same real star.

## What Track B does NOT yet do (honest scope boundary)

- **Colour byte is a first-pass linear mapping** (`bp_rp` clamped to [-0.5, 2.0] → [0,255]), not
  calibrated against the shader's exact Planckian O→M ramp. Flagged in the encoder's own header
  comment as a C1 rendering-integration task, not reverse-engineered here.
- **Object type byte is provisional** (`1`, arbitrarily) — no type-byte legend for values 1–7 was
  found documented anywhere in the codebase; aligning it to a real shader legend is C1 work.
- **Only a 2,000-row sample was encoded**, not the full 359,073 — proving the mechanism, not
  producing the shipped asset. Streaming the full catalog (avoiding a 359,073-row in-memory
  array) is noted in the PF-10 plan as still-open for C2's much larger SDSS DR18 pass, which
  shares this same encoder.
- **Not wired into `SpaceScene`/`babylon-engine.ts` at all** — this closes C0 (pipeline
  foundation), not C1 (actually rendering white dwarfs).
