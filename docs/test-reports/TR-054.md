# TR-054 — TR-053's 3 red tests root-caused and fixed; 2 further missed cutover pins found

**Date:** 2026-07-19
**Scope:** Validate and dispose of TR-053's BLOCKED verdict. The owner's preferred option was
quarantine (`test.fixme` the 3 synthetic-tick specs). **Quarantine was not needed and would
have been wrong** — the diagnosis behind it was incorrect. Root cause found, fixed, suite green.
**Verdict: OVERALL: READY TO PROCEED** — **216/216 unit · 70/70 E2E** at `--retries=0`,
lint clean, `astro check` 0 errors / 0 warnings / 0 hints, build complete.

## Correction to TR-053 (the record, honestly)

TR-053's ruled-out list states: _"GL context loss"_ ruled out, and _"`gl` valid, `_ctxLost`
false"_. **Both are wrong.** A direct probe of the live page shows:

```
ctxLost: true          frame: 2 (frozen across all 400 synthetic ticks)
_lastT: never updated   k reached 1.0125 at f=56 yet mode stayed "aim"
```

`_frame` frozen at 2 is decisive: `_tick()` was returning at `space-engine.js:1970`
(`if (!gl || this._ctxLost) return;`) — **before** `this._frame++` on line 1971. The aim
branch on line 2031 was never reached. The math was never in question.

TR-053's conclusion — _"the harness contract is broken … the aim state machine won't advance
under manual ticking even with a +5-second timestamp"_ — described the symptom accurately and
attributed it to the wrong cause. The `+5000` probe failed for the same reason every other
tick failed: it returned at line 1970.

## Actual root cause

Headless Chromium's SwiftShader **drops and restores this page's WebGL context ~2 s into
page life**, a ~1 s outage:

```
LOST@1632   RESTORED@2642      (second run: LOST@1975  RESTORED@2997)
console: "WebGL: CONTEXT_LOST_WEBGL: loseContext: context lost"
```

Nothing in this repo calls `loseContext` (`grep` over `src/`, `tests/`, `scripts/`,
`playwright.config.ts` — no match). It is the emulator recycling the context.

**The engine handles this correctly.** `webglcontextrestored` → `_rebuildGL()` recompiles all
six programs, re-uploads buffers, and reloads the craft (`space-engine.js:1879-1965`). Probed
recovery timeline on `?craft=1k&engine=webgl`:

| t       | craftState | ctxLost  | frame |
| ------- | ---------- | -------- | ----- |
| 1758 ms | error      | **true** | 2     |
| 2822 ms | loading    | false    | 3     |
| 3877 ms | **ready**  | false    | 12    |

That recovery is why real-time journeys always passed — the wall-clock specs simply outlive
the outage. The synthetic-tick specs could not: **the loop is synchronous**, so a context lost
at loop start can never be restored inside it (restoration is delivered as a DOM event, and
the whole 400-iteration loop completes in ~50 ms of real time). The specs began ticking at
exactly the moment the context was down, every tick no-opped, the state machine froze in
`"aim"`, and they reported 0 warp samples.

Also corrected: the `[space-engine] craft model failed … craft-loader shader: ?` warning is a
_consequence_ of the lost context, not an independent defect — `getShaderInfoLog` returns null
on a lost context, which is what renders as `?`.

**So the harness contract was sound.** It carried an unstated precondition — a live GL
context — that nothing enforced.

## The fix

**1. `flight-v3.spec.ts` — make the precondition explicit (the real fix).**
`waitForLiveContext()` gates the harness on a context that has been _continuously_ healthy
across a window longer than the observed outage (any loss resets that window, so it cannot
clear mid-outage), and on the craft load having settled either way.
`waitForTickableEngine()` composes it with the existing station wait.

**2. `flight-v3.spec.ts` — fail loudly, never silently.** `flyToAbout` now returns
`ctxLostDuringRun` and `ticksApplied` (`_frame` delta), breaking the loop on any mid-run loss.
All three specs assert `ctxLostDuringRun === false` and `ticksApplied > 100`. A future
recurrence reports "the ticks never reached the render loop" instead of an inscrutable
`expected > 0, received 0`. This is the assertion whose absence cost TR-053 its session.

**No production code was changed. No assertion was weakened** — three were added.

## Known limitations

- The SwiftShader context drop is **environmental and still present** — this fix makes the
  suite robust to it rather than preventing it. It does not occur on real GPU hardware in the
  `channel: "chrome"` specs. If it ever moves later than the 25 s gate timeout, `flight-v3`
  will fail on the wait rather than mid-assertion — a clear, correct failure.
- `ticksApplied > 100` is a floor chosen to prove the loop ran, not a tuned figure.
- These specs still guard the **archived** engine's internals; the ADR-0006 archival framing
  is unchanged by this report.
- This report does **not** revisit the cutover's product deltas — those are separate and are
  registered in
  [the cutover gap analysis](../analysis/2026-07-19-webgl-babylon-cutover-gap-analysis.md),
  which remains the open item requiring owner disposition.
