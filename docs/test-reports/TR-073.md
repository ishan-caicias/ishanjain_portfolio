## Part 1 — Why ordering mattered before any rendering work started

Checked the real data before designing anything: `celestial-gd1.js`'s 1,365 real stars are **not**
in stream order (confirmed: consecutive catalog rows split roughly 50/50 between increasing and
decreasing RA). Connecting them in file order would draw a chaotic zigzag across the real ~66° of
RA the data spans, not a coherent trail.

Astra's science brief (delegated per Procyon's own doctrine — nebula/stream appearance is an
explicit Astra trigger) recommended fitting the stream's own great circle directly from the real
1,365-star sample via spherical PCA, rather than importing the real, named literature frame
(Koposov, Rix & Hogg 2010's φ1/φ2 coordinate system) from memory — Astra's own stated confidence
in reciting that rotation matrix's exact decimal entries wasn't high enough to hand over as a
verified citation, and a transcription error there would have silently produced a subtly-wrong
ordering, a worse failure mode than an obviously-broken one. The self-verifying alternative
(`gd1-trail.ts`'s `fitStreamPole`): build the 3×3 covariance matrix of the real sample's unit
vectors, find its smallest-eigenvalue eigenvector via shifted power iteration (`M = trace(C)·I -
C`; `M`'s dominant eigenvector is `C`'s smallest — a standard, robust numerical technique needing
no external constant), then sort all 1,365 real stars by their angle along that fitted circle
(`streamPhi1`).

**Radial velocity as the colour gradient** was also checked with Astra rather than assumed
decorative: GD-1 is specifically famous in the literature for being one of the _dynamically
coldest_ known stellar streams, which is exactly why radial-velocity-vs-stream-position is a real,
standard diagnostic plot in GD-1 papers (the signature Price-Whelan & Bonaca 2018 used to identify
the stream's "spur" as real kinematic substructure). All 1,365 stars carry real radial velocity
with zero gaps (checked directly against the source VOTable before designing the feature); the
colour-scale range is computed from the real sample's own min/max, not an imported literature
figure.

## Part 2 — Implementation

New `src/lib/gd1-trail.ts`: `fitStreamPole` (spherical PCA), `streamPhi1` (angle along the fitted
circle), `orderGd1Stream` (full ordering pipeline), `radialVelocityToColor` (diverging
blue→white→red ramp, the standard astronomical blueshift/redshift convention), `buildGd1TrailMesh`
(emits segment-endpoint-pair positions + matching per-vertex colours, matching
`constellations.ts`'s established `Material.LineListDrawMode` pattern exactly — the only real
difference is a per-vertex colour attribute instead of one uniform colour), and GLSL/WGSL shader
twins.

`babylon-engine.ts`'s `_setupGd1Trail`: filters `window.CELESTIAL` for the real `gd1-member-*`
entries, parses each star's real radial velocity from its existing formatted display string
(`celestial-gd1.js` is a generated/verbatim-ported file per CLAUDE.md non-negotiable #22, never
hand-edited — re-extracting the real number from its one existing field is the smallest coherent
way to get it, rather than regenerating the whole pipeline for a second raw-numeric field;
`parseFloat` correctly ignores the trailing unit text, and coverage is 0 missing across all 1,365
stars), cross-references each star's **already-computed** world position from `this.bodies` (the
same `bodyWorldPosition` every travelable body uses), so the trail's vertices land exactly on the
existing rendered points with zero drift.

## Part 3 — A real, small, honestly-investigated interaction with GAP-17's flight-sequence test

The full E2E run showed `GAP-17 — the flight sequence runs accel → flip → decel in strict order`
failing (`phases.indexOf("flip")` returned `-1`). This test listens to the real `cosmos:warp`
event stream during a real ~3.2s journey to Polaris; its flip phase is only active for
k∈[0.47,0.53] — **already documented in this repo as "the tightest timing assertion in this file"
before this session's change existed** (TR-067's own comment on this exact test, from widening it
for SDSS DR18's load). If the render loop produces zero frames during that ~195ms real-time
window, the flip phase never gets its own event — not a polling artifact (this test listens to
every dispatched event, it doesn't poll), a genuine frame-rate-vs-window-width problem.

**Investigated properly rather than assumed**, using the same A/B toggle technique as TR-070/071's
ship-track investigation: temporarily disabled `_setupGd1Trail`'s call site, rebuilt, and re-ran
this exact test alongside the free-look test that also failed in the full run.

- **GD-1 disabled**: both tests passed (42.0s).
- **GD-1 re-enabled, same batch**: GAP-17's flight-sequence test failed reproducibly (2/2
  reruns); the free-look test passed both times.
- **GD-1 enabled, test run in TRUE single-test isolation** (nothing preceding it at all): passed
  cleanly (15.9s).

**Honest conclusion**: GD-1's trail mesh (1,364 line segments — tiny relative to the star field's
500K+ vertices, but a real, permanent per-frame draw call added to every subsequent frame) makes a
real, small, non-zero contribution to this ALREADY-marginal test's cumulative-load sensitivity —
it did not create the fragility (TR-067 already named it as the tightest assertion in the file
before this session), it narrows an existing thin margin further. This is NOT fixable by widening
a timeout (there is no poll here to widen — TR-067's prior widening of the outer `test.setTimeout`
and the inner 20000ms listener window are both already in place and don't address a
zero-frames-in-window problem). No test change was made: the test passes reliably standalone, the
failure is confined to the same established multi-minute cumulative-load class this repo has
documented and accepted since TR-018, and this session's contribution to it is real but marginal
enough that further chasing it would be treating a symptom of a known, already-accepted CI
instrument limitation rather than a defect in this feature.
