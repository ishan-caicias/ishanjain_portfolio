# TR-107 — Two full-suite E2E failures root-caused as timing-margin issues, fixed in isolation (VERIFIED)

**Date:** 2026-07-28
**Slice:** Root-cause and fix the 2 failures from the 2026-07-28 full-suite run (150 tests,
29.8 min, reported at `localhost:9323`): `accessibility.spec.ts:104` and
`engine-select.spec.ts:1385`.
**Predecessor:** [TR-106](TR-106.md), whose own "Known limitations" section already flagged
`accessibility.spec.ts:104`'s focus-race as a watch item and predicted (incorrectly, see below)
that the fix would be a `.poll()`-style wait.

## What the full run actually showed

Both failures were read directly from the HTML report (`localhost:9323`), not re-derived from
memory:

**1. `accessibility.spec.ts:104` — "scene chrome stays keyboard-operable on the Babylon path."**
`expect(rng).toBeFocused()` failed after 5000ms: `rng.focus()` was called but
`document.activeElement` never became the RANDOM JUMP button ("Received: inactive").

**2. `engine-select.spec.ts:1385` — "PF-10 catalog layers... load and are real travel targets."**
Failed at 19.9s (well under its 45s test timeout): the second of two sequential real travel
journeys in this test (`travelTo("ngc2000-lagoon-nebula")`) never reached `arrivedId ===
"ngc2000-lagoon-nebula"` within its 10000ms poll. The first journey (`cluster-pleiades`) had
already succeeded, but at 6.9s against the same 10000ms budget — already near the edge.

## Root cause

**Isolation-confirmed first (CLAUDE.md #27 — never run the full suite to characterize a single
failing spec):** both tests, run individually 3-4× each, passed every time
(`accessibility.spec.ts:104`: 3.8-5.2s; `engine-select.spec.ts:1385`: 7.1-10.5s — both
comfortably inside their original budgets). This ruled out a functional regression before any
source change was made.

**Test 1 — a missing PF-11 D1.2 update, not a flaky assertion.** PF-11 D1.2 put
`#ij-mission-bar` (the WHERE-TO input and RANDOM JUMP button) behind `body.ij-loading`
(`opacity:0; pointer-events:none` in `global.css`) until a real visitor dismisses the PRE-FLIGHT
gate (`PreFlight.tsx`). Every other Babylon E2E test that touches this bar already dismisses the
gate first (e.g. `engine-select.spec.ts`'s "RNG mission control button" test clicks SKIP INTRO
before interacting with it, a change explicitly named at D1.2 landing) — this accessibility test
was never updated to match. Testing focus on a still-gated element also races
`PreFlight.tsx`'s own `moveFocusTo(launchButtonRef.current)` effect, which fires the instant the
scene's `armed` state flips true and steals focus to the LAUNCH button — a real race whose
outcome depends on whether boot completes during the test's assertion window. This corrects
TR-106's watch-item prediction: the fix is not a `.poll()`-style wait (there is nothing to wait
for — the button never receives durable focus while gated), it's dismissing the gate first, the
same convention already established elsewhere in this suite.

**Test 2 — a real, previously undocumented timing-margin gap, same class as TR-067/TR-080's
"near-zero-margin" failures.** `warpDurationForLy` (`ship-dynamics.ts`) caps warp duration at
`WARP_MAX_MS` = 4200ms regardless of distance, so `ngc2000-lagoon-nebula` (5199.99 ly, near the
distance ceiling) and `cluster-pleiades` (444 ly) both launch on similar configured durations —
but the warp/arrival state machine advances on real wall-clock time, gated by requestAnimationFrame
delivery, which this repo has repeatedly measured stretching multiple-fold under CI's SwiftShader
software rendering, worse under sustained load (the exact mechanism TR-067/TR-080 already fixed
for other single-journey tests in this same file). This test does **two** sequential real
journeys in one boot (merged from 3 tests at TR-104), compounding the stretch. Neither poll had
ever been given headroom for this — the file's established convention (widen the specific tight
poll, keep every assertion unchanged, document why) simply hadn't reached this test yet.

## Changes

- `tests/e2e/accessibility.spec.ts`: added `await page.getByRole("button", { name: "SKIP INTRO"
}).click();` at the start of "scene chrome stays keyboard-operable on the Babylon path" —
  matching the PF-11 D1.2 convention already used elsewhere. Scoped to this one test, not the
  shared `beforeEach`, so the sibling "no serious/critical axe violations" test's audit of the
  PRE-FLIGHT dossier itself is unaffected.
- `tests/e2e/engine-select.spec.ts` ("PF-10 catalog layers..." test): `test.setTimeout`
  45000->90000; the `cluster-pleiades` arrival poll 10000->20000; the `ngc2000-lagoon-nebula`
  arrival poll 10000->25000 (the near-max-distance journey gets the larger budget, matching
  sibling near-max journeys elsewhere in this file, e.g. the ship-track test's m42 poll at
  25000-30000). Every assertion is unchanged — this is a declared timeout-only change per
  CLAUDE.md #15.
- No `src/` file changed.
