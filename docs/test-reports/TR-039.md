# TR-039 — Correction: the WGSL twin CAN be validated on real WebGPU hardware in Playwright

**Date:** 2026-07-19
**Scope:** Owner pushback on TR-038's honest-limits section: _"Playwright chromium supports WebGPU
out of the box. You just need [an] enable flag in the settings[.]js."_ Revalidated empirically
rather than argued from memory.
**Verdict: OVERALL: READY TO PROCEED** — the record is corrected, a new real-hardware E2E test is
added and passes, and one prior claim was worse than imprecise: it contradicted already-recorded
project state I should have cross-checked.

## Two separate errors, not one

**Error 1 — imprecise, in TR-038.** "Playwright's chromium has no WebGPU adapter" was stated as a
flat fact. Empirically retested (see Method below) across the bundled Playwright Testing-build
Chromium and the real installed system Chrome, on `about:blank`, `https://example.com`, and
`http://localhost:4321`, headless and headed, with five flag combinations. The precise picture:

| Binary                                                              | `navigator.gpu` exists              | `requestAdapter()` returns real adapter           |
| ------------------------------------------------------------------- | ----------------------------------- | ------------------------------------------------- |
| Bundled Playwright chromium, **insecure** context (`about:blank`)   | ❌ (spec requires a secure context) | n/a                                               |
| Bundled Playwright chromium, **secure** context (https / localhost) | ✅                                  | ❌ — null under every flag tried                  |
| Real system Chrome via `channel: "chrome"`, secure context          | ✅                                  | ✅ — real AMD/NVIDIA adapter, **no flags needed** |

So: not "no WebGPU adapter, full stop." The bundled Testing-build binary genuinely can't get one;
pointing Playwright at the real installed browser does, immediately, with zero configuration.

**Error 2 — worse, in TR-038.** "The WGSL twin is still unvalidated on real WebGPU hardware...
unchanged from B2 step 1" **directly contradicted [ADR-0003](../adr/0003-babylon-webgpu-renderer-adoption.md)
condition 2**, already marked ✅ DISCHARGED on 2026-07-19 — the owner read `BABYLON WEBGPU` on a
physical Android **before B2 step 2 even started**. I wrote a stale claim into a new report without
cross-checking the ADR that already settled it. The delivery plan's own header line said as much
("mobile condition DISCHARGED 2026-07-19") and I did not connect it.

**Correct statement:** the WGSL twin has been proven on real hardware (physical Android, owner-run,
2026-07-19, ADR-0003 condition 2). What was actually true and narrower — CI specifically cannot
exercise it, because Playwright's bundled Chromium has no real adapter — is a CI-tooling gap, not a
hardware-validation gap. TR-038's "honest limit" conflated the two.

## Method — what was actually tried, so this doesn't need re-litigating

Five configurations of the **bundled** Chromium (chromium-1228, reports as Chrome/149 internally),
headless and headed, on a secure-context page:

1. no flags
2. `--enable-unsafe-webgpu`
3. `--use-angle=swiftshader --enable-unsafe-swiftshader`
4. `--enable-unsafe-webgpu --use-webgpu-adapter=swiftshader`
5. `--use-gl=angle --use-angle=vulkan --enable-features=Vulkan`

All five: `requestAdapter()` → `null`. Also checked `chrome://gpu` via a CDP
`SystemInfo.getInfo` call (not innerText — that page is a Polymer shadow-DOM app and reads empty),
which reported `"webgpu": "enabled"` at the browser feature-flag level with real GPUs enumerated
(AMD Radeon, NVIDIA RTX 3070) — so the **binary** believes WebGPU is on; it is the **Testing-build
Chromium's** ability to hand out a real adapter that fails, independent of flags.

Then `chromium.launch({ channel: "chrome" })` — the already-installed system Chrome (v150), zero
extra flags: `requestAdapter()` → a real AMD adapter, immediately, on both `https://example.com`
and `http://localhost:4321`.

## What shipped

New [tests/e2e/webgpu-hardware.spec.ts](../../tests/e2e/webgpu-hardware.spec.ts). Deliberately:

- **Not** the default Playwright project — `playwright.config.ts` is untouched. The test manually
  launches its own `chromium.launch({ channel: "chrome" })` instance rather than using the
  `page`/`browser` fixtures, so it doesn't affect any other spec's configuration.
- **Not** added to the CI workflow. CI runs on GitHub's `ubuntu-latest`, which has no GPU hardware
  and only installs the bundled `chromium` (not the `chrome` channel) — see
  `.github/workflows/*.yml`. Installing real Chrome there would be speculative cost with no
  evidence it would produce an adapter on a GPU-less runner. Flagged here as a deliberate scope
  boundary, not a silent omission.
- **Fails open.** If `channel: "chrome"` can't launch, or launches but returns no real adapter, the
  test calls `test.skip(true, reason)` rather than going red — this is an environment-capability
  probe, not a regression gate. Confirmed via the exhaustive bundled-Chromium sweep above that the
  "no real adapter" branch's underlying condition is real and reachable (it's what CI will hit).

The test asserts `sceneStats()` from the running `<babylon-scene>` — the same tested, existing
diagnostic surface, not a new pixel-sampling path — for `backend === "webgpu"`,
`materialReady === true`, and the B2-step-2 catalog identity (`starSource === "catalog"`,
`starCount === 168959`). This is **ADR-0003 condition 2's exact assertion**, run as an automatable
(if non-continuous) check instead of a one-off manual badge read.

A race identical to TR-038's (`<babylon-scene>` mounts before the async boot resolves) hit this
test on the first run — `stats.backend` was read before `_boot()`'s sequential awaits reached it.
Fixed the same way: poll on `starSource` (which resolves after `backend` in the boot sequence, so
polling on it guarantees both are set) instead of reading once.
