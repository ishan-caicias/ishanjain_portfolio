# TR-032 — Gate Instrument Defect: fps Measured Host rAF, Not Engine Renders

**Date:** 2026-07-18
**Scope:** Owner submitted the first round of PF-09 B1 gate readings. Reviewing them before
rendering the go/no-go revealed that **the measurement instrument could not produce a valid
reading** — a defect in my own harness, not in the owner's method.
**Verdict: OVERALL: READY TO PROCEED** (instrument fixed and verified) — **but the B1 gate
remains GATED; Round 1 data is void and must be re-measured.**

## Why the submitted data could not decide the gate

| #   | Problem                                                                                           | Evidence                                                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **`fps` counted host `requestAnimationFrame` ticks, not engine renders** — structural over-report | Measured on the production build: **139 host ticks vs 82 real renders** (~1.7×), and 130 vs 73 in a second run                                                                              |
| 2   | **140 fps reported on an iPhone is physically impossible** — rAF is vsync-locked                  | iPhone panels are 60 Hz, or 120 Hz ProMotion; both below 140                                                                                                                                |
| 3   | **20–39 ms startup impossible for the current engine**                                            | `cosmos:ready` waits for the star stream: 168,959 stars ÷ 8,000-star chunks × `setTimeout(…,16)` = **≥350 ms of timers alone**, before 2.9 MB of PNG fetch/decode. CI measures ~840–1270 ms |
| 4   | Near-identical readings across desktop / iPhone / mid-Android                                     | Not how heterogeneous hardware behaves — consistent with the instrument reporting page cadence rather than per-device render cost                                                           |

Root cause is mine: the harness sampled the host rAF loop, which keeps ticking at panel rate
regardless of whether the engine drew anything, and the snapshot recorded neither the display
refresh ceiling nor which device produced it — so a reading was neither interpretable nor
attributable. I noticed this weakness while debugging B1 and did not act on it.

## Instrument v2

[perf-telemetry.ts](../../src/lib/perf-telemetry.ts) now records:

- **`renderFps` — the gate metric.** Derived from the engine's own frame counter over a 2 s
  trailing window (`space-engine._frame`, `babylon-scene.renderFrames`). This is what the engine
  actually drew.
- **`displayHz`** — estimated from the fastest observed frame. `fps` can never exceed it, so an
  impossible reading is self-evident.
- **`renderFrames`** — 0/null proves the scene is _not_ drawing even when fps looks healthy.
- **`device`** — UA, DPR, cores, memory, screen and viewport, making every gate row attributable.

The `?perf=1` overlay now marks the field to record explicitly:

```
ENGINE webgl · TIER high
STARTUP 2626ms
▶ RENDER FPS 13   ← RECORD THIS
   host rAF 13 / 208Hz
   rendered 90
```

**Correction (same day).** An earlier revision of this report claimed the overlay already showed
`RENDER FPS`. It did not — the edit that was supposed to replace the old host-rAF `FPS` line
failed silently (string-escaping mismatch in a scripted patch) and was not verified, so the
overlay kept displaying the very number this report declares invalid. Caught only when the owner
asked which of the three visible fields to record. Fixed, and the rendered output above is
verified in a real browser, not assumed. Lesson: verify a patch landed in the file **and** in the
rendered output — a scripted string replace that silently no-ops is indistinguishable from success
in the build log.

| Unit         | **91/91** (+5: displayHz from a 60 Hz vs 144 Hz cadence, device context + render counter, `renderFps` isolating a 30 fps engine under a 120 Hz host loop, null-until-two-samples)                                                                                                                                                                           |
| E2E          | **52/52** on the final run. Honest note: three consecutive full runs gave 51/52, 51/52, **52/52**, with two _different_ single failures (`?engine=babylon … reports babylon`, then `accessibility › heading hierarchy`) — each passing 4/4 and 5/5 in isolation. | Build · lint | Exit 0 · 0 errors                                                                                                                                                                                                                                                                                                                                           |

(Headless SwiftShader numbers remain non-representative — they demonstrate the instrument, not
device performance.)

## Consequence for B1

**The gate stays `gated`.** Round 1 is preserved in the
[gate procedure](../validation-checklist/2026-07-18-pf09-b1-gate-measurement.md) marked VOID with
reasons, and a Round 2 table with the v2 columns replaces it. No ADR is written; ADR-0002 stands.

Rejection rules now stated in the procedure: reject any row where `renderFps > displayHz`,
`renderFrames` is 0/null, `startupMs < 300` for the current engine (warm page), or the `device`
block repeats across rows claiming different hardware.

## Follow-up raised (not fixed here)

Reviewing my own change caught a self-inflicted inefficiency: `readEngineFrames()` initially ran
`document.querySelector` **every animation frame** — avoidable per-frame cost inside the very loop
being measured. Now caches the element (re-queried only when disconnected).

The residual E2E flakiness under 4 parallel WebGL workers is a standing issue (first documented in
TR-025). It is not blocking, but the suite would be more trustworthy with WebGL-heavy specs
serialised (a `fullyParallel: false` project, or a worker cap for those files) — worth doing
before CI enforces perf budgets in B6.

## Process note

The owner's readings were taken in good faith against the instrument I supplied; the failure is
the instrument's. Worth keeping as a reminder that a measurement harness needs its own validity
checks before it is trusted to decide an architectural gate — "looks consistent" across
heterogeneous hardware is a warning sign, not a reassurance.
