## Why this exists

TR-108/TR-109 shipped Phases D5 and D6 green. A subsequent REVIEW pass over the same working
tree found ten defects — one user-visible, four affecting allocation/idempotency, five hygiene
and rule-consistency. This TR records fixing all ten. Its central finding, stated plainly
because it drove the fix ordering: **the D5 UI slice was measurably less rigorous than the D6
engine slice** — D6.2 got a mid-implementation bug caught, a cross-module constant test and an
Astra audit, while D5.2 shipped ~60 lines of stateful keyboard/ARIA logic with zero unit tests
and a reachable dead state.

## Fixes, in the order they were applied

### HIGH

**1 — Escape then keep typing left the search box dead.**
`MissionControlBar.tsx` set `open` on focus and on Arrow Up/Down, never on `onChange`. Escape
closes the list without moving focus, so a visitor who pressed Escape and kept typing got no
suggestions until they blurred and refocused. Reproduced with a throwaway RTL test during the
review (`listbox after Escape+type: STILL CLOSED`) before any fix was written. `onChange` now
opens the list. **Not caught by any of D5.2's six E2E specs** — none of them types after an
Escape.

### MEDIUM

**2 — `nearestOfType` allocated an object per record, and its own doc denied it.**
`star-catalog.ts`'s doc comment claimed "a typed-array scan with no per-iteration allocation";
the loop destructured `unpackTypeAndColour`, which returns a fresh `{ type, colour }` every
record. Over the loaded field × one call per class row, that is millions of short-lived objects
per cold camera epoch. The type byte is the integer part of the packed float, so `Math.floor`
reads it directly and the unused colour half is never computed. **The claim is now true.** A new
test pins `Math.floor(packed) === unpackTypeAndColour(packed).type` across the whole 8×256
type/colour domain — including the ciByte-255 boundary that `CI_PACK_DIV`'s "divide by 256, not
255" comment exists for — plus an end-to-end scan at that boundary.

**3 — D6.2 put allocation back in the render loop.**
`toBeltSpace`/`fromBeltSpace` return fresh tuples. `beltPullAccel` went from 1 to 2 arrays per
call and runs once per rock per frame in both the kinematic (`visualDriftStep`) and Havok
(`babylon-engine.ts`) loops; `beltDensityAt` went from **zero** allocation to one per call and
runs up to 26× per frame during warp (point sample + `minSlowAlongSegment`). Against CLAUDE.md's
"no per-frame allocation in the render loop", and introduced by a slice whose stated cost was
"the same math in a different basis".

The six multiply-adds are now inlined in both functions. New `beltPullAccelInto(px, py, pz, out)`
writes into a caller-owned array — `visualDriftStep` uses a module scratch, the engine's Havok
loop a new `_beltPullScratch` field, so **both hot loops now allocate nothing per rock**.
`beltPullAccel` keeps its original tuple signature as the pure tested API and delegates.
Duplicated math is only safe if pinned, so three tests do that: the inlined rotation is checked
against `toBeltSpace`/`fromBeltSpace` composed by hand (4 probes incl. the degenerate on-axis
case, 12 decimals), the tuple and scratch forms are checked bit-for-bit, and `beltDensityAt`'s
inline is checked against the helper the same way.

_Honest scope note:_ `passageDeflectForce`, in the same Havok loop, also returns a tuple per
rock per frame. That is **pre-existing** (PF-09 B4), not introduced by D6.2, and was left alone
rather than widened into this pass — recorded as a follow-up below.

**4 — `getFeaturedSuggestions()` ran on every SpaceScene render.**
`featuredEntries` builds a lookup map over the whole ~4,834-entry index to resolve six
hard-coded ids, and it was called unconditionally from the render body at the ~7.5 renders/s
idle rate this file's own comment documents — even with the console never focused. Its two
siblings both short-circuit on `if (!cmd.trim())` with a comment explaining exactly why; the
featured path missed that guard. Now resolved once inside `getSearchState()`'s existing cache
(invalidated on catalog growth, which is the only thing that can change the answer), which also
hands `MissionControlBar` a **stable array reference** across renders. `featuredEntries`'
doc now states it is index-lifetime work, not per-render work.

**5 — `patch-atlas.mjs` default mode generation-lossed the whole atlas.**
Compositing forces a full 4096×4096 re-encode, and default mode called `apply(PATCHES)`
unconditionally — writing even when `toAdd` was empty. A second `npm run assets:atlas` therefore
re-encoded an already-lossy JPEG, degrading all ~260 already-shipped cells and churning the
committed binary. The mode a human is most likely to type by hand was the destructive one.

Default mode now applies only genuinely-stale patches (missing atlas-map entry, **or** a source
image newer than the atlas), and a new `--force` keeps the full-re-encode escape hatch while
warning at the console what it costs. New exported `stalePatches()` makes the decision testable
without touching image files; 4 tests cover it, including that a missing atlas or unreadable
source reads as "not newer" rather than silently reinstating the unconditional re-encode.
**Verified live:** `node scripts/patch-atlas.mjs` on the committed tree now prints _"nothing to
do"_ and writes nothing.

### LOW

**6 — `celestial-catalog.js` was hand-edited against CLAUDE.md #22; D5.4 used an overlay for the
same class of change.** Rule and practice had diverged in the same session — itself the drift
class this repo treats as a defect. Resolved by **correcting the rule, not the code**, because
the rule was factually wrong: `src/data/celestial/*.js` is hand-curated data ported from the
PF-07 prototype, **not machine output**. Nothing regenerates it, so "never hand-edited" was never
enforceable and a wrong RA/Dec had nowhere to be fixed. CLAUDE.md #22 now separates the two
cases and states enforceable rules instead: additive changes go through an overlay module
(`celestial-missing-moons.js` / `celestial-saturn-moons.js` / `celestial-content-overlay.js`
are the precedents); a direct edit to a base port is allowed **only** to correct factually wrong
data, must be the minimal field change, and must be named in a TR with its source. The
now-inaccurate "kept byte-identical to their prototype source" claims in `.prettierignore` and
`eslint.config.js` were corrected in place with dated pointers rather than deleted.

**7 — `MissionControlBar.tsx` had no unit test.** New `tests/unit/mission-control-bar.test.tsx`,
**10 tests** driving the real component through real DOM events: the finding-1 regression,
featured-on-focus/hide-on-blur, the NO CONTACT state, Enter-with-no-arrow → top-ranked,
ArrowDown → that option, ArrowUp wraparound, fresh-keystroke re-tops the highlight,
`aria-expanded`/`aria-controls` resolution, `aria-activedescendant` ↔ `aria-selected` agreement,
and the honest-truncation line's threshold. _Discovered while writing it:_ `vitest.config.ts`
sets `globals: false`, so RTL's auto-cleanup never registers — the file calls `afterEach(cleanup)`
explicitly and says why. (`MissionControl.test.tsx` sidesteps this by only querying its own
`container`; role-based queries cannot.)

**8 — `search()` and `totalMatches()` each ran an independent full scan**, and SpaceScene called
both from the render body (plus a third from the funnel keystroke record) — with a ~4,841-entry
`withClassEntries` spread in front of each. New `searchWithTotal()` returns both from one
ranking pass; the two single-purpose functions stay as the narrow public API. **The honest-
truncation guarantee is unchanged and explicitly re-tested**: `total` is still the length of the
UNCAPPED ranking, never derived from the capped list — the original rationale was right that the
count must not come from a capped list, but it never required a second _scan_. Two tests: one
proving observational identity with `search()`/`totalMatches()` across 6 queries × 3 limits, one
proving `total` stays uncapped.

**9 — one measured number, two values.** Aldebaran's peak belt density was `~0.97` in
`babylon-asteroids.ts` and `engine-select.spec.ts`, `~0.96` in TR-109, the delivery plan, and the
realism review. **Re-measured rather than picked**: swept `beltDensityAt` along each
destination's origin ray at 0.05-unit steps — **Aldebaran 0.9639 at r ≈ 165; m42 0.0002**. The
docs' 0.96 was correct. Source comments corrected to the measured figures (m42's is 0.0002, not
the recorded ~0.0001 — a second, smaller re-measurement, recorded here rather than changed
silently). Both figures are now **pinned by a unit test** so they cannot drift again, and that
test doubles as a guard that a future `ASTEROID_BELT` change hasn't quietly restored the m42
crossing D6.2 retired (which would mean the belt had drifted back off the real ecliptic).

**10 — `.claude-flow/` was prettier-ignored but not git-ignored.** It sat permanently in
`git status`, one `git add -A` from being committed. Added to `.gitignore` with the reason
(`.prettierignore` stops it being _formatted_, not _committed_).
