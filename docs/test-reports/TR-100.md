## 1. `isFarField` fix (SpaceScene.tsx)

**Root cause:** `isFarField(id)` (SpaceScene.tsx) drove the HUD's `LOCAL FIELD BELOW
RESOLUTION · MILKY WAY ASTERN` line off `catalog().find((e) => e.id === id)?.ly` —
i.e. a lookup against `window.CELESTIAL` only. Field objects (`fs-N` ids, synthesized on demand
by `entryForFieldStar` from the engine's live `fieldInfo()`) are **never written into
`window.CELESTIAL`** — they're constructed fresh per-call by `entryFor()`'s `fs-` fallback
branch, which `isFarField` didn't use. So for any `fs-` arrival, the catalog lookup always
missed, `?? 0` defaulted the distance to zero, and the far-field HUD line could never fire —
regardless of the object's real distance.

**Why "unreachable" until now:** before D4.2 (TR-099), Babylon's `travelTo` had no `fs-` branch
at all, so `state.arrivedId` could never actually hold an `fs-` id on the shipping engine — the
bug existed in the code but no live arrival could ever exercise it. D4.2 shipped field-object
arrival on 2026-07-25 (same day), making this immediately reachable: PF-10's SDSS DR18 field
layer places real galaxies at comoving distances of **32.6M–28.86B ly** (per `babylon-engine.ts`'s
own `_loadSdssGalaxyLayer` comment), thousands of times past the `EXTRAGALACTIC_LY` (1e6)
threshold — exactly the "scale honesty" signal PF-11 exists to get right, silently absent for
every field-object arrival.

**Fix:** `isFarField` now reads `entryFor(id)?.ly` instead of `catalog().find(...)?.ly`.
`entryFor()` (already used by hover/vista/card resolution) already has the correct fallback —
catalog lookup first, then the `fs-` branch via the live engine's `fieldInfo()` — so this closes
the gap by reusing an existing, already-exercised code path rather than adding new logic. No
regression risk for catalog ids: `entryFor`'s catalog branch is byte-for-byte the same lookup
`isFarField` used before.

**New E2E coverage** (`tests/e2e/field-travel.spec.ts`, +1 test): scans the live field for one
record past `EXTRAGALACTIC_LY` and one under it (after waiting for the async bonus-layer merge,
same pattern the file's existing log-depth test uses), travels to the near one first and
asserts the HUD line is **absent** (the control — proves the assertion isn't tautological),
then travels to the far one and asserts the HUD line **is visible**. Isolated 4/4 clean across
two runs (`--repeat-each=2`) before the full gate.

## 2. D4.4 batch 2 — NGC2000 content (drafted, staged unwired)

Five parallel research passes (one per ~8 objects) confirmed every object's real-world identity
via live search before drafting — not trusting supplied guesses blindly — and grounded every
claim in a source found this session, following the exact rule batch 1 used (no fact from
memory alone). New override-only `celestial-content-overlay-ngc2000.js` (mirrors
`celestial-content-overlay.js`'s pattern exactly — CLAUDE.md #22, never hand-edits the generated
`celestial-ngc2000.js`), covering all 41 ids that carried the `[[TODO: content pass...]]`
placeholder (verified exhaustive: overlay's 41 keys match the catalog's 41 flagged ids 1:1, no
gaps, no extras). Full per-object source list:
[docs/analysis/2026-07-25-ngc2000-card-content-sources.md](../analysis/2026-07-25-ngc2000-card-content-sources.md).

**Deliberately staged UNWIRED** — built and unit-tested (`celestial-content-overlay-ngc2000.test.ts`,
6 tests, mirrors the batch-1 test file) but **not** added to `SpaceScene.tsx`'s import chain.
Batch 1's own overlay module is already live in that chain (approved and shipped in TR-099), so
adding batch-2 entries directly into that file would have shipped them without a separate
approval gate — a new sibling module was the only way to preserve "stage unwired until
approved" for this batch specifically. Wiring is the same one-line `.then()` addition, once
approved.

**Two real data-quality findings surfaced during research** (flagged in the source-list doc,
NOT fixed — `celestial-ngc2000.js` is generated/pipeline output, out of scope for a
content-only overlay):

1. **`ngc2000-crescent-nebula`'s own `ly` field (5, ~1.5 pc) is very likely a data-pipeline
   error** — the real Crescent Nebula (NGC 6888) is ~4,700–5,200 ly away, roughly three orders
   of magnitude off. The authored text never states a distance figure for this id specifically
   so the anomaly can't leak into shipped copy — unit-tested directly (a new assertion checks
   the authored `f`/`lo` text never contains a "5 ly"-shaped claim).
2. **`ngc2000-butterfly-nebula` and `ngc2000-bug-nebula` looked like a pipeline duplicate
   mid-research (same nickname, different catalog distances) but are two genuinely different
   real objects.** Resolved by checking each record's own `ra`/`dec`/`ly` fields directly
   (`ngc2000-bug-nebula`'s `d` field explicitly reads `"NGC 6302 · nebula"` and its coordinates
   match; `ngc2000-butterfly-nebula`'s coordinates match Minkowski 2-9 / M2-9, confirmed via a
   live search this session against M2-9's published ~2,100 ly distance, matching this record's
   `ly:2100` almost exactly). Content was drafted for the object each id's own data actually
   points to, not for the shared nickname. A related naming collision
   (`ngc2000-box-nebula`/`ngc2000-little-gem-nebula` both informally nicknamed "Box Nebula") was
   resolved the same way and is recorded in the source-list doc.

cleanly). Console stayed clean throughout (`BJS - Babylon.js v8.56.2 - WebGPU1 engine`, zero
errors) — the one class of check the pane CAN still confirm regardless of frame compositing.

**What still needs the owner's own eyes:** does the `MILKY WAY ASTERN` HUD line read correctly
