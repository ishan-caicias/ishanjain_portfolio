# TR-041 — PF-09 B2 step 4: chase camera, launch-at-click, arrival framing

**Date:** 2026-07-19
**Scope:** PF-09 B2 step 4 of 6 — "the PF-08 choreography." Replaces step 3's damped-spring
position stand-in with the live engine's actual eased path + behind-the-thruster waypoint chase
offset, adds a launch-at-click turn preview, and lets arrival framing fall out of the chase-look
damping rather than requiring separate code.
**Verdict: OVERALL: READY TO PROCEED** — 116/116 unit · 56/56 E2E · build/lint exit 0.

## What changed from step 3

Step 3 ([TR-040](TR-040.md)) deliberately used a damped spring toward the target as an
intermediate stand-in — the plan's own step 3 wording named "damped spring + quaternion slerp"
specifically, with the real choreography named as step 4's job. This step supersedes that stand-in
entirely; the spring state and its imports are removed, not left dead.

| Aspect       | Step 3 (spring stand-in)                 | Step 4 (PF-08 choreography)                                                 |
| ------------ | ---------------------------------------- | --------------------------------------------------------------------------- |
| Position     | 3-axis damped spring toward `to`         | Fixed-duration eased path (`warpEase`) + waypoint chase offset              |
| Progress `t` | Distance-based approximation             | Real elapsed-time fraction — matches the live engine's own semantics        |
| Orientation  | Slerp straight along travel direction    | Slerp toward a look-AHEAD point past the "ship" (`CHASE_LOOK_AHEAD`)        |
| Arrival      | Distance/velocity threshold (asymptotic) | Exact — `cam(1) = to` algebraically, by waypoint-table construction         |
| HUD readout  | None (no `phase`/`vC` in the payload)    | Full accel/flip/decel + apparent-velocity readout, matching the live engine |
| Durations    | `AIM_DUR_MS=350` (placeholder)           | `900`/`2400` — the live engine's own non-reduced values                     |

## The "no ship mesh" adaptation, stated explicitly

The live engine's chase camera trails a separate ship SPRITE; Babylon has no ship mesh on this
path yet (craft loading is a different track). So the camera itself plays the "ship" role: a
virtual ship position is computed each frame (`shipW = from + (to-from)·warpEase(k) + dir·SHIP_VIEW_DEPTH`)
and the camera trails it at the waypoint offset — same math, no visible ship required. This was
named explicitly in [TR-040](TR-040.md) as the framing to carry forward, and it's carried forward
here rather than re-derived.

## The arrival-position invariant, proven not asserted

`chaseOffsetAt(0)` and `chaseOffsetAt(1)` both equal `[0, 0, SHIP_VIEW_DEPTH]` by construction (the
waypoint table's first and last rows) — so algebraically `cam(0) = from` and `cam(1) = to` hold at
every warp, without needing a special-cased snap. The E2E test below reads `warp.to` and the
post-arrival `cam` and asserts they match to 6 decimal places — not "close enough," exact, because
that's what the math guarantees and a regression here would be a real defect, not noise.

## Launch-at-click and arrival framing — both real, both proportionate to what's honestly portable

- **Launch-at-click.** The live engine turns the ship's NOSE toward the clicked object's on-screen
  direction during "aim," before the burn. With the camera playing that role, "aim" now holds
  camera POSITION at `from` (matching the live engine's "the view holds still here") while
  orientation begins slerping toward the travel direction — a preview turn, not a full commitment,
  exactly mirroring what the ship would be doing if it existed.
- **Arrival framing.** Not a separately-coded feature — an emergent property of chase-look damping.
  The look target is `shipW + dir·CHASE_LOOK_AHEAD`; as `k → 1`, `shipW` converges on
  `to + dir·SHIP_VIEW_DEPTH`, so the look point converges on a point just past the arrived body.
  The camera settles looking roughly at what it just arrived at, without bespoke "look-at-arrival"
  code. Recorded honestly: this is a real behaviour, not a claim that the full live-engine arrival
  polish (ship-sprite scale/fade bump) was ported — there is no sprite to bump.

## HUD readout ported, not just camera math

`WarpOverlay.tsx` is engine-agnostic — it reads `warp.phase`/`warp.wphase`/`warp.vC`/`warp.ly` from
React state, populated purely from `cosmos:warp` event payloads. Porting the brachistochrone
accel/flip/decel classification and the apparent-velocity formula (`vC = lyTotal·dsdk / warpDur / 3.1688e-8`,
identical to the live engine's) means the **same transit HUD text** — "ACCELERATION BURN",
"FLIP & BURN — ROTATING SHIP", "DECELERATION BURN", "APPARENT VELOCITY N c" — now renders for a
Babylon journey with zero UI code changes. Verified directly in the new E2E test, not inferred from
the emitted event shape alone.

## Deliberately out of scope (unchanged from TR-040's framing, re-confirmed)

- **Distance-scaled pacing** — still B2 step 5. Warp duration is fixed (2400 ms) regardless of
  target distance, matching the live engine's own non-distance-scaled behaviour today.
- **Screen-space station projection** (`sx`/`sy`/`ex`/`ey`) — not one of the plan's six named B2
  sub-steps; still deferred, still verified-safe rather than merely absent (see TR-040).
- **Reduced-motion parity** — B2 step 6. `AIM_DUR_MS`/`WARP_DUR_MS` use the live engine's
  non-reduced values only; nothing on the Babylon path checks `prefers-reduced-motion` yet.
- **Relativistic aberration/Doppler in the star shader.** A real velocity profile (`dsdk`/`vC`) now
  exists — the exact blocker TR-038's shader comment named — so this is newly _possible_, not newly
  _in scope_. Flagged as a reasonable near-term follow-up rather than absorbed into this step's
  scope, which the plan names specifically as chase camera / launch / arrival.
- **Free-look drag/orbit controls, field-star hover/picking** — unchanged from TR-040.

## Honest limits

- The launch-at-click turn and arrival framing are real but necessarily reinterpreted for a
  ship-less scene — they animate the camera where the live engine animates a separate sprite. A
  future craft-loading step for Babylon could add a visible ship without changing this camera logic
  (the "virtual ship" position already computed each frame is exactly what a real mesh would sit
  at).
- `warp.wphase === "flip"` (the ~144 ms window at `k ∈ [0.47, 0.53]`) is implemented and emits
  correctly (same thresholds as the live engine) but is NOT separately asserted in the new E2E test
  — the window is too narrow to poll reliably without flakiness risk. Covered indirectly: accel and
  decel both being observed proves the state machine transitions through flip between them.
