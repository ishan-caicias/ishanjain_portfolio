## Fix 1 — HiDPI blur: `adaptToDeviceRatio` missing on the WebGPU path

Root-caused against `@babylonjs/core` source, not guessed. `Engine` (the WebGL2 fallback)'s
constructor takes `adaptToDeviceRatio` as a **4th positional argument**
(`new Engine(canvas, antialias, options, adaptToDeviceRatio)`), and the code already passed `true`
there — correct since B1. `WebGPUEngine`'s constructor has **no such positional slot**
(`constructor(canvas, options)`, 2 params only) — it must be set via `options.adaptToDeviceRatio`,
which the code never did. Confirmed in `AbstractEngine`'s shared constructor
(`node_modules/@babylonjs/core/Engines/abstractEngine.js`):

```js
adaptToDeviceRatio = adaptToDeviceRatio || options.adaptToDeviceRatio || false;
this._hardwareScalingLevel = adaptToDeviceRatio
  ? 1.0 / Math.min(limitDeviceRatio, devicePixelRatio)
  : 1.0;
```

With it defaulting to `false`, the canvas's drawing buffer was sized to CSS-pixel resolution
regardless of the display's actual pixel density. On any HiDPI screen (very common — most modern
Windows laptops and external monitors run at 125–200% scaling), the browser then stretches that
lower-resolution buffer to fill the physical pixel grid — exactly what reads as "blurry." The
WebGL2 fallback was never affected, which is consistent with the owner only reporting this on the
desktop WebGPU reading.

**Fix:** `new WebGPUEngine(canvas, { antialias: true, adaptToDeviceRatio: true })`.

**Verified on real hardware, not by inspection alone** — [webgpu-hardware.spec.ts](../../tests/e2e/webgpu-hardware.spec.ts)
gained a new test that launches with `deviceScaleFactor: 2` (simulating a common HiDPI setting) and
asserts the canvas's drawing-buffer resolution actually scales with it
(`canvas.width / canvas.clientWidth > 1.8`), not just that the option was passed. Same fails-open
pattern as the rest of that file (skips if no real WebGPU adapter is available in the environment).

## Fix 2 — Ambient idle drift ("the background remains static")

Checked the live engine before building anything: `space-engine.js` has an ambient idle-at-home
drift (`if (this.warp.mode === "idle" && !this.reduced && Math.hypot(...this.cam) < 1) this.yaw += 0.00012;`)
that the Babylon path never ported — nothing animated at all while parked, which reads as "the
scene is dead" rather than "parked." Two new pure helpers in
[ship-dynamics.ts](../../src/lib/ship-dynamics.ts), unit-tested: `quatFromAxisAngle` (axis-angle →
unit quaternion) and `quatMultiply` (Hamilton product, composing rotations). Applied each idle
frame at home: `_camQuat = quatMultiply(quatFromAxisAngle(UP_AXIS, IDLE_DRIFT_RATE * dt), _camQuat)`.

`IDLE_DRIFT_RATE = 0.0072` rad/s is a **converted**, not copied, value: the live engine's own
`0.00012`/frame is an implicit ~60fps-normalized increment (frame-rate DEPENDENT — faster monitors
drift faster in the live engine, which is arguably its own minor bug), so this multiplies by 60 and
applies it properly scaled by `dt` instead, making the Babylon version frame-rate independent. A
very slow spin (~14.5 minutes per revolution) — enough that the view isn't frozen, not a feature in
its own right.

**Explicitly NOT the same as free-look navigation.** This is passive ambient motion at rest, gated
off entirely the moment any real travel starts or the camera leaves home. It does not touch, and
should not be confused with, pointer-drag orbit controls — those remain unbuilt (see below).

## Not fixed here — known, already-documented scope boundaries

- **"No 360 nav"** — free-look drag/orbit controls. [TR-040](TR-040.md) named this explicitly as
  out of scope ("not mentioned in the delivery plan's step 3 wording; the Babylon camera doesn't
  yet respond to pointer drag") and it has stayed out of scope through steps 4–6 (TR-041/042) —
  this is not a regression the demo introduced, it is a feature that has never existed on this
  path. Worth scoping as a deliberate increment if the owner wants it before B3, rather than folded
  into this reactive fix.
- **"No spaceship"** — no craft mesh loads on the Babylon path. Flagged since B0/B1: the camera has
  played the "ship" role throughout the flight-model work (TR-040/041) specifically because there
  is no ship to render yet. Craft loading for Babylon is a separate, unscoped track.

## Flagged, not fixed — the startup numbers need B1-gate-grade rigor first

The B1 gate's own history (TR-032/033) is that raw device readings are not self-verifying —
Round 1 was voided over an instrument bug, Round 2 caught a display-Hz artefact. Applying the same
skepticism here rather than reacting to either number at face value:

- **Desktop 3023 ms** exceeds the ≤2.5 s budget. Nothing in this session's changes (this fix or the
  B2 step 3–6 work) touches the boot sequence's cost — the DPR fix and idle drift both only affect
  per-frame render-loop behaviour, not the one-time catalog-decode/body-population startup path —
  so this isn't attributable to today's changes, but it is a real number worth tracking. 144 fps
  and 142 host rAF against a 164 Hz display are self-consistent and plausible (not an "impossible"
  reading in the TR-032 sense), so the instrument itself looks credible here.
- **Android 267 ms** is implausibly fast for decoding a 2 MB+ PNG-packed star catalog via
  `ImageBitmap` + canvas on mobile hardware — worth confirming this wasn't a warm/cached reload
  (the gate procedure's own methodology requires a cold load) before treating it as real. Recording
  it as a real 267 ms figure without that confirmation would risk exactly the kind of false
  certainty TR-033 explicitly warned against.

**Recommendation, not yet actioned:** re-run both readings using the established gate procedure
(cold load, device signature line visible, both readings on the same page load) before deciding
whether the desktop startup number needs a profiling pass.
