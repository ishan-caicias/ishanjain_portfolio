## Root causes

### #1 — home-orbit auto-aim never yielded to free-look after a drag ended

`_tickWarp`'s `if (this._homeOrbit)` branch (babylon-engine.ts) re-derived the camera's
`_yaw`/`_pitch` from the orbit position on **every frame the visitor wasn't actively mid-drag** —
including the very first frame after a drag ENDED. A visitor drags away, releases, and the next
tick snaps the view straight back to face Earth. The code even had a comment claiming "free-look
drag still overrides" — true only for the instant of the drag itself, not after release, which
is the opposite of what "drag persists" means everywhere else in this file (the sibling "ambient
idle drift" branch, three lines below, explicitly states the correct philosophy: "a visitor who
has already dragged/looked around keeps their own orientation"). The camera's **orbital
position** (owner requirement R16, delivered correctly in TR-088) was never the problem.

### #2 — the hover/click picker has no concept of the planet sphere at all

`_pick`/`_pickField` are a **screen-space nearest-projected-point search** over `this.bodies`
and a cone-angle sweep over the star field — never a real depth/occlusion test. This was
harmless before D6.4: nothing solid was ever on screen for the camera to look past (an
arrival's planet sphere fills the frame and the camera is pinned to look at it). D6.4 put a
26-world-unit opaque sphere at a fixed point the visitor can now freely look around, and the
picker kept working exactly as before — whatever body/star was screen-space-nearest to the
cursor got picked, with no awareness that Earth's rendered surface was in front of it. Babylon's
own `mesh.isPickable` flag (already `false` on the planet sphere) is irrelevant here — this
picker never calls `scene.pick()` in the first place.

### #3 — D5.1 approved, never implemented

`MissionControlBar.tsx` still read `RNG`/`SOL` with `title="Random destination"` /
`"Return to Sol"`. The delivery plan's own D5.1 entry (line 599) is marked "✅ NAMES APPROVED"
but the phase table shows no "DELIVERED" line — the decision was recorded, the code never
followed.

## What shipped

### Fix #1 — `_homeLookOverridden`

A new field, latched `true` on the first genuine drag since the home orbit was last (re)armed;
`false` on every arming site (`beginAscent`'s two paths, `skipAscent`, and the regular
`goHome`-via-warp arrival — four sites, all four updated). The tick loop's auto-aim now checks
`!this._dragging && !this._homeLookOverridden` instead of just `!this._dragging`. The orbital
**position** update is untouched — R16 still holds; only the forced re-aim of the **view** stops
once the visitor has taken control of it. Exposed on `sceneStats()` as `homeLookOverridden` for
regression testing.

### Fix #2 — ray/sphere pick occlusion

Two new pure functions in `ship-dynamics.ts`, unit-tested directly:

- `cursorRayDir(x, y, rectW, rectH, right, up, fwd, tanFov, aspect)` — the world-space unit ray
  for a screen point, factored out of `_pickField`'s own inline NDC math (which used to be
  reimplemented, not shared, risking silent drift between the two).
- `raySphereDist(camPos, dir, center, radius)` — nearest ray/sphere intersection distance, or
  `Infinity` if the ray misses or the sphere is behind the camera.

`_pick` now computes the cursor ray once, tests it against the planet sphere
(`_planetOcclusionDist`, gated on `this._planetMesh?.isVisible`), and rejects any body candidate
farther from the camera than the sphere's near surface; the field-star fallback is skipped
outright when the sphere occludes at all (field stars are always vastly farther than a
26-unit-radius sphere, so a finite occlusion distance always wins). `_pickField` was refactored
to accept the precomputed ray/camPos instead of recomputing them, removing the duplicate NDC math
rather than leaving two copies to maintain.

### Fix #3 — D5.1 renames, exactly as approved

`MissionControlBar.tsx`: `RNG` → `RANDOM JUMP ▸` (`title`/`aria-label` "Jump to a random
destination"), `SOL` → `◂ RETURN HOME` ("Return home to Earth orbit"), with a sub-400px
compressed variant (`JUMP ▸` / `◂ HOME`) via a CSS breakpoint — both strings render, one hidden
by `max-[399px]:hidden`/`hidden max-[399px]:inline`, so `aria-label` stays the single source of
truth for the accessible name at every width, exactly as the implementation plan specified.
`CollectorCard.tsx`'s `◂ RETURN TO SOL` → `◂ RETURN HOME` (named in the plan). **`SectionOverlay.tsx`
carried the identical string and was updated too**, even though the plan's D5.1 entry only named
CollectorCard explicitly — leaving it would have reintroduced exactly the inconsistency the
rename's own "one-phrase-per-action" rationale exists to remove. Four E2E test files updated
their `RNG`-button locator to match the new accessible name (named test changes, CLAUDE.md #15).

### Test-instrument incident, root-caused rather than worked around (CLAUDE.md #14)

The first two isolation attempts at the drag-persistence spec failed — not from a code defect,
but from **Playwright's own `page.mouse.move()` hanging indefinitely** against this specific
scene state (idle, home-orbit, slow ambient revolution — no other page in this suite drives a
real OS-level drag against a quiet, non-warping scene). Diagnosed methodically before touching
anything:

1. Ruled out CPU contention first (this session's own prior lesson, TR-095/096): confirmed via
   `tasklist` that zero stray node processes were running, and re-ran clean — still hung.
2. Called `_pick()` **directly** via `page.evaluate` (bypassing Playwright's input layer
   entirely): returned instantly, correctly (`hoverId: null`), proving the application code was
   never at fault.
3. Dispatched real `PointerEvent`s straight at the canvas via `canvas.dispatchEvent(...)` from
   inside the page (still real DOM events reaching the real `_bindPointer` listeners, just not
   routed through Playwright's CDP-level OS input simulation): `_dragging`, `_yaw`/`_pitch`, and
   `_homeLookOverridden` all updated exactly as expected, reliably, every time.

The known-good precedent this repo already had (`engine-select.spec.ts`'s "free-look drag stays
authoritative" test) uses `page.mouse` successfully — but only **mid-warp**, while the scene is
continuously animating. Whatever makes CDP mouse dispatch reliable there does not hold against a
quiet idle scene. All of this spec's pointer interaction — drag AND hover AND click — now goes
through the same proven `dispatchEvent` technique; nothing in this file depends on `page.mouse`
against the babylon canvas. Recorded as a genuine environment/harness finding for future specs
touching the idle home-orbit state, not silently patched around.
