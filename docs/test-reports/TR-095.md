## What this slice is

The last D3 slice, and the smallest — but it closes the phase's audited baseline item
_"`travelTo`/`goHome` silently no-op mid-warp (both engines)"_. Pressing HOME or picking a
destination during a warp did **nothing, and said nothing about doing nothing**. It survived
unnoticed until TR-080's dead-code reset went looking for why a reset never fired.

Owner ruling (ADR-0010): HOME mid-journey **ABORTS** — the journey is abandoned where the ship
currently is and a fresh home-bound warp launches from that exact point. A destination pick
mid-journey **QUEUES** a retarget that launches on arrival, last selection wins. Neither is ever
silent.

## What shipped

### 1. The decision itself is a pure module, not a mode list

`flightInputPolicy(mode, request) → "proceed" | "queue" | "abort" | "ignore"`
(ship-dynamics.ts). Three surfaces have to agree about what a press does — the engine, the HUD
badge (next slice), and the Where-To console's mid-warp row (D5.2) — and the pre-D3.3 shape of
this decision was the same `mode === "warp" || mode === "aim" || mode === "ascent"` disjunction
copy-pasted into `travelTo`, `goHome` and `beginAscent`. A pure function makes it unit-testable
off-GPU (`babylon-engine.ts` cannot be imported in jsdom) and gives the HUD slice one import
rather than a rule to re-derive.

**`ascent` is the one surviving no-op, and it is named.** The launch cinematic is a rails climb
that owns the camera, fired before the console is even revealed — there is no input to honour and
nothing to say about it. Returning `"ignore"` rather than falling through a mode list makes that
a deliberate verdict at the call site instead of an accident of ordering. A unit test asserts
exhaustively that `ascent` is the ONLY (mode, request) pair that yields it.

### 2. Abort inherits the live position by construction

`goHome()` mid-journey calls `_beginWarp(undefined, _homeArrivalPoint(), true, quiet, 0)`.
`_beginWarp` reads `this.cam`, which `_tickWarp` keeps integrated every frame — so the abort
starts from wherever the ship actually is with **no new bookkeeping**, which is the whole reason
the implementation plan specified this mechanism. The new warp resets `k=0`, so the ship plays a
full D3.2 accel → coast/flip → brake home rather than a cut. `cosmos:abort
{toHome, abandonedId, quiet}` fires immediately; `abandonedId` is carried so the HUD can name what
was given up without re-deriving it from stale state.

### 3. The queue is public display state

`queuedTargetId` is a **public** field on the element, added to the `SpaceEngineElement` contract
as optional (`queuedTargetId?: string | null`) exactly the way `beginAscent?()` was — the archived
WebGL engine has no queue, and readers must treat `undefined` as "this engine has no queue"
rather than "the queue is empty". A queue nobody can render would be the silent no-op this slice
exists to kill.

`travelTo` mid-journey sets it (last-wins) and emits `cosmos:retarget-queued {id, quiet}`.
`goHome` clears it on both paths — an abort **discards** the queue, it does not inherit it — as
does `beginAscent` and `disconnectedCallback`.

### 4. The drain is deferred, deliberately

At `k >= 1` the queue drains through a `setTimeout(0)`, never inline. `travelTo` replaces
`this.warp` wholesale while the rest of that same tick still reads the local `w` for β,
aberration and the camera write — launching inline would run the tail of an old frame against a
brand-new journey's state. The handle is cancelled in `disconnectedCallback`, the same hazard
class as D0.1's band-build timer (a callback that outlives the engine).

Guard: if the queued id equals the id just arrived at, clearing it **is** the whole action —
re-flying would be a zero-length warp and would re-fire `cosmos:arrive` over the dossier that
just opened.

### 5. A pre-existing UI defect this slice would have made worse (SpaceScene.tsx)

`goSection()` set `sectionTravelRef.current = sec` **unconditionally** before calling `travelTo`,
and the `cosmos:arrive` handler consumed it on the NEXT arrival whatever that arrival was. Under
the old no-op that already meant a nav click during a warp opened the section over the wrong
body. Under queuing it gets worse in a new way: the click now genuinely flies somewhere, but the
_interrupted_ journey's arrival still consumes the intent, so the section opens early at the
wrong body and never opens at the right one.

Fixed at the seam rather than worked around: the ref now carries `{id, sec}` and the handler only
consumes it when `detail.id === id`. `cosmos:home` clears it, so an abort discards a pending
section intent instead of leaving it to fire on some unrelated later arrival. This also removes
the pre-existing wrong-body bug. No test was modified for it.

`dispatchRoute` needed no change — it already guards `warp.mode !== "idle"`, so route sync
cannot abort a journey.

## Legacy engine — intentional divergence (CLAUDE.md #3/#17)

`space-engine.js` is **not** ported. It keeps its silent mid-warp no-op by design: the archive is
a rollback lever, not a feature target. The new E2E spec therefore pins the default Babylon path
only and addresses `babylon-scene` directly rather than the engine-agnostic selector, which is
#17's rule applied in its inverse direction.

## Reduced motion (CLAUDE.md #24)

The policy is orthogonal to motion preference and deliberately so: an abort and a retarget are
_navigation semantics_, not animation. Under reduced motion both still happen, with the journeys
they produce running the existing fixed-short reduced profile (`WARP_DUR_REDUCED_MS`, `_flipRate
= 1`). Nothing in `flightInputPolicy` reads `_reduced` — there is no reduced-motion branch to
diverge.

### Test-instrument note — why the interrupts are driven inside the page

Each journey is launched AND interrupted inside a single `page.evaluate` driven off the page's
own rAF. A Playwright-side poll would round-trip between "we saw k=0.2" and "we called goHome",
and TR-094 measured that under SwiftShader a whole journey can render in ~10 frames — the
interrupt would land after the ship had already parked and **every downstream assertion would
pass for the wrong reason**. Each spec therefore reports `progAtInterrupt` /`modeAtInterrupt` /
`distAtInterrupt` and asserts on them before asserting anything else.

The same reasoning removed one poll that was written and then deleted: the interrupted journey's
own arrival is asserted from the captured `cosmos:arrive` **event**, never from polling
`arrivedId === FIRST` — the queue drains one task after arrival, so that state is true for a few
milliseconds and a ~100 ms poll would have made the spec a coin flip. Polling for a transient is
a flake you write yourself.

## Manual regression (CLAUDE.md #25) — ⚠ PARTIAL, and the gap is named

`npm run preview` on the built `dist/` booted **console-clean on WebGPU with the full 168,959-star
catalog** (`backend: "webgpu"`, `starSource: "catalog"`, zero console errors), and the D3.3 state
machine was then exercised **live against the shipped bundle** while a journey was under way:

| Live check on the production build (warp mode `aim`, moon journey in flight) | Result                                                              |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| destination pick mid-journey queues                                          | `queuedTargetId === "mars"`, `cosmos:retarget-queued:mars`          |
| queue is not an abort — the journey keeps flying                             | mode still `"aim"`                                                  |
| last selection wins                                                          | pick `jupiter` → `queuedTargetId === "jupiter"`, second event fired |
| HOME aborts and discards the queue                                           | `queuedTargetId === null`, mode `"aim"`, `warp.home === true`       |
| the abort names what it gave up                                              | `cosmos:abort` with `abandonedId: "moon"`                           |

**What could NOT be done here, stated plainly:** the harness's browser pane runs **hidden**
(`document.hidden === true`), so `requestAnimationFrame` never fires and the render loop does not
tick — the moon journey sat at `warp.prog === 0` indefinitely. Everything downstream of the render
loop is therefore **unverified by human eyes** in this session: the mid-BURN interrupt (as opposed
to mid-`aim`), arrival, the abort's on-screen deceleration and re-launch, the arrival dossier
open/dismiss, Where-To search, classic-view toggle, and the reduced-motion pass. Screenshots would
have proven nothing (CLAUDE.md #11's sibling problem: a hidden pane reads blank regardless of
correctness).

Those behaviours **are** covered by the automated suite on a visible headless browser — the four
new specs all interrupt mid-BURN with `progAtInterrupt` asserted, and the arrival/dossier/toggle/
reduced-motion items each have standing E2E coverage that ran green in this gate. But automated
green is not the manual pass #25 requires. **The owner-eyes regression is OUTSTANDING and is the
condition on this slice being called delivered** — specifically: does an abort mid-burn _read_ as
a manoeuvre, and does the 900 ms `aim` hold at speed look wrong (see the follow-up below).

## Known limitations / follow-ups

- **HUD strings are NOT in this slice** — by owner direction. The engine emits
  `cosmos:abort {toHome, abandonedId, quiet}` and `cosmos:retarget-queued {id, quiet}` and
  exposes `queuedTargetId`; nothing listens to them yet. The delivery plan's
  `ABORTING · RETURNING HOME` and `RETARGET QUEUED · {name}` badges, and the Where-To console's
  mid-warp row (D5.2), consume that contract in the follow-up pass. **Until then the policy is
  correct but still visually silent** — the "never a silent no-op" acceptance criterion is
  half-met, and the slice is not the phase exit on its own.
- **Funnel instrumentation not extended.** `funnel.ts` records `travel` / `arrival`; an abort and
  a queued retarget are new visitor intents with no milestone. Left to the HUD pass so the
  events and their instrumentation land together.
- **Velocity discontinuity at the abort, unresolved and owner-visible.** The mechanism the
  implementation plan specifies (`_beginWarp` from the live position) necessarily restarts the
  profile at `k=0`, so world speed drops from mid-burn to zero at the moment of the press and the
  new journey opens with a 900 ms `aim` hold before accelerating home. The plan called this
  "acceptable and cinematic" in advance and it is implemented exactly as specified — but it is
  the same _class_ as owner complaint R6 (motion that doesn't decelerate legibly), and it is
  worth a Vega SHOT-BRIEF in a D3 polish pass rather than a silent tune here. Candidate levers:
  a shortened `aim` for aborts, or a real retro-burn blend from the live velocity.
- **Astra REALISM-AUDIT of the full journey** remains the D3 exit criterion (delivery plan) and
  has not run — it is the next D3 action, and must re-state **L15**'s compression magnitudes
  against the D3.2 duration table.
