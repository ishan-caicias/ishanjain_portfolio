## Two real bugs found (not assumed fixed — verified live, then fixed, then re-verified)

**1. `<babylon-scene>` never received `density`/`constellations`/`ship`/`craft` attributes at
all, ever, on any page load.** `SpaceScene.tsx`'s attribute-setting effect read
`engineRef.current` — but `engineRef` is only attached via JSX `ref={engineRef}` on the
`<space-engine>` branch; the `<babylon-scene>` branch has its own comment explaining it
deliberately has **no** ref, driven instead by the file's established `engineEl()` combined-
selector accessor (used everywhere else in the file). The attribute effect was the one site that
missed that convention, so on the Babylon path `el` was always `null` and the whole effect
silently no-op'd. GAP-12 (TR-058) wired `attributeChangedCallback` correctly — it just never
fired. Found via `getAttribute('craft')` returning `null` immediately after
`data-craft-state="ready"` (proving the ship loaded via the engine's own internal URL/stored
resolution, while the attribute React was supposed to set was never there). **Fix:** one-line —
`engineRef.current` → `engineEl()`, matching the pattern already used everywhere else in the
file. Verified: `craft`/`density`/`constellations`/`ship` all present and correct on the live DOM
after the fix.

**2. Babylon's no-WebGPU/WebGL2 fallback couldn't complete a journey.** Investigating GAP-19's
"WebGL fallback" test surfaced this: `space-engine.js`'s `travelTo`/`goHome` have an explicit
`noGL` fast path (instant arrival via a 250ms `setTimeout`, since nothing else will ever tick a
real warp state machine when there's no render loop). `babylon-engine.ts` had no equivalent —
its `travelTo`/`goHome` always went through `_beginWarp`, which only ever advances via
`_tickWarp` inside `engine.runRenderLoop`'s callback. When `_boot()`'s `createEngine()` throws
(no WebGPU, no WebGL2 either — CLAUDE.md #6's fallback policy), that render loop never starts,
so a warp launched in that state would stall in `"aim"` forever and `cosmos:arrive` would never
fire — breaking navigation for a no-WebGL visitor, silently. Not exercised by any existing test
because GAP-19's fallback test was pinned to the archived engine, which has always had this
fast path. **Fix:** ported the same fast path (`!this._engine` guard, instant arrival,
`cosmos:select`/`cosmos:arrive` with the same 250ms grace) into both methods.

## What shipped, by gap

**GAP-17 — `flight-v3.spec.ts`'s travel choreography.** Disposition, not a blind re-point: the
first 3 tests stay pinned to `?engine=webgl` deliberately — they drive `space-engine.js`'s own
synchronous `_tick(now)`/`.gl` internals with a synthetic-clock harness that has no Babylon
equivalent to port to (Babylon's render loop only runs via `engine.runRenderLoop`), and test 3's
premise ("camera holds still during aim while the ship turns") describes the archived engine's
specific choreography — Babylon's aim phase turns the _camera_ itself, by design, not the ship;
porting that assertion literally would assert behaviour Babylon was never built to have. Test 4
(free-look drag, wall-clock, real UI, no synthetic ticks) **was** genuinely portable and now has
a direct Babylon-native sibling in `engine-select.spec.ts`. A second new test closes the rest of
GAP-17's real gap: strict `accel → flip → decel` phase ordering, asserted via the `cosmos:warp`
event stream directly (not DOM text — see "A test-design lesson" below) against a deterministic
target (`polaris`, same one `engine-select.spec.ts`'s existing choreography test already uses and
for the same reason: provably clear of the asteroid belt's proximity-slowdown tube).

**GAP-18 — `craft-ship.spec.ts`.** Mechanically portable once bug #1 above was fixed: all 7 tests
now target the default engine. `SpaceScene.tsx` sets `craft`/`density`/`constellations`/`ship`
identically regardless of which engine mounts, and GAP-15 (TR-058) already made
`dataset.craftState`/`cosmos:craft` match shape on both engines — the only per-test change needed
was the `space-engine` → `babylon-scene` selector swap once the underlying attribute bug was
fixed.

**GAP-19 — `space-scene.spec.ts`'s 10 pinned gotos.** Un-pinned; adjusted the reduced-motion
test's field read (`en.reduced` → babylon-engine.ts's private `_reduced` — still readable at
runtime, TS privacy is compile-time only, same pattern this suite already uses for other private
fields). The WebGL-fallback test needed bug #2's fix to actually pass on Babylon — it was the
test that found the bug, not a test that could be un-pinned around it.

**GAP-20 — `engine-select.spec.ts`'s missing frames assertion.** One line:
`expect(snap.frames).toBeGreaterThan(0)` restored on the default-engine test, matching the
`?engine=webgl` test's own assertion (which never lost it). This is exactly the assertion TR-059's
bug would have failed — `cosmos:ready` fired while `scene.render()` was throwing on every frame,
and nothing on the default-path test suite ever read `frames` to notice.

**TR-059 regression coverage.** A new `webgpu-hardware.spec.ts` test boots the default engine on
real WebGPU hardware and proves `renderFrames` advances across the Milky Way band's entire
chunked-texture-build window (the exact span TR-059's bug lived in), then confirms continued
healthy production afterward, then confirms `bandReady`/`bandTextureReady` (proving the window
was actually crossed, not skipped past by lucky timing) and zero console/page errors.

## A test-design lesson (caught by first-attempt failures, not shipped uncorrected)

Two of the four new tests initially failed for reasons that were about the TESTS, not the
product — worth recording so the pattern isn't repeated:

- **GAP-17's flip-ordering test, first draft:** asserted `"FLIP & BURN — ROTATING SHIP"` becoming
  visible in the DOM. The flip window is only k∈[0.47,0.53] — ~6% of `polaris`'s ~3.2s journey,
  roughly 195ms of wall clock — and React's own state-update batching can coalesce several
  `cosmos:warp` events into one render; if "flip" and "decel" land in the same batch, only the
  last one ever paints. The engine's phase sequence was correct; the DOM assertion just couldn't
  reliably observe a ~195ms window through a render layer with its own batching. **Fixed** by
  asserting the `cosmos:warp` event stream directly (same technique `flight-v3.spec.ts`'s
  synthetic-tick harness already uses for exactly this reason, just with the real clock instead
  of manual ticks) — this is what GAP-17 actually needs verified, and sidesteps React's rendering
  layer entirely.
- **The TR-059 regression test, first draft:** sampled `renderFrames` every 300ms starting
  immediately after `starSource` resolved, demanding every consecutive pair strictly increase.
  Failed on a flat window early in boot — not TR-059 recurring, but Havok WASM compilation and
  the ship GLB decode both still running as concurrent fire-and-forget promises at that exact
  point, a genuine (expected) brief stutter unrelated to the band's texture binding. **Fixed** by
  recording frames before the band-build danger window, waiting for `bandReady` (which only flips
  once the exact window that used to crash every frame has been crossed), and asserting frames
  net-increased across that _whole_ span — TR-059's actual signature was zero frames advancing
  for the _entire_ window, not an isolated slow frame under concurrent load.

Both were caught by running the tests for real against a live server before calling this done,
not assumed correct from the code.
