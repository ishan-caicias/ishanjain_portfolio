## Why this exists

D7's audit (2026-07-22) named six memory/runtime opportunities, ranked. Two had already moved
since the audit was written: the 2026-07-29 D5/D6 code-review pass (TR-110) landed
`beltPullAccelInto` and flagged `passageDeflectForce`'s matching tuple allocation as "D7's

fetch tier-gated (D7.2's other half). This TR closes what was left, and completes the two that

## D7.1 — `clearCachedData()` for the three bulk billboard meshes

`babylon-engine.ts`: `_applyStarFieldGeometry` (star field, both the initial boot upload and the
bonus-layer merge rebuild), `_loadSdssGalaxyLayer`, `_loadAsteroidVisualLayer` now call
`mesh.geometry?.clearCachedData()` after their final vertex-buffer upload.

**Verified safe, not assumed:** all three meshes are `isPickable = false`, and the engine's own
picking (`_pick`/`_pickField`) reads `this._field` — a plain typed array kept independent of the
GPU geometry — never `mesh.getVerticesData()` or `scene.pick()`. Confirmed via
`node_modules/@babylonjs/core`'s own source: `VertexData.applyToMesh` calls `setVerticesData`,
which always builds a **fresh** `Geometry` rather than reusing a cleared one — so clearing after
the star field's first (boot) upload cannot break the second (bonus-merge) rebuild on the same
mesh. **Real trade-off, documented inline:** a lost WebGL context can no longer restore these
three meshes' real data (Babylon's own docstring: "prevent picking, collisions, or physics" —
confirmed by reading `Buffer._rebuild()`, which falls back to an empty same-size buffer with no
CPU cache) — accepted because the Babylon path has no context-restore recovery today regardless
(only the archived `space-engine.js` handles `webglcontextlost`).

**Expected win:** ~430 MB CPU-side vertex/index arrays freed (SDSS ~361 MB, merged/bonus star
field ~54 MB, belt ~15 MB) — per the audit's estimate; real-device heap snapshot is the owner's
to confirm.

## D7.2 — Planet texture ladder: departure disposal (fetch gating already shipped by D6.3.2)

The "ultra fetched unconditionally regardless of tier" half of this audit finding was **already
fixed** by D6.3.2 (shipped 2026-07-23, TR-087) — found stale during this slice's implementation,
recorded here rather than silently reused. The **remaining real gap**: nothing disposed the
bound per-body textures when the sphere went invisible with no next body queued (only on
`_planetBodyId !== key`, i.e. only when switching bodies, not when departing to nowhere).

New `_disposePlanetBodyTextures()` (babylon-engine.ts) disposes the six real per-body textures
(surface, height, normal, cloud, night, specular) plus any in-flight VT detail atlas, and rebinds
every sampler to its existing shared placeholder (`_planetPlaceholderTex`/`_planetFlatNormalTex`/
`_planetBlackTex`) rather than leaving a disposed reference bound — CLAUDE.md #9 (TR-059): a
declared sampler needs a real texture object before the mesh next draws. Wired into both
`_tickPlanetSphere` early-return branches (no manifest; no body and not at home), guarded so it
only runs on the actual departure transition, not every idle frame.

**Trade-off:** returning to the same body re-fetches its textures (usually HTTP-cache-absorbed)
rather than keeping them warm — the point of the method. **Expected win:** Earth alone was
measured (per the audit) at ≈683 MB VRAM with mips retained indefinitely across a session;
real-device before/after is the owner's to confirm.

**Landed early with this slice (originally itemized under D7.4):** the VT streamer's
`atlas.canvas.toDataURL("image/png")` → `new Texture(dataUrl, scene)` round-trip (`_tickPlanetVt`)
PNG-encodes then immediately re-decodes a canvas up to 4096×4096×4 = 64 MB. Replaced with
`RawTexture.CreateRGBATexture` fed directly from `ctx.getImageData(...).data` — same visual
result (`invertY`/mipmap defaults matched to preserve orientation), zero codec round-trip. Kept
the `toDataURL` path as a defensive fallback for the (unreached, since `composeAtlas` already
required a 2D context to draw the tiles) case `getContext("2d")` fails.

## D7.3 — SDSS decode moved to a Worker (the base catalog and belt stay on the main thread)

New `src/workers/catalog-decode.worker.ts`: receives the already-fetched SDSS `Blob` (fetch +
D1.1 progress reporting stay on the main thread, unchanged), does `createImageBitmap` →
`OffscreenCanvas` → `getImageData` → decode → billboard-build entirely off the main thread, and
transfers the resulting typed arrays back with zero copy. `_loadSdssGalaxyLayer` now awaits
`_decodeCatalogInWorker(blob)` instead of doing the decode inline. **Scoped to SDSS only** (named
in the plan) — the base catalog (168,959) and belt (154,662) are ~20-24x smaller and stayed on
the existing synchronous path; touching all three multiplies risk for comparatively little gain
on the smaller two.

New `decodeStarCatalogFromRGBA()` (star-catalog.ts) reads packed records directly out of the RGBA
buffer `getImageData` returns, eliminating the separate alpha-stripping copy pass
`decodeStarCatalog` requires (`DataView.getFloat32` needs contiguous bytes; RGBA's alpha byte
breaks that every 3rd byte, so this version gathers each record's 15 bytes via the pixel/channel
mapping instead). This removes one whole ~47-63 MB transient buffer from the SDSS decode's peak.
**5 new unit tests pin it byte-for-byte identical to `decodeStarCatalog`** across single/multi
chunk, trailing-partial-record, missing-chunk, and `Uint8ClampedArray` (the real `getImageData`
return type) cases.

**CSP:** `worker-src 'self' blob:'` was already present in `astro.config.mjs` (added for a prior
feature) — no new directive needed; verified rather than assumed.

**Verified via a full production build**, not just typecheck: `dist/_astro/catalog-decode.worker-*.js`
is a real separate bundled chunk; `babylon-engine.*.js` references it correctly.

## D7.5 — Havok bodies actually sleep, not just this engine's own force loop

`_tickAsteroids`'s existing `if (!this._beltPhysicsAwake) return` (D2.1) already skipped this
file's own per-frame force-application loop while the belt is faded — but Havok's solver was
still stepping and integrating every body regardless, since skipping OUR loop doesn't stop the
physics WORLD from simulating them. `_tickAsteroids`'s own comment named this gap explicitly as
"D7.5's measured refinement — recorded, not done here."

New `_setBeltPhysicsAwake(awake)` (babylon-engine.ts), called from `_updateFrameLadder` in place
of the old direct boolean assignment: on a state **flip** (not every frame — a full body loop
every frame just to re-set the same value would be its own waste), sets every Havok body's
motion type to `STATIC` on fade-out and `DYNAMIC` on fade-in via Babylon's
`PhysicsBody.setMotionType`. The `PhysicsMotionType` enum is read via a `typeof import(...)`
type-only reference (zero bundle cost) from the module `_setupPhysicsInner` already dynamically
imports for `PhysicsShapeType` — no new import, lazy or otherwise.

New `sceneStats().beltBodiesStatic` proves the bodies themselves changed state (not just the
pre-existing `beltPhysicsAwake` flag): `true`/`false` when Havok-backed, `-1` when the physics
tier is anything else (visual/off/loading/failed — no motion type to read). `frame-ladder.spec.ts`
(E2E, not run this session) gained assertions at all four existing checkpoints (Mars, M42,
nbg-a0554-07, home), each tolerating the `-1` fallback for hardware without SIMD/Havok.

**Also under this row (delivery plan's own D7.5 text names both):** "bonus-layer merge re-decodes
the base catalog and rebuilds all 541k billboards." The re-decode half is fixed: new
`mergeStarFields(base, bonus)` (star-field.ts, pure) concatenates the already-decoded base field
(`this._field`, set once at boot) with a freshly-decoded bonus field, so `_loadBonusStarLayers`
no longer re-runs `decodeStarCatalog` over the ~168,959 base records it already parsed once.
3 new unit tests, including a direct equivalence check against the old
`decodeStarCatalog([...base, ...bonus])` single-call path it replaces. **The "rebuilds all 541k
billboards" half is NOT fixed** — `_applyStarFieldGeometry` still calls `buildStarBillboards` on
the whole merged set. Avoiding that too means splitting base and bonus into separate meshes (the
same reason SDSS and the belt already have their own meshes), which is a bigger structural change
than this pass's scope — recorded as a follow-up, not attempted here.

## D7.6 — Retained one-shot buffers

- `MilkyWayBandBuilder`'s ~2 MB equirect RGBA `buf` (built once, uploaded once to `_bandTex`) —
  `_bandBuilder` is now set `undefined` immediately after the upload in `_buildBandSlice`, rather
  than only in `disconnectedCallback`. `bandProgress`'s `_bandReady` short-circuit already never
  reads it again once true, confirmed by reading the getter before making this change.
- `_baseCatalogRgb` (~2.4 MB, the two base-catalog RGB chunks retained for the bonus-layer merge)
  — nulled in `_loadBonusStarLayers`'s `finally` block, which runs on every exit path (success,
  the "every bonus chunk failed" early return, and the catch). The method itself is guarded to
  run at most once per boot (`_bonusLayersRequested`), so this is its last possible read.
