## Issues Found and Fixed During This Phase

| Issue | Fix | Scope |
|---|---|---|
| `HTMLElement is not defined` — SSR crash | `client:load` islands still execute module-scope imports during Astro's server-side render pass. `space-engine.js` (`class SpaceEngine extends HTMLElement`) and the celestial data files (`window.CELESTIAL = ...`) reference browser-only globals at module scope. Fixed by moving all 6 imports into dynamic `import()` calls inside `useEffect`, which only runs client-side. | `SpaceScene.tsx` |
| `File '...celestial-*.js' is not a module` (TS2306) | The 5 celestial data files have zero `import`/`export` statements, so TS won't type a dynamic `import()` of them as a module. Appended one no-op `export {};` line to the end of each file — no existing data touched, MD5 differs only by that trailing line. | `src/data/celestial/*.js` |
| `Property 'space-engine' does not exist on type 'JSX.IntrinsicElements'` | React 19's `@types/react` nests the JSX namespace inside `declare namespace React`, not the bare global `JSX` namespace. Ambient declaration needed `declare module "react" { namespace JSX {...} } }`, not `declare global { namespace JSX {...} } }`. | `src/lib/space-engine.d.ts` |
| Local preview tooling couldn't reach the dev server (port mismatch) | `astro.config.mjs` didn't read a `PORT` env var, so Astro's own port-conflict auto-increment (4321→4322) diverged from the port the preview harness proxied. Added `server.port` reading `process.env.PORT`, falling back to 4321 unchanged. Pre-existing gap, unrelated to this feature, fixed opportunistically because it blocked verification entirely. | `astro.config.mjs` |
