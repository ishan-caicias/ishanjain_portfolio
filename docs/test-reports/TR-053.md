## The 2 red tests — diagnostic state (bounded-retry stop)

`flight-v3.spec.ts` "chase camera pans the look mid-warp" and "launch points at the click"
(and "full journey", which only ever passed via the suite's global retries) fail because the
**synthetic-tick harness** (`flyToAbout`: `cancelAnimationFrame(en._raf)` then `en._tick(now)`
at simulated 60 fps) no longer advances the live engine's warp state machine:

- Probed facts: `travelTo("st-about")` sets `warp = {mode:"aim", start:<real now>, aimDur:900}`;
  120 synthetic ticks advance `now` 1.9 s past `start` yet mode stays `"aim"` and `start`
  never drifts; even a SINGLE `_tick(now + 5000)` does not flip the mode. `gl` valid,
  `_ctxLost` false, `_raf` cancel confirmed effective (frame counter freezes), real-time rAF
  operation normal (~12 fps SwiftShader), **real-time journeys work** (space-scene click-through
  suite green).
- Ruled out: my cutover changes as the cause (the only live-path runtime change is
  `resolveEngine`'s default constant — the engine module itself is untouched today); GL context
  loss; frame-throttle guards (lines 1970/1974); `warp.start` reset loops; reduced-motion.
- Unresolved: why `_tick(t)`'s aim branch (`(now - w.start)/aimDur`, line 2031 — pure time
  math with no intervening return found) does not fire under manual invocation on this build.
  Possibly a long-standing probabilistic harness fragility (these tests carry the global
  retries:2 and the file's earlier flake history) newly made deterministic by unrelated timing
  shifts — but that is a hypothesis, not a finding.
