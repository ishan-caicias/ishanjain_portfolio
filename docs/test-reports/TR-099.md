## D4.2 — field-object travel parity

`travelTo` now resolves `fs-<i>` ids via a new `_fieldBody` synthesis (babylon-engine.ts),
wired in **before** the D3.3 mid-journey policy gate so a field object picked mid-warp queues
like any other destination instead of falling out the old `if (!b) return` as a fresh silent
no-op. `aimAt` (the `?testhooks` hook) extended to resolve field ids too, so specs can drive
the real hover→click path rather than calling `travelTo` directly.

**Two real defects in the implementation plan's own prescribed port, caught before shipping**
(the plan is corrected in place — see its D4.2 section, superseded not edited away):

1. **Stride.** Legacy `space-engine.js`'s `fieldF` is 4 floats/record; Babylon's
   `_field.positions` is 3. A verbatim `i*4` port silently reads a neighbouring star's
   coordinates — no crash, no visual error, just travel to the wrong object. Pinned by a new
   pure `fieldStarTarget(id, positions, count)` export, unit-tested directly (12 tests) rather
   than only exercised inside the engine class.
2. **Depth convention.** The plan's prescribed `ly: L*3.9` is correct only for the base HIP
   field (type 0). PF-10's typed bonus layers (WD/OC/GD-1/EXO/AST/OORT) are **log-depth**
   (`fieldInfo`'s `type > 0` branch); `L*3.9` there reports a record at ~10³ ly instead of its
   real distance — not cosmetic, since that value drives `warpDurationForLy`,
   `localFieldVisibility` (D2.2's extragalactic collapse), and `_farDestLy` (the impostor's
   size). Shipped routes `ly` through `fieldInfo(i)` itself instead — the same source the
   hover tooltip and collector card already read, so the three agree by construction. An E2E
   test asserts `warp.lyTotal === fieldInfo().ly` for a real log-depth record AND that the
   legacy formula would genuinely have disagreed there — proving the assertion isn't vacuous.

**Test-instrument findings during this slice's own development** (root-caused, not
worked around): a histogram probe of the live field found PF-10's typed records live in the
deep-layer band around index ~118,000, not appended at the tail as first assumed — a draft
E2E test scanning the tail found nothing and silently skipped itself, asserting nothing; fixed
by measuring first (a throwaway diagnostic spec, since deleted) and scanning forward instead.
A field-index chosen naively for hover tests (index 5000) turned out to be within 34px of a
real catalog body (`ngc752`) at that camera angle — `_pick`'s body-priority correctly won,
so the draft spec was testing catalog-body travel while claiming to test field travel; fixed
with a `clearFieldIndex` helper that scans for a field star angularly clear of every catalog
body/station before hovering it.

## D4.3 — card polish

`CollectorCard.tsx`: real focus trap (new `trapFocus(container, event)`, `focus-utils.ts`) +
focus-on-mount/restore-on-unmount (reusing D4.1's `moveFocusTo`/`restoreFocusTo`, not
re-authored); `aria-labelledby` pointing at the name heading (was a plain `aria-label`); style
dots now 24×24px real hit targets (WCAG 2.5.8) wrapping the original 14px decorative dot,
`aria-label`/`aria-pressed` added; stat-bar fill divs marked `aria-hidden`; the vestigial
`e.r === "field" ? rc : rc` ternary (both branches identical) deleted.

`SpaceScene.tsx`: `hover: null` added explicitly at both card-open sites (the direct
already-arrived reopen branch, and the vista's `onOpenCard`), **and** `HoverTooltip`'s render
gated on `!state.cardId && !state.vista` as a render-time backstop — belt-and-suspenders so a
future card-open path that forgets the explicit clear still can't leave a stale tooltip
showing. HoverTooltip's CTA string `"ON STATION · CLICK TO OPEN DOSSIER ▸"` →
`"ON STATION · OPEN COLLECTOR CARD ▸"` — the naming-overload fix R8's audit named (the card's
own "dossier" _visual style_ option and SectionOverlay's own "dossier" display mode are
untouched, both pre-existing, plan-endorsed uses of the word for a different concept).

**Deviation from the implementation plan, recorded not silent:** the plan's D4.3 section
describes `moveFocus(el, restoreTo)` and `useEscapeStack(layer, handler)` as new functions
this slice creates. Both already existed by the time D4.3 started — D4.1 landed first (as the
plan's own "if D1 lands first, create it here" note anticipated) and shipped
`moveFocusTo(el)`/`restoreFocusTo(el)` as two functions and
`useEscapeStack(layers: readonly EscapeLayer[])` taking a priority array. D4.3 reused them as
built; only `trapFocus` was genuinely new here. The implementation plan is corrected to the
shipped reality (superseded, not edited away).

## D4.4 batch 1 — cluster content (owner-approved 2026-07-25)

New override-only `celestial-content-overlay.js` — never hand-edits the generated
`celestial-clusters.js` (CLAUDE.md #22) — patches the `"f"`/`"lo"` fields of the 25 clusters
that carried the `[[TODO: content pass...]]` placeholder. Numerical facts (distance/age/
magnitude) were **not re-derived**; they were already hand-verified in each record's own
`"st"` field per that file's own header (an Astra realism review, 2026-07-20). This batch
supplies narrative field notes and one sourced lore fact per cluster, every claim backed by a
web search performed this session — full per-cluster source list at
[docs/analysis/2026-07-25-card-content-sources.md](../analysis/2026-07-25-card-content-sources.md).

Wired into `SpaceScene.tsx`'s import chain as its **own `.then()` sequenced strictly after**
the base-catalog `Promise.all` resolves — not as one more entry inside that array.
`Promise.all` does not order its own array's module top-level side effects relative to each
other, and this overlay's entire job (overriding ids the base catalog modules add) depends on
every one of them having already run. A literal "add it to the Promise.all list" reading would
have made the override's success a race, not a guarantee.

**Owner approval process, followed as specified, not skipped:** the plan's own gate ("owner
approves each batch before ship; no invented facts, ever") was honored — the overlay was built
and unit-tested but deliberately left **unwired** from the live import chain, staged with its
full source list, until the owner reviewed and explicitly approved batch 1 mid-session
(2026-07-25). Only then was the one-line `.then()` wiring added and the build/gate re-run.
**Batch 2 (the 41+ NGC2000 nebula entries) has not been started** — recorded open per this
repo's honesty convention, not silently dropped.

## Gate-run incidents, root-caused rather than accepted (CLAUDE.md #14/#27)

Two full-suite attempts this session were **invalidated by a self-inflicted instrument
error**, not a product defect: a `npm run build` was run to pick up D4.3's source changes
while an already-in-flight `npm run test:e2e` gate (started for D4.2) was still executing
against the previous `dist/`. Astro's static build overwrote files on disk out from under the
live Playwright run mid-flight — later tests in that run were served a mix of old and
rebuilt files (stale HTML referencing superseded chunk hashes, or vice versa). Symptoms: the
run's own output file was truncated to its last 60 lines (a genuine capture artifact from the
corrupted run, separate from the file-swap itself) and it reported one failure
(`mid-warp-input.spec.ts`, a D3.3 test this slice's diff never touches) that did not reproduce
on a clean re-run. Root-caused via `TaskOutput(block:false)` confirming the run was still
genuinely executing (not hung — the working theory before that check) and via re-running the
full gate with **nothing else touching `dist/` concurrently**, which then completed cleanly.
Lesson, generalizing TR-096's CPU-contention finding: it is not just concurrent _load_ that
invalidates a running gate — concurrently **rebuilding the artifact the gate is serving**
invalidates it outright, and must never happen. No test assertion was loosened; the corrupted
run's results were discarded, not massaged into a passing summary.

A second, smaller incident: two new `collector-card.spec.ts` tests (D4.3) failed on their
first real run, both genuine bugs in the new test code, not the product:

1. "Focus restored to the trigger on close" assumed the vista's `OPEN COLLECTOR CARD ▸` button
   survives closing the card. It doesn't — clicking it dismisses the vista in the same action
   that opens the card, so `restoreFocusTo`'s `isConnected` guard correctly no-ops against a
   detached element (that guard is unit-tested directly in `focus-utils.test.ts`). Fixed by
   asserting the real, honest contract instead: closing never leaves focus orphaned inside the
   hidden dialog — `document.activeElement` lands on `<body>`, the browser's own fallback when
   a focused element is removed from the DOM.
2. "Hovering the parked body shows the renamed CTA" assumed arrival leaves the camera looking
   at exact viewport-center. It doesn't reliably enough — idle drift and the `ARRIVE_STANDOFF`
   approach geometry left it hovering a background SDSS galaxy (NGC 2146) instead of the
   parked body. Fixed with the same `aimAt` + settle-frame + throttle-aware retry technique
   D4.2's own field-travel.spec.ts had already established for the identical class of problem.
