# TR-034 — CI Failing on Unsupported Node Runtime (not the `astro check` hints)

**Date:** 2026-07-19
**Scope:** Owner report — `npx astro check` shows 3 warnings believed to be failing GitHub CI and
blocking the Netlify preview deploy. Also: protect the `main` branch.
**Verdict: OVERALL: READY TO PROCEED**

## The reported cause was not the actual cause

The three diagnostics are real, but they are **hints**, and `astro check` exits **0** with them
present. Reproducing all three CI lint/typecheck steps locally:

| CI step                  | Local result                                 |
| ------------------------ | -------------------------------------------- |
| `npx astro check`        | 0 errors · 0 warnings · 3 hints — **exit 0** |
| `npx prettier --check .` | All files match — **exit 0**                 |
| `npx eslint .`           | Clean — **exit 0**                           |

Nothing there fails a build. Reading the actual run log (`gh run view 29647017980 --log-failed`):

```
Node.js v20.20.2 is not supported by Astro!
Please upgrade Node.js to a supported version: ">=22.12.0"
##[error]Process completed with exit code 1.
```

**Root cause:** `.github/workflows/ci.yml` pinned `node-version: 20`. Astro 7 requires
**≥ 22.12.0**. `astro check` aborts on the version guard _before parsing a single file_ — so the
job failed for a reason that had nothing to do with the code, and the hints were never even
reached.

This had been failing on **every push since at least 2026-07-16** (8 consecutive red runs, each
28–59 s — too fast to have compiled anything). Because `Build` and `E2E` are `needs:`-gated behind
`Type Check`, they never ran at all.

### Same root cause blocked the Netlify preview

`netlify.toml` independently pinned `NODE_VERSION = "20"`. Two separate files, one mistake, two
symptoms — which is why the CI failure and the preview failure appeared together.

## Fix

| File                       | Change                                                                  |
| -------------------------- | ----------------------------------------------------------------------- |
| `.github/workflows/ci.yml` | `node-version: 20` → `22` (all 5 jobs); `checkout`/`setup-node` v4 → v5 |
| `netlify.toml`             | `NODE_VERSION = "20"` → `"22"`                                          |
| `package.json`             | Added `"engines": { "node": ">=22.12.0" }`                              |
| `.nvmrc`                   | New — `22`                                                              |

**Node 22, not 24** (local dev is 24.15): 22 is Active LTS, unambiguously satisfies Astro's floor,
and is the best-supported Netlify runtime. Testing on the declared minimum is also the more useful
signal — it catches anything that only works because the developer is ahead of the floor.

`engines` + `.nvmrc` are the regression guard: the version now has a single declared source rather
than living implicitly in two CI configs that drifted.

The `actions/*` v4 → v5 bump clears the "Node.js 20 is deprecated … forced to run on Node.js 24"
annotation that appeared on every job. It is an annotation today, but a forced break later.

## The three hints (fixed on their own merits, not because CI needed it)

| Hint                                                   | Fix                                                                           |
| ------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `ts(6387)` `document.execCommand` deprecated           | **Fallback preserved.** Routed through a local `LegacyClipboardDocument` type |
| `ts(2568)` `window.CELESTIAL_EXTRA_DONE` may not exist | Declared in `celestial.d.ts` alongside the existing `CELESTIAL_BASE_DONE`     |
| `ts(6133)` `ly` declared but never read                | Renamed `ly` → `_ly` in `rarityFor`                                           |

On the first: `execCommand` is the **catch branch** of a `navigator.clipboard` call — the fallback
for non-secure contexts and older Safari, i.e. exactly where the modern API is missing. Deleting it
to silence a deprecation hint would have removed working behaviour on the browsers the code exists
to serve. The local structural type carries no `@deprecated` tag, so the hint clears while the
runtime path is byte-identical.

On the third: `_ly` rather than deleting the parameter, because these `celestial-*.js` files are
carried verbatim from the prototype and mirror `factFor(tK, n, con, ly, sp)` — keeping the arity
uniform is worth more than one saved argument.

## Branch protection

`.github/rulesets/main-protection.json` — deletion + force-push blocked, linear history, PR
required, all five CI jobs required as status checks, review threads must resolve.

**`required_approving_review_count` is `0`, deliberately.** GitHub does not permit a PR author to
approve their own PR. On a solo repository a value of `1` makes `main` permanently unmergeable —
the rule could only ever be satisfied by bypassing it. `0` still blocks direct pushes, force-pushes,
deletion, and any merge with red CI.

⚠️ **The committed JSON does not enforce anything until it is imported** into repository settings
(Settings → Rules → Rulesets → Import, or `gh api --method POST /repos/:owner/:repo/rulesets`).
The file is the reviewable source of truth, not the live state.

## Process note

The reported symptom ("3 warnings failing CI") and the real defect shared no overlap. Both the
prettier and eslint jobs were green, and the one red job failed on a runtime guard. Fixing the
hints alone would have produced a confident, well-tested change that left CI just as red.

The generalisable point: `astro check`'s summary line said `0 errors` while the terminal above it
rendered three items in warning-yellow. That is a genuinely misleading surface, and it is why the
hints looked like the culprit. **Reading the CI log was a ~30 s step that redirected the entire
task** — worth doing before acting on any inferred cause.

This is the same failure mode as TR-030/TR-032/TR-033, one layer out: there, the _instrument_
misreported; here, the _diagnosis_ was inherited from a plausible-looking local symptom. Check what
the failing system actually says before fixing what looks broken.
