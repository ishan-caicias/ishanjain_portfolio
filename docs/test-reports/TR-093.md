## What this slice is

Owner complaint R6: "decel doesn't slow, abrupt flip." D3.1 fixes the **legibility** half — the
cues that carry perceived braking — leaving the flip choreography itself to D3.2. Astra §3.2:
perceived braking is ~80% two cues (destination angular-size closure-rate ease-out, and the
plume/attitude reversal), all of which must derive from `d(warpEase)/dk`, not `k`. This slice was
briefed by Vega before IMPLEMENT (cinematic slice → SHOT-BRIEF) and audited after (MOTION-AUDIT).

## What shipped

1. **Chase back-distance opens during braking, never looms** (`ship-dynamics.ts` `CHASE_WAYPOINTS`).
   The decel segment previously closed the camera 5.3 → 3.5 → 2.2 across k 0.55→0.92, driving the
   ship **larger than its arrival size** while braking — the CONTRADICTS cue behind R6. It now
   opens to a braking pull-back (**5.8 at k=0.72**, the ship recedes as the retro-burn lights) then
   **monotone-settles** to the arrival framing, staying **≥ `SHIP_VIEW_DEPTH` for the entire brake**
   so the ship never exceeds its arrival size before k=1. The `chaseOffsetAt(1) === [0,0,3]` arrival
   invariant is untouched.
2. **FOV breathing — the missing speed cue** (`warpFovMult` + `_baseFov`). New pure
   `warpFovMult(dsdk) = min(1 + 0.06·dsdk/2, 1.08)`; the camera FOV breathes
   `_baseFov × warpFovMult(dsdk)` each warp frame, peaking +6% at k=0.5 and relaxing to rest across
   the brake. Driven off the **same `dsdk`** as β and the streaks, so no cue can disagree.
   **Integration trap the SHOT-BRIEF caught:** the breathing base is the camera's runtime FOV
   (`_baseFov = camera.fov`, Babylon's ~0.8 rad), **not** `SHIP_BASE_FOV` (70°, a ship-mesh scale
   constant) — the latter would have snapped the lens on warp start. Off under reduced motion;
   reset to base at arrival / idle / ascent.
3. **HUD label "DECELERATION BURN" → "BRAKING BURN"** (`WarpOverlay.tsx`) — the tighter NASA-ops
   cue that matches the picture. The `wphase` phase-boundary computation now sources the shared
   `WARP_ACCEL_END`/`WARP_DECEL_START` constants (was hard-coded 0.47/0.53 literals), so the label
   boundaries can't drift from the hull `flipPhase` and **D3.2's window widening is a one-place
   change**. The `cosmos:warp` `phase` string is unchanged — the event contract stays additive.
4. **`sceneStats()` gains `fov` + `baseFov`** so the lens cue is machine-checkable.

Cue-source verification (D3.1 step 3): streaks (real frame-to-frame camera displacement) and β
(explicit `dsdk`) already derived from the true motion — confirmed, unchanged. Plume intensity is
phase-boolean (burns through decel); its cutoff/relight is **D3.2**, scoped out honestly.

### ⚠ Gate-run incident: one full-suite run was INVALID and briefly looked green

Recorded because it is an instrument failure, not a code failure, and the near-miss is the
lesson (CLAUDE.md "an instrument needs its own validity checks"):

- The first full-suite run reported **31 passed** with **88 error-context attachments**
  (31 + 88 = 119, the whole suite). Every failure was
  `page.goto: net::ERR_CONNECTION_REFUSED at http://localhost:4321/` — the preview server was
  not up. **Nothing to do with D3.1**; no test logic failed.
- **Root cause:** `playwright.config.ts` sets `reuseExistingServer: !process.env.CI`, so locally
  Playwright will attach to whatever already holds 4321 instead of spawning its own. Two stray
  preview processes (`npm run preview` + its `astro preview` child — _not_ Playwright's
  configured direct-bin command, per TR-013) were occupying/cycling that port, so the suite ran
  against a server that wasn't reliably there.
- **The near-miss:** the run was launched as `npm run test:e2e 2>&1 | tail -20`. A shell pipeline
  returns the **last** command's status, so `tail`'s exit 0 masked Playwright's real non-zero
  exit, and the truncated tail happened to show a plausible-looking summary line. It briefly
  read as a pass. **Rule for future gates: never pipe the suite** — redirect to a file and read
  the process's own exit code (`> log 2>&1; echo $?`), and confirm 4321 is free first.
- **Resolution:** stray servers stopped, port confirmed free, full suite re-run with
  `--reporter=line`, output redirected (not piped), and the true exit code captured. That
  re-run is the result recorded above.

**E2E design note — the FOV cue-proof was deliberately NOT put on the flaky GAP-17 test.** The
first draft sampled the FOV inside GAP-17's warp-event loop; isolation ×3 (fail/pass/pass) confirmed
the failure was the **documented GAP-17 flip-skip flake** (TR-081: the ~195 ms flip window is
skipped when a SwiftShader frame runs longer than it — the exact defect D3.2's screen-time floor
fixes; D3.1 does not touch the flip window). Coupling a new cue-proof to a known-flaky test is poor
design, so GAP-17 was restored verbatim and the FOV breathe/relax assertion relocated to the
**stable chase-camera choreography test**, whose peak-FOV tracker only needs the warp to pass
through k=0.5 (every completed journey does) — independent of catching the flip window. 3/3 stable
in isolation.

**What automated coverage proves:** the chase curve opens and never looms (pure unit invariants
over the whole braking range); `warpFovMult` peaks and clamps correctly; on the real render loop
the FOV breathes >+2% over base and relaxes to base at the dock; the HUD shows "BRAKING BURN".
**What needs owner eyes** (per the MOTION-AUDIT): whether the pull-back reads as "easing back" not
"shrinking away", and whether the +2.75°-peak lens breath is _felt_ — subliminal by design.
