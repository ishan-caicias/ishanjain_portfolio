# TR-035 — `TIER low` Interpretation + Backend Missing From the Gate Overlay

**Date:** 2026-07-19
**Scope:** Owner reported the Babylon overlay on a physical Android reads only
`ENGINE BABYLON · TIER low` — no backend. Investigating produced one reassuring finding, one
comparison caveat, and one genuine instrument defect (mine).
**Verdict: OVERALL: READY TO PROCEED**

## Finding 1 — `TIER low` does NOT reduce what Babylon rendered

The immediate worry: if `low` tier cut the scene down, [Round 3](../validation-checklist/2026-07-18-pf09-b1-gate-measurement.md)'s
60 fps was measured on a reduced scene and the condition-1 discharge was premature.

**It did not.** [babylon-engine.ts](../../src/lib/babylon-engine.ts) calls
`buildStarField(LIVE_STAR_COUNT)` unconditionally — `tier` is never consulted on the Babylon path.
`classifyDeviceTier` is documented as "coarse device class for per-tier budget **reporting**", and
actual tier gating is B5 scope ("formalize the per-device tiers"), not yet implemented.

`low` was assigned purely because `viewportWidth < 768` (the phone is 384 CSS px) — a viewport
rule, not a capability judgement.

**Consequence: the Round 3 result is _stronger_ than recorded.** Babylon sustained 60 fps on the
**full 168,959-star field**, on a low-tier phone, under battery-saver throttling. Confirmed live:
`sceneStats()` → `starCount: 168959, totalIndices: 1013754`.

## Finding 2 — the engine comparison is asymmetric, in the CURRENT engine's favour

Worth recording before the 678 ms vs 1745 ms figure is quoted anywhere as like-for-like:

|                           | Current engine (`space-engine.js`)                                                                                                                                | Babylon                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Adaptive quality governor | **Yes** — `this.tier` 0–2, self-downgrades after 70 bad frames, re-upgrades after 900 good ones; scales quality multipliers (0.95/0.8/0.65, 1/0.72/0.5, 1/0.55/0) | **None**                       |
| Craft asset tier          | 1K GLB at `viewportWidth < 768`                                                                                                                                   | n/a (ship not ported until B2) |

The current engine can **buy framerate by shedding quality**; Babylon cannot. Both reported 60 fps,
but only one had that lever. Babylon also isn't yet carrying the ship, so its startup figure is not
yet a complete like-for-like either — a caveat in the _other_ direction, and the reason B2's port
should be re-measured rather than assumed.

Neither observation changes the discharge: the gate asks whether Babylon clears ≥ 40 fps on real
mobile hardware. It does, at full quality, with no governor.

## Finding 3 — the overlay never showed the backend (instrument defect, mine)

[ADR-0003](../adr/0003-babylon-webgpu-renderer-adoption.md) condition 2 is "confirm the WebGPU
backend actually ran". The gate procedure said to read an on-canvas badge — which **does** exist
([babylon-engine.ts:264](../../src/lib/babylon-engine.ts)) and renders
`BABYLON WEBGPU · 168,959 STARS · PF-09 B1` — but it is positioned `bottom: 12px, left: 12px`,
i.e. the opposite corner from the perf overlay the procedure tells you to read. On a 384 px phone
that is easy to miss entirely.

So the owner's report was correct and complete for where they were told to look: the perf overlay
genuinely printed `ENGINE ... · TIER ...` and **no backend field at all**.

### Fix

Backend now renders on the perf overlay itself:

```
ENGINE babylon · WEBGPU · TIER low
```

It shows `BACKEND ?` while Babylon's async init is still resolving, and is omitted entirely on the
WebGL engine (where it is meaningless).

### The fix's own first version was broken — caught by verifying, not assuming

The first implementation read the element via a handle that is **only assigned inside the rAF
loop**. Verified in-browser: the overlay printed `BACKEND ?` while the element reported
`backend: "webgpu"`.

Root cause: `requestAnimationFrame` is throttled to zero in background tabs and heavily under
battery saver, while the HUD's `setInterval` keeps firing. Element resolution was therefore
extracted into `resolveEngineEl()`, which both the rAF loop and the HUD interval call
independently.

**This mattered specifically here:** the owner's readings were taken in battery-saver mode — the
exact condition that would have left the new field reading `BACKEND ?` forever. Verified against
the harshest case (a tab with `host rAF 0`), where it now correctly prints `WEBGPU`.

**Incidental:** this machine's headless Chrome **did** obtain a WebGPU adapter, so the WGSL twin
executed on a real backend for the first time. That is a desktop data point only — it does **not**
discharge condition 2, which asks what the owner's phone negotiated.

## Process note

Three separate near-misses in one report, all caught by checking rather than assuming:

1. `TIER low` _looked_ like it invalidated the discharge; reading the code showed the opposite.
2. The overlay defect was reported as a user observation; it was my documentation pointing at the
   wrong screen corner.
3. My own fix shipped broken and was caught only by loading it in a browser — the failure mode
   (rAF throttling) is invisible to the build, to 92 unit tests, and to 52 E2E tests.

Consistent with TR-030/032/033/034: the instrument keeps being the weak link, and every defect has
been found by checking a claim against reality rather than by testing.
