## What this slice is

TR-095 shipped the D3.3 engine state machine — `flightInputPolicy`, the abort, the retarget
queue — and left it deliberately silent: `cosmos:abort` and `cosmos:retarget-queued` fired into
a void, nothing rendered them. That TR's own "known limitations" named this explicitly and
handed it to a Sonnet 5 pass for "HUD and console strings." This is that pass. No engine code
changes — this is entirely the presentation layer that makes ADR-0010's "never a silent no-op"
acceptance criterion actually true for a visitor, not just true in engine state.

## What shipped

### 1. A transient acknowledgement + a persistent badge — two different questions

The delivery plan names two strings: `ABORTING · RETURNING HOME` and
`RETARGET QUEUED · {name}`. These answer different questions and so are two different pieces of
UI state in `SceneState` (`space/types.ts`):

- **`notice: NavNotice | null`** — "did my press just register?" One-shot, auto-clears after
  `NAV_NOTICE_MS` (2200 ms, SpaceScene.tsx). Fires for BOTH an abort and a queued retarget.
- **`queuedTargetId: string | null`** — "is something still queued?" Persistent — lives for
  exactly as long as the engine's own `queuedTargetId` is non-null, independent of whether the
  2.2s notice has already faded. A queue with no visible trace once the toast clears would just
  be a slower silent no-op, which is the exact failure mode this whole slice exists to kill.

Both render in `WarpOverlay.tsx`: the notice as a pill above the main readout (amber, matching
this repo's existing "actionable" accent), the queued badge as a small persistent line under the
velocity readout. `MissionControlBar.tsx` — the console the visitor was looking at when they
pressed Enter — swaps its `WHERE TO ▸` label to `QUEUED ▸ {NAME}` for the same duration as the
badge, not the notice, so the console stays honest even after the toast fades.

### 2. Clearing the queue: one event in, three ways it can end

`queuedTargetId` in `SceneState` cannot simply mirror `cosmos:retarget-queued` — it has to clear
again, and the DOM event stream doesn't give one single signal for that. Three cases, three
different clearing sites in `SpaceScene.tsx`:

1. **The queued journey actually launches** — the engine's drain fires `cosmos:select` for the
   queued id (no new event type; TR-095's `_beginWarp` already emits it). Cleared in the
   `cosmos:select` handler when `detail.id === stateRef.current.queuedTargetId`.
2. **The queued id turns out to already be the arrival just reached** — the engine's same-id
   no-op case (TR-095 §4's guard: `next !== this.arrivedId`). No `cosmos:select` ever fires for
   this path, so the ONLY observable signal is the `cosmos:arrive` event for that same id.
   Cleared in the `cosmos:arrive` handler under the identical id check, added to every one of its
   four branches (section-match, quiet, dossier-reopen, normal) rather than only the common one —
   a queue that survived the section-match branch because it looked like a different code path
   would be exactly the kind of silent residue this slice is about removing.
3. **An abort discards it** — `cosmos:abort` clears it immediately (synchronous with the press,
   not deferred to the home arrival), matching the engine's own timing from TR-095.

`cosmos:home` clears it too, defensively, so a stale badge can never survive into an idle scene
even if some future caller finds a path TR-095 didn't anticipate.

### 3. `bodyDisplayName` — one lookup, three call sites

The two-step "catalog entry, else station list" lookup existed inline inside `warpDestName`'s
IIFE and nowhere else. The queued-badge text and the mission-console label both need the SAME
resolution for an id that may not be the current `warp.id`, so it became a module-level function
in `SpaceScene.tsx` and `warpDestName` was refactored to call it rather than keep its own copy.
One behavioural difference from the original inline version: an id neither lookup resolves now
falls back to the raw id string instead of `""` — strictly more informative for a notice
("QUEUED ▸ st-unknown" beats "QUEUED ▸ "), and every real caller's id already resolves through
one of the two lookups, so this is not observable for any body or station the site actually
ships.

### 4. Console strings — deliberately minimal, not the D5.2 rewrite

The delivery plan scopes _"the Where-To console's mid-warp state (D5.2) reflects the queue"_ to
its own future phase — a combobox/matching rewrite that doesn't exist yet (`MissionControlBar.tsx`
today is a plain text input with no mid-warp branching at all). Building that now would be
implementing D5.2 ahead of its own slice, using assumptions that slice's own design pass hasn't
made yet. What this pass does instead: submitting a destination into the console mid-warp
**already queues correctly** (TR-095's engine change is orthogonal to this UI), and the console's
own label now visibly reflects that — a one-line acknowledgement where the visitor was looking,
not a rebuild of the surface.

### 5. Test disambiguation the first isolation run caught

The first version of the two new E2E specs matched the queued-badge text with a bare
`page.getByText("RETARGET QUEUED · Procyon")` — which is ambiguous for the ~2.2s the transient
notice and the persistent badge render the IDENTICAL string simultaneously. Playwright's strict
mode correctly refused to guess and failed the isolation run rather than silently picking one.
Fixed by adding `data-testid="nav-notice"` / `data-testid="queued-badge"` to the two elements and
re-pointing the specs at those — a small, permanent testability hook rather than a
looser-matching workaround, since the ambiguity was real (both elements DO show the same text by
design) and will recur for any future spec touching this area.

## Legacy engine / reduced motion

No change to either. The archived WebGL engine has no `queuedTargetId`/`cosmos:abort` to render
against (CLAUDE.md #3/#17 — not ported). The new UI is small opacity/text-only chrome; it follows
this repo's own established precedent for this class of overlay entrance (`ArrivalVista.tsx`,
`CollectorCard.tsx` both ship unconditional `animate-[ij-fadein_...]` with no
`prefers-reduced-motion` branch) rather than inventing a new contract for two small badges.

### Manual verification of the rendering path (not a screenshot — see limitation below)

The Browser-pane harness used for the owner-eyes pass never composites a frame in this
environment: `document.visibilityState` reports `"hidden"` even with the tab fronted, so the
engine's `requestAnimationFrame`-driven render loop never ticks (confirmed via the PreFlight
dossier's own `FIRST FRAME: STALLED` status line) and `computer.screenshot()` times out with
"the Browser pane is not displayed, so the page is not compositing frames." This is the same
constraint TR-095 hit.

What COULD be verified without compositing: `cosmos:select`/`cosmos:warp`/`cosmos:retarget-queued`
/`cosmos:abort` were dispatched synthetically on `window` (the same transport `emit()` uses in
`babylon-engine.ts`), and the resulting DOM was read directly — React's own state commit does not
require a painted frame, only a task-queue tick (confirmed: absent immediately after a synchronous
dispatch, present after a 50ms `setTimeout`, gone again after 2500ms). This proved, against the
real built bundle: the queued badge and console label appear together and read the correct name;
the abort notice appears, reads the correct copy, and the console never shows a stale queue; the
notice self-clears within its budgeted window. What it did NOT prove: pixel layout, animation
timing, color contrast, or how any of this looks alongside the rest of the HUD in a real composited
frame — that remains an owner-eyes item, same as TR-095 left it.

## Known limitations / follow-ups

- **Owner-eyes visual confirmation is still outstanding** — for the same reason TR-095 recorded:
  this harness cannot composite a frame in this environment. Confirmed by DOM state, not by eye.
  What needs a human: does the notice pill's position/styling read well against the rest of the
  HUD, does the console's `QUEUED ▸ NAME` label truncate acceptably on narrow viewports, does the
  2.2s duration feel right.
- **Screen-reader parity is a known, named gap, not a silent one.** `WarpOverlay`'s entire root is
  `aria-hidden="true"` (pre-existing, unchanged by this pass) — the notice and badge added here
  inherit that and are invisible to assistive tech, same as the rest of this component's readouts
  (destination name, phase, velocity). No `aria-live` region exists anywhere in this codebase yet
  for travel/arrival narration; adding one for just these two strings, ahead of the rest of the
  HUD, would be an inconsistent half-measure. Flagged for whenever travel-state screen-reader
  narration is scoped as its own piece of work, not silently absorbed into this one.
- **Funnel instrumentation is still not extended**, and this pass makes that choice explicit
  rather than continuing TR-095's forward-punt. `FunnelEventName` is a closed vocabulary tied
  to the UX research plan's nine named milestones (funnel.ts's own doc comment) — adding
  `abort`/`retarget-queued` entries to it is a research-instrumentation decision, not a string
  display one, and "HUD and console strings" was the scope actually requested for this pass.
  Left for whoever next touches funnel.ts with that broader question in view.
- **D5.2's real console reflection remains its own slice.** The label swap here is a minimal
  acknowledgement, not the combobox rewrite the delivery plan scopes to D5.2.
- **The abort's velocity discontinuity (TR-095's flagged item) is untouched** — out of scope for
  a strings pass; still a candidate for a Vega SHOT-BRIEF.
- **Astra's full-journey REALISM-AUDIT** (the D3 phase's own exit criterion) has not run and is
  unaffected by this pass.
