# TR-059 — P0 fix: Milky Way band crashed the entire WebGPU frame from boot

**Date:** 2026-07-20
**Scope:** Root-cause and fix a real, owner-reported defect: on real WebGPU hardware, the
default Babylon path never rendered a frame at all — blue background, `RENDER FPS 0`,
`rendered · NOT DRAWING` on the `?perf=1` overlay. **Not a TR-058 regression** — reproduced
byte-identical on the pre-TR-058 base commit; present since GAP-03 (TR-057), invisible until
now because nothing had exercised the default engine on real WebGPU hardware for the ~26 frames
this bug needed to surface (see "Why this slipped through" below).
**Verdict: OVERALL: READY TO PROCEED** — **299/299 unit · 71/73 E2E** (same 2
environmental-only `webgpu-hardware.spec.ts` exclusions as TR-056…058), lint clean,
`astro check` 0/0/0, build complete, bundle gate green (+0.1 KB gz).

## The report

Owner ran `npm run build && npx astro preview --port 4400`, opened `/?perf=1` on real WebGPU
hardware: solid blue background, no stars, no animation. The perf overlay read `STARTUP —`,
`RENDER FPS 0 ← RECORD THIS`, `rendered 0 · NOT DRAWING`, while `host rAF 144/149Hz` confirmed
the browser itself was healthy and the requestAnimationFrame loop was ticking — the render
callback was running and failing every single frame, not stalled.

## Root cause

`scene.render()` threw synchronously on **every** frame:

```
TypeError: Required member is undefined.
    at getBindGroups (webgpuEngine.js) ... at InstancedMesh._draw ...
```

The stack trace pointed at an `InstancedMesh` draw (the Havok asteroid rocks), which is what
this session's own sandboxed-browser investigation during TR-058 verification had already hit
and — wrongly — written off as a pre-existing, environment-specific WebGPU limitation (stashing
TR-058's changes reproduced the identical crash on the unmodified base commit, which was true,
but "pre-existing" was conflated with "environment-only"; it is neither only-in-sandbox nor
unfixable). Seeing the same symptom on the owner's real hardware forced a proper re-investigation
instead of standing on that earlier conclusion.

**Live bisection against the owner's running server** (disable every mesh, re-enable one at a
time, re-render after each) isolated the actual offender: **not** the asteroid instances — the
`milkyWay` mesh. Disabling every `InstancedMesh` first and re-testing still crashed identically,
which is what exposed the original stack trace as a red herring (whichever mesh happens to be
first in WebGPU's opaque render-order pass shows up in the trace; it isn't necessarily the mesh
that's actually broken).

**The mechanism:** `_setupMilkyWay` sets `mesh.alwaysSelectAsActiveMesh = true`, so the band's
sphere draws starting frame 1. Its `ShaderMaterial` declares a `uTex` sampler — but the real
equirect texture isn't built until `_tickMilkyWay`'s chunked loop finishes, ~26 frames later
(20 rows/frame against a 512-row grid). For those first 26 frames, **no texture object is bound
to `uTex` at all**. `material.isReady()` returns `true` regardless (the shader compiled fine —
readiness checks shader compilation, not whether every declared sampler has a resource), so
Babylon proceeds to draw. On WebGL2 this degrades to a console warning
(`Texture "uTex" not found in the material context...`) and a no-op draw. On WebGPU, building
the draw's bind group with no resource for that binding is a **hard, uncaught exception** —
`GPUBindGroupEntry.resource` has no fallback — which unwinds out of `scene.render()` entirely.
Every mesh queued after `milkyWay` in that pass never draws either, and the render loop's own
`renderFrames++`/`cosmos:ready` bookkeeping never runs, because it all lives after the (now
unreached) `scene.render()` call.

Confirmed directly on the live scene before writing the fix:

```js
bandMesh.material.isReady(bandMesh, false); // true
bandMesh.material.getActiveTextures().length; // 0  <- nothing bound
```

**Why this repo's other async textures don't have the same bug:** the photo-body atlas
(`new Texture("/assets/atlas.jpg", scene)`) and the nebula raymarch output
(`RawTexture.CreateRGBAStorageTexture(null, w, h, scene, ...)`) both bind a **real texture
object** to their sampler immediately at setup — the image/content loads asynchronously, but the
GPU-side resource for the bind group exists from frame 1. The Milky Way band was the one place
that bound nothing at all until the content was fully ready.

## Fix

`_setupMilkyWay` now creates and binds a tiny 1×1 placeholder `RawTexture` immediately
(`mat.setTexture("uTex", placeholder)`), matching the pattern the photo/nebula textures already
use. `_tickMilkyWay` swaps in the real texture once the chunked build completes and disposes the
placeholder. No visual difference (the band fades in via `uFade` regardless, per its existing
design), zero behavioural change to the build pacing — purely closes the window where the
sampler binding was empty.

## Why this slipped through TR-057/058's own verification

Every E2E pass to date (TR-056/057/058, and this session's own runs) executes against
Playwright's bundled Chromium, which has no real WebGPU adapter and falls back to WebGL2 (TR-039)
— the backend that only warns, never crashes, on this bug. The suite's one real-WebGPU-hardware
spec (`webgpu-hardware.spec.ts`, `channel: "chrome"`) has been blocked all session by the
unrelated port-4321 exclusion (TR-056…058's own documented environmental issue) and — even when
it does run — targets narrower assertions than "let the default scene run 26+ frames and watch
for an uncaught exception." Nothing in the automated suite was positioned to catch this until an
owner actually opened the default engine on real WebGPU hardware. **This is the visual-
verification gap TR-056/057/058 all flagged as outstanding, made concrete.**

## Known limitations

- The underlying `webgpu-hardware.spec.ts` port-4321 blocker (TR-056…058) is still open; it
  would have caught this class of defect in CI and didn't. Recommended follow-up: get that spec
  running against the shared `baseURL` fixture (or investigate why this machine keeps landing
  a WSL2 port reservation over 4321) so full-boot real-WebGPU coverage isn't dependent on an
  owner manually loading the page.
- No other `ShaderMaterial` in this codebase has an unbound-sampler-at-setup pattern (checked:
  photo bodies, nebula, star trails, curated bodies, embers all bind a real texture object
  immediately or declare no sampler at all) — but this class of bug (declared sampler, deferred
  content, WebGPU-only hard failure) is now a named risk for any future async-texture feature;
  worth a line in the graphics-engineering reference for the next one.
