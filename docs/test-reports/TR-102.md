## Fix 1 — arrival camera doesn't aim at the body (owner items #2 and #4, one root cause)

**Symptom, as reported:** (a) arriving at Mars left the camera pointing away from the planet;
(b) after dismissing the arrival vista or closing the collector card, the body just traveled to
was off-screen — should stay visible so dismissing either surface still shows what was arrived
at.

**Root cause (`babylon-engine.ts`):** `travelTo` already computes the correct arrival
_position_ — `w.to`, `ARRIVE_STANDOFF` (38 units) back from the body along the Sun→body ray —
and `_tickWarp`'s `k >= 1` arrival branch correctly snaps `this.cam` to that point. But
_orientation_ was left wherever the chase-look `quatDamp` had converged to during the flight, a
function of the **travel direction** (`wd`, i.e. `from`→`to`), not the direction from the
now-snapped standoff point to the body itself. Those two directions only coincide when the
ship approaches dead-on; from any other approach angle, position and orientation disagree and
the body can land off to the side or fully out of frame. Neither dismiss handler
(`SpaceScene.tsx`'s `dismissVista` / the card's `onClose`) touches the camera at all — by
design ("ship stays parked exactly where it landed") — so a bad arrival aim simply persisted
through both, which is exactly why items #2 and #4 are the same bug reported from two angles.

This was already understood at the code level: a `?testhooks`-only `aimAt(bodyId)` method
exists with a comment describing this precise failure mode, but it was never wired into the
real arrival path — only reachable from a harness.

**Fix:** in the `k >= 1` arrival branch's `w.target` case, compute the unit vector from the
now-snapped camera position to the body's world position (identical math to `aimAt()`), set
`_yaw`/`_pitch` from it (so later idle-branch frames stay consistent — the idle branch
recomputes `_camQuat` from `_yaw`/`_pitch` every frame), **and** set `_camQuat` directly in the
same tick so there's no one-frame pop. `w.home` arrivals are untouched — the home orbit has its
own dedicated look-at-Earth system (R16) that was already correct.

**New E2E coverage:** `tests/e2e/collector-card.spec.ts` — "arrival itself aims the camera at
the parked body — no `aimAt` needed (TR-102)". Travels to Sirius, dismisses the vista via
Escape, and hovers at exact viewport-center **without ever calling `aimAt`** — the sibling test
right above it in the same file had to call `aimAt` explicitly specifically because this bug
existed; the new test proves the real fix without that crutch. Isolated 4/4 clean (1 run + 3
repeats) before the full gate.

**What this does NOT fix:** the owner's "zoom out a little... so the star field is also
partially visible" is a separate, related ask about the arrival _distance_, not just the aim
direction — reported on separately below, not implemented this pass (see Completion Summary).

## Fix 2 — classic-view scroll jank (owner item #6)

**Symptom, as reported:** classic view works but scrolling isn't smooth.

**Root cause (`SpaceScene.tsx`):** a `requestAnimationFrame` loop positions the 7 station
sprites every frame, gated on `engineReady` only — **not** on travel-vs-classic-view mode. Its
sprite-visibility calculation already requires `travel` to ever show anything
(`show = travel && ...`), so in classic view every sprite is always hidden — but a separate
"dodge the hero copy" computation upstream of that check ran regardless, gated only on
`atHome` (camera near origin), independently of `travel`. That computation calls
`getBoundingClientRect()` three times (`h1`, `badge`, `heroCopy` itself) — each one forces a
synchronous layout flush — **every single animation frame**, including while the visitor is
mid-scroll in classic view, which is exactly when forced layout is most expensive and most
visible as jank.

**Fix:** gate the `heroCopy` lookup (and its three bounding-rect reads) on `atHome && travel`
instead of `atHome` alone. Zero behavior change in travel mode — the dodge calculation was
already unreachable in classic view (`show` requires `travel` regardless of `dodge`), so this
purely removes wasted work, never a case where classic view. This is a partial fix: it removes
the specific layout-thrash cause found this pass. A deeper root cause — the Babylon render
loop's own per-frame tick functions (`_tickWarp`, `_tickMilkyWay`, `_tickTrails`, etc.) running
unconditionally in classic view, only cadence-halved past 55vh scroll — is the **already-tracked,
partially-fixed GAP-13** (`docs/analysis/2026-07-19-webgl-babylon-cutover-gap-analysis.md`);
closing it further is a larger, separate engine-tick-throttling change, not attempted this pass.

**No new test added:** this is a removed-computation change with no new observable behavior in
any mode the existing suite already exercises (dodge was already unreachable in classic view);
the existing mobile-responsive/classic-view specs (space-scene.spec.ts) continue to pass
unchanged and are the regression backstop.

## Known limitations / follow-ups (recorded here, expanded in the Completion Summary)

- **Arrival standoff distance** ("zoom out a little" so the star field is visible alongside a
  planet): `ARRIVE_STANDOFF` (38 units) is shared verbatim with the ascent cinematic's end
  distance and the home-orbit radius (both unit-tested as exact equalities to it), and feeds
  the virtual-texturing patch-visibility budget (`visiblePatchDegrees`). At the current
  distance a `PLANET_SPHERE_RADIUS=26` sphere already subtends ~86° of frame. Changing it
  safely requires either a genuinely new, decoupled planet-class distance (leaving ascent/home-
  orbit/VT untouched) or a coordinated change across all three — not attempted this pass.
- **User-adjustable zoom control** (owner item #3) — new feature, not scoped this pass.
- **Babylon.js 8.56.2 → 9.2.1 upgrade** (owner item #7) — confirmed 9.2.1 is a real, current
  stable release with genuine relevant gains (Frame Graph v1, ~40% GPU memory savings in some
  scenarios per Babylon's own 9.0 announcement, clustered lighting, Havok FloatingOrigin
  Multi-Region), but this is a full rendering/physics-stack version bump requiring its own
  spike (shader-twin compilation, thin-instance/Havok compatibility, tree-shaking/budget
  impact) and an ADR per this repo's documentation contract — not attempted this pass.
- **Local star-field density vs. far field** (owner item #1) — likely already addressed by
  PF-11's own planned D8 phase (Gaia DR3 Tiny, all 2,552,302 stars, per ADR-0010's D8.1
  decision) — not a new gap, a not-yet-reached phase.
