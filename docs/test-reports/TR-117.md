## What this pass found and closed after the workflow

Two implementation-phase agents each independently flagged, but did not act on, a live
inconsistency: the P2b magnitude-formula change updated the _encode/decode constants_ in
several pipeline scripts but the workflow's scope explicitly excluded running two of the
costlier regenerations. Left as-is, this would have been a real, silent visual regression —
worse than PF-11 was before this pass, which the owner explicitly ruled out ("the system should
improve not get worse"). Closed before the gate above ran:

1. **`public/assets/sdss18.png`** (47 MB, the shipped SDSS DR18 galaxy field, C2) — regenerated
   via `node scripts/gaia-sdss18-pngpack.mjs --out public/assets/sdss18.png` (3,637,836 real
   rows, 868ms). Record count unchanged; only the per-row magnitude byte changed, correcting a
   live dimming (byte 60 was decoding as mag ~14.47 instead of the intended ~9.21 under the new
   formula until this ran).
2. **The 8 `public/assets/gaia-tiny-NN.png` chunks + manifest** (PF-11 D8, ADR-0012) —
   regenerated via `npm run gaia:tiny` (2,465,763 records across 8 chunks, ~6s). Same class of
   fix; chunk sort order (by real `appMag`, computed before byte-encoding) is unaffected, so
   ADR-0012's magnitude-sorted-chunk-prefix invariant survives untouched.
3. **`budgets.config.mjs`** — both regenerations changed on-disk byte counts slightly
   (`sdssField` +40 bytes, `gaiaTiny` +408,435 bytes — real per-row bytes spreading across the
   format's wider range, same effect as the `bonusStars` fix above). Updated `layerBytes` to
   match, plus `totalMB` (291.9 → 294.5) and `groupsMB."(root)"` (95.0 → 95.6) to absorb the
   real, deliberate growth from this pass (Sun texture +0.96 MB, 25 new DSO4 photos +1.06 MB,
   the two regenerations' compression-noise deltas) — each with a dated justification comment
   per this file's own convention, re-verified green after.
4. **`groupsMB.dso4: 1.1`** added — `check-bundle-budgets.mjs` itself flagged `assets/dso4` as
   unbudgeted (informational, not a failure) after the image-fallback phase added it; gated now
   per that tool's own suggestion.

## Open items needing owner input

1. **DSS2/CDS survey-plate license risk (P1).** The image-fallback phase verified this live
   (archive.stsci.edu/dss, CDS hips2fits docs, VizieR/Aladin terms) and found no explicit
   third-party redistribution grant — DSS plates are copyrighted by AAO/Caltech/AURA/PPARC and
   "distributed... by agreement." Recorded as an owner-flagged risk in
   `docs/research/texture-sources-public-domain.md` §14 (same treatment as the existing Gaia
   DR3 §6 entry), **not** silently treated as public domain. The 25 fetched images
   (`public/assets/dso4/`) are shipped pending this decision. Options: accept the risk as-is,
   seek a cleared alternative source, or hold `dso4` back from the live site until resolved.
2. **White-dwarf visual body was not built (P2b scope reduction).** The owner's chosen option
   was "full rescale + real body." What shipped: the magnitude rescale (full), and white dwarfs
   now promote into `this.bodies` on first visit (real position, correct arrival standoff,
   precise pickable, travelable, survives mid-warp retarget-queueing) — but no new visual mesh.
   They still render as the same point-sprite in the shared star-field buffer, just at their
   now-correct (much brighter) byte. The design spec's diffraction-spike beacon-mesh proposal
   was explicitly deferred by the implementation phase as too high-risk to build without visual
   verification in an unattended pass. The design phase's own photometric finding is worth
   restating: even at a _correctly_ encoded magnitude, the point-sprite model structurally
   caps out around ~15% alpha / ~8px for a genuinely faint point source — a dedicated beacon
   mesh is the only mechanism that would make white dwarfs obviously visible, not optional
   polish. Confirm whether that follow-up is wanted.
3. **Minor-planet photo exclusion (P1).** The 4 `celestial-minorplanets.js` objects were
   excluded from the real-photo fetch — their tabulated ra/dec is a moving-target snapshot, so a
   static DSS2 plate would show unrelated background stars, not the asteroid, and (combined with
   `t:"dwarf"`) would incorrectly route them onto the sphere-render path. They keep the new
   procedural `asteroid` treatment instead. Confirm or override.
