## What was built

- **`scripts/lib/votable-binary2.mjs`** — a VOTable 1.3 BINARY2 reader. Real finding, not
  assumed going in: the Gaia Sky cluster/star catalogs (`catalog-mwsc`, `catalog-clusters-hunt-reffert-2023`,
  `catalog-cns5`, `catalog-nbg`, `catalog-ocdr2`, all four SDSS packs) do **not** ship plain JSON
  records — their `particles-*.json` files are Gaia Sky app config pointing at a `.vot` file; the
  real per-object data is a CDS/VizieR-exported VOTable using base64-encoded **BINARY2**
  serialization (per-row null bitmask + big-endian primitives), not the more common
  human-readable `TABLEDATA` form. Confirmed by reading the raw file (`grep` for `<TABLEDATA>`
  found nothing; `<BINARY2>`/`<STREAM encoding='base64'>` did). The reader parses `<FIELD>`
  declarations for schema, then decodes the stream — `long`/`int`/`short`/`float`/`double`/`char`/
  `char*` (variable-length, 4-byte length prefix), deliberately narrow to the datatypes present in
  this repo's local dataset packs rather than the full VOTable type system.
- **`scripts/gaia-dataset-pipeline.mjs`** — CLI converter, `--dataset <key> (--names "A,B,C" |
--sample N) [--out path]`. Maps decoded rows into the exact `celestial-gaia.js` record shape
  (`id`/`n`/`d`/`t`/`r`/`ra`/`dec`/`ly`/`mg`/`sp`/`img`/`c`/`con`/`st`/`f`/`lo`).
- **`scripts/run-gaia-pipeline.ps1`** (primary — this repo's Windows dev box) and
  **`scripts/run-gaia-pipeline.sh`** (bash/CI equivalent) — thin local wrappers so bulk
  decode/inspect runs happen outside a chat/agent session, per the owner's explicit ask not to
  spend session tokens rendering large batches.
- `npm run gaia:pipeline` added to `package.json`, matching the existing `assets:craft`/
  `budget:check`/`docs:check` script convention.

## Proof against real data, not synthetic fixtures

Ran against the actual local `catalog-mwsc/mwsc/catalog-mwsc.vot` (Kharchenko et al. 2013,
Milky Way Star Clusters catalog): decoded **3,006/3,006 rows in 145 ms**, matching the file's own
declared `nParticles`. Verified the PowerShell wrapper end-to-end too (`run-gaia-pipeline.ps1
-Dataset mwsc -Sample 2`), not just the underlying Node script.

Converted 3 named clusters and checked the output against known real astronomy, not just schema
validity:

| Cluster (catalog name) | Common name              | Decoded RA / Dec  | Decoded distance | Real RA / Dec / distance    |
| ---------------------- | ------------------------ | ----------------- | ---------------- | --------------------------- |
| `Melotte_22`           | Pleiades (M45)           | 56.505° / 24.37°  | 424 ly           | ≈56.75° / ≈24.1° / ≈444 ly  |
| `NGC_2632`             | Praesepe / Beehive (M44) | 130.095° / 19.69° | 610 ly           | ≈130.0° / ≈19.6° / ≈577 ly  |
| `NGC_1912`             | M38                      | 82.215° / 35.8°   | 3,731 ly         | ≈82.0° / ≈35.8° / ≈3,750 ly |

All three within a few percent on position and the right order of magnitude on distance (MWSC is
a 2013 catalog; small deltas from modern Gaia-DR3-refined values are expected and not a pipeline
defect). This is the concrete evidence behind the C1 plan update: these three are the named
clusters referenced in [PF-10's C1 hybrid decision](../delivery-plan/PF-10-gaia-dataset-realism.md#phase-c1--missing-objects).

## What the pipeline deliberately does NOT fabricate

`con` (constellation) emits the literal `"—"` placeholder `celestial-gaia.js` already uses for
`moon-topo`/`mars-topo` when it isn't computed — not a guessed or omitted value passed off as
real. Narrative fields (`f` flavour text, `lo` lore entries) emit an explicit
`[[TODO: content pass — ...]]` marker. Neither is real astronomical data, so neither gets
invented prose dressed up as one. A human content-authoring pass is a named, separate step in
PF-10 C1, not something this script self-authorizes.

## Honest limits

- Track B (PNG-pack background layer) is unstarted — needed for C2 (SDSS DR18) and C1 (white
  dwarfs). The BINARY2 reader is a real prerequisite (SDSS uses the same format) but a 3.6M-row
  file needs a streaming decode, not the whole-file-in-memory approach that was sufficient to
  prove Track A at MWSC's 3,006-row scale.
- Coordinate conversion (RA/Dec → Cartesian) and photometric shading are deliberately **not**
  reimplemented here — the existing, already-verified runtime path
  (`ship-dynamics.ts`'s `raDecToDir`/`bodyWorldPosition`, PF-09 TR-040) consumes `ra`/`dec`/`ly`
  directly, so this pipeline's job stops at emitting those fields correctly, which is what was
  proven.
- Only MWSC was exercised end-to-end; Hunt-Reffert 2023 is wired into `DATASETS` but not yet run
  against real rows in this pass.
