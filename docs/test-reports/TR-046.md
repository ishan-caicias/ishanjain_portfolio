# TR-046 — B3 volumetric/raymarched nebulae: WebGPU compute primary + WebGL2 fragment fallback

**Date:** 2026-07-19
**Scope:** PF-09 B3, owner-selected next increment ([delivery plan](../delivery-plan/PF-09-babylon-havok-realism.md)
B3 section): volumetric/raymarched nebulae on the Babylon path. Four raymarched gas volumes
anchored at real catalog nebulae (`m42` Orion, `ngc7293` Helix, `veil`, `rosette`), tier-gated per
B3's exit criterion: **WebGPU raymarches in a compute shader** (Babylon `ComputeShader` → half-res
rgba8 storage texture); **WebGL2 runs the same raymarch as a `ProceduralTexture` fragment pass**
(no compute API on WebGL2). One fullscreen triangle composites the texture additively on either
tier. Architecture recorded in [ADR-0004](../adr/0004-volumetric-nebulae-compute-raymarch.md).
**Verdict: OVERALL: READY TO PROCEED** — 164/164 unit · 62/62 E2E (incl. real-WebGPU hardware,
clean console) · build/lint/typecheck exit 0 · real-hardware screenshots confirm the volumetric
look on the compute tier.

## What was verified as NOT a port (the TR-044 discipline)

Grepped `space-engine.js` before writing code, as the plan's B3 note instructed: the live engine's
nebulae are **2D billboard sprites** — lobed gaussians in the celestial point-sprite fragment
shader (`space-engine.js:273`, type-2 catalog objects). Nothing volumetric, raymarched, or
3D-positioned exists there, and the Babylon path had no nebula visual at all (grep across `src/lib`
matched only `ship-dynamics.ts` comments). New work with a named 2D reference, not a port.

## Design facts a future session needs

- **Single source of truth:** `nebula-field.ts` holds volume placements, march tuning
  (`NEBULA_MARCH`), JS mirrors (hash/noise/fbm, ray-sphere, density, front-to-back march), and
  the **generators** that bake every constant into both shader sources. No per-volume uniforms, no
  UBO array layout to desync. Dynamic uniforms are camera basis + tanFov/aspect + time only.
- **Anchoring:** volume centres use `bodyWorldPosition(ra, dec, ly)` — the identical function
  `travelTo()` uses — so travelling to `m42` flies the camera _into_ the Orion volume
  (ARRIVE_STANDOFF 38 < radius ≈77, deliberate: the arrival view is inside the gas). Unit tests
  pin volume centres to the catalog entries' ra/dec/ly.
- **Steps/resolution tiering:** compute 40 steps, fragment 18 steps, both at half render
  resolution (`NEBULA_TEX_SCALE`), recreated (compute) or `resize()`d (fragment) on canvas resize.
- **V-orientation contract:** the GLSL pair (ProceduralTexture RTT + GLSL composite) uses no
  flips; the WGSL pair flips V in both the compute writer and the WGSL composite sampler. Each
  backend pair is self-consistent; unit-tested as a structural assertion.
- **Reduced motion:** `uTime` pins to 0 — the slow fbm domain drift freezes, the gas stays
  visible as a static sky feature.

## The defect found and fixed during VERIFY

First full-suite run on real WebGPU hardware: `activeIndices: 0`, `renderFrames: 0` — the render
loop was dead. Root cause: **`@babylonjs/core`'s tree-shaken WebGPU engine loads compute support
from a side-effect extension module** (`Engines/WebGPU/Extensions/engine.computeShader`) which
`webgpuEngine.js` does **not** auto-import (it does auto-import `engine.rawTexture`, which is why
the storage-texture creation succeeded and the failure landed one line later). `new
ComputeShader(...)` threw `createComputeContext is not a function` inside `_boot`, killing the
loop before the first frame. Fix: dynamic-import the extension alongside the engine in
`createEngine()`'s WebGPU branch — WebGPU code stays out of the eager WebGL2 bundle. Found by the
suite, not by an owner report — the TR-045 gap-closure (console assertions + real-hardware spec)
did its job this time.

Also fixed during VERIFY: one new unit test initially asserted `raySphere` returns `null` for a
sphere behind the ray; the actual (correct) contract is infinite-line intersection with negative
`t` culled by the march and both shader twins. The **test** was wrong, not the code; rewritten to
assert the real contract. Declared here per the no-unexplained-test-modification rule.

## Honest limits

- **Visual tuning is first-pass.** Inside a volume the gas reads dense/washed-out near arrival
  (approach screenshot ~85% warp shows near-full pink coverage). All knobs are in `NEBULA_MARCH`;
  owner taste pass expected. The exit criterion ("reads as real volumetric FX; fallback coherent")
  is met; "beautiful at every camera position" was not claimed.
- **The in-app browser pane stalls at `renderFrames: 0`** on its software-WebGPU adapter — loop
  registered, manual `scene.render()` fine, `frameId` never advances (rAF never pumps the engine).
  Same false-alarm class as TR-040's Electron-pane investigation: environment, not code — real
  Chrome on the same machine renders 700+ frames clean. Recorded so nobody re-diagnoses it.
- Nebula visibility from home depends on bearing (the four volumes sit at their true RA/Dec);
  the home screenshot faces RA 3h and legitimately shows none.
- Perf on real mid-tier mobile WebGPU is unmeasured (B2's own re-measurement condition is still
  open); the compute pass adds ~256k rays × ≤40 steps at half-res. B5's tier system is the named
  home for per-device step/resolution scaling.
