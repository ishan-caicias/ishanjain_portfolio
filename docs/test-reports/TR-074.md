# TR-074 — PF-10 C3: the full real Gaia DR3 asteroid belt replaces the procedural one

**Date:** 2026-07-20
**Scope:** PF-10 phase C3 — replace `babylon-asteroids.ts`'s seeded-LCG procedural torus with the
real Gaia DR3 asteroid catalog (154,662 real objects with real Keplerian orbital elements), as a
two-tier split: a full-catalog non-physical visual layer plus a bounded, real-catalog Havok physics
subset. Astra produced a real science brief before implementation
(`docs/analysis/2026-07-20-dr3-asteroid-belt-science-brief.md`); three of its findings changed what
shipped, one is recorded as an open owner decision.

**Verdict: OVERALL: READY TO PROCEED** — see Part 7 for the exact counts and the one thing this
pass explicitly does NOT prove.

---

## Part 1 — What the data actually turned out to be

Nothing here was assumed from the plan; each was measured against the real local file.

**A fifth local serialization.** PF-10 has now met VOTable BINARY2 (TR-061), VOTable TABLEDATA
(TR-065), FITS binary tables (TR-063), and Gaia Sky's own `BinaryPointDataProvider` format
(TR-066). The asteroid packs are none of those: they are plain, pretty-printed JSON. That sounds
like the easy case and is not — `asteroids-dr3.json` is **150.7 MB**, where `JSON.parse`
materializes the whole object graph at once, exactly the allocation pattern TR-066's SDSS work
established as the thing to avoid. `scripts/lib/gaiasky-orbit-json.mjs` streams it instead: a
string- and escape-aware brace-depth scanner that emits one small parsed record at a time, with one
1 MB chunk retained rather than one catalog. Real measured run: **154,662 objects in ~2.0 s**.

**Record count, corrected three times.** `dataset.json` advertises 154,787. A first chunked key
census suggested 154,635 (the regex was being split across stream chunk boundaries — an unreliable
method, discarded). The real full stream reports **154,662 objects, every one carrying complete
orbital elements, 0 skipped**. Astra independently measured the same 154,662. That is the number
used everywhere downstream.

**No photometry, verified rather than assumed.** A key census over the real file finds exactly
`name`, `color`, `parent`, `impl`, `provider`, `ct`, `transformFunction`, `orbit{epoch,
meananomaly, semimajoraxis, eccentricity, argofpericenter, ascendingnode, period, inclination}`,
`onlybody`, `newmethod`. There is **no magnitude, no diameter, no albedo and no rotation data**
anywhere in the catalog. Consequences are handled honestly in Part 3, not papered over.

**Per-object epochs matter more than expected.** The catalog carries **945 distinct epochs**
spanning **JD 2456876.5 – 2457888.5** — a 2.8-year spread, not the ~4 months a first sample
suggested (Astra's correction). Propagating every object from its own real epoch, as designed, is
therefore not a nicety: a single common epoch would smear objects by up to 2.8 years of mean
motion.

## Part 2 — The two-tier split, and why it is not a sampling convenience

154,662 Havok rigid bodies is ~3,200× the current tier budget. This is a frame-time impossibility,
not a data-handling preference, and the plan named the split in advance.

**Visual layer — all 154,662.** Positions solved per object via a real Kepler state solver
(`scripts/lib/asteroid-kepler.mjs`), packed into `public/assets/asteroids-dr3.png` (2.0 MB) in the
exact 15-byte layout `star-catalog.ts` already decodes, and rendered on its own mesh by
`_loadAsteroidVisualLayer` — modelled line-for-line on `_loadSdssGalaxyLayer` (fetch after
`cosmos:ready`, idle-gate before the geometry build, graceful failure), because that pattern is
proven and this layer has the same shape of problem.

It needs its own mesh for the same reason SDSS does: these positions are in the **belt's own
world-unit frame**, not the star field's linear-light-year convention. Merging them into one
`decodeStarCatalog` call would silently corrupt whichever convention lost.

**Physics layer — bounded, and unchanged in size.** Tier body counts stay at 20/32/48. The budget
is a frame-time fact, so the real catalog changes **which** rocks exist, not how many. The subset
lives in the generated `src/data/asteroids-dr3-physics.ts` — a TypeScript module rather than JSON
or a fetch, so the field can never be half-built because a request was in flight, and so no
`resolveJsonModule` dependency is introduced.

**Object-type byte 6 was already waiting.** Both shader twins' vertex stage already carried
`else if (ty < 6.5) { px *= 0.85; } // DR3 asteroid` — a slot reserved by earlier PF-10 work and
never filled. C3 fills it and adds the matching fragment branch in both twins
(`exp(-d*d*9.0)*0.70` — tight, no bloom, so 154,662 additive specks read as rock dust rather than
a second star field). Pinned by a source-text unit test asserting both twins carry the branch
**and** that it precedes the open-ended `ty > 6.5` oort catch-all, since that ordering is
load-bearing.

This also surfaced a real documentation defect: `star-catalog.ts`'s object-type-byte legend still
described bytes 2/4/5/6 as "UNDOCUMENTED/UNUSED". All four have had real shader branches since
later PF-10 work. Corrected additively (the stale claim is kept as written, with a dated
correction above it), per this repo's convention.

## Part 3 — Astra's brief changed what shipped

Delegated per Procyon's own doctrine before implementation, not after. Three findings were applied
directly.

**The colour byte was wrong.** The first draft used byte 214 (ramp t ≈ 0.85), which the Planckian
O→M ramp renders as RGB (1.00, 0.81, 0.53) — B−V ≈ 1.4, about 4000 K, **a K5–M0 star**. Real
main-belt asteroids are a C-type (B−V ≈ 0.70) / S-type (≈ 0.85) mix with a magnitude-limited mean
of ≈ 0.80, barely redder than the Sun's 0.65; Vesta and Ceres are famously grey. Changed to
**byte 173** (t ≈ 0.68). This is exactly the class of error a plausible-looking guess produces and
only a real audit catches — the first draft would have shipped an ember-coloured belt.

**The magnitude byte moved to the format's floor (byte 0, mag 12.5).** Astra's point: even that
floor is 3–5 magnitudes brighter than a real main-belt asteroid, so the dimmest byte the shared
format has is the only honest choice. The draft's byte 24 was gratuitously bright on top of an
already-generous floor.

**The physics-subset selection was epoch-dependent, and shouldn't have been.** The first draft
ranked candidates purely by snapshot position relative to the belt spine — which silently makes
the belt's physics roster a function of the date the script happened to run. Replaced with Astra's
epoch-independent real orbital-element cut: **a ∈ [2.60, 2.75] AU, e < 0.10, i < 5°**, the
catalog's own density peak restricted to near-circular, near-coplanar orbits (2,339 real
candidates), with spine proximity used only to order within that set. The element bounds are not
tuning knobs: e < 0.10 at a ≈ 2.7 AU produces radial excursions of about ±17 world units and
i < 5° about ±14.9 — which is independently where the belt's existing tuned spread numbers came
from.

**Cleared by the brief, with real arithmetic:**

- **Vis-viva confirmed exactly.** 18.126 km/s at 2.7 AU × the declared scale × TIME_ACCEL = 4e5
  gives **3.053 world units/s**, inside the belt's existing tuned 1.5–4.5 drift range. Astra
  classifies uniform time acceleration as ACCURATE rather than a licence: it is a redefinition of
  the time unit, Kepler's third law survives exactly, and the differential shear between inner and
  outer asteroids stays real.
- **Two-body propagation ~10 years past epoch: SIMPLIFIED, ship it.** The error is almost entirely
  along-track and works out to **0.4–4 world units** — smaller than one rendered rock, along the
  one axis where the belt is axisymmetric. a/e/i are not propagated at all.

## Part 4 — The one real defect, recorded rather than resolved

**The belt's frame is 23.44° off the real zodiac.** The scene's X–Y plane is DECLARED to be the
ecliptic; the rest of the catalog (stars, DSOs) is equatorial. Gaia Sky's own dataset ships
`"transformFunction": "eclipticToEquatorial"` on every object — its own instruction to rotate.
Astra's measurement: ~47 full-Moon diameters of displacement at the solstitial points. Visible to
anyone who knows where the ecliptic runs through the constellations.

It is **not fixed by default**, and the reason is not the rotation — that is nine multiplies, and
`--frame equatorial` performs it today. It is that `babylon-asteroids.ts`'s entire belt model
(spine circle, herding pull, gaussian density, warp slowdown, passage deflection, and the
deliberately-chosen m42 showcase-route crossing documented in `ASTEROID_BELT`'s ORIENTATION note)
is defined in the X–Y plane about world Z. Rotating only the data tilts the real belt out of the
frame those act in: the spine circle would intersect the belt at two nodes instead of ringing it,
the density falloff would register almost nowhere, and the physics bodies would be herded steadily
out of their own real orbital plane.

Doing it properly means re-expressing the belt model itself in an inclined basis. That is real,
bounded work and a goal-1 (realism) versus tuned-and-E2E-guarded-interaction call. **It belongs to
the owner, not to a silent default**, so it is written into the delivery plan as an open decision
with the fix path and its cost stated.

## Part 5 — Proof the belt is real, not procedural

The strongest available check, and the one Astra recommended building the test around: **assert gap
LOCATION, not depth.** A noise function can fake a notch; nothing procedural puts four independent
minima at (n_J/n)^(2/3) · a_J.

Measured by the pipeline over the real computed elements:

| Resonance | a (AU) | Bin count at resonance | Local density | Depletion |
| --------- | -----: | ---------------------: | ------------: | --------: |
| 3:1       |   2.50 |                  5,578 |        10,842 |    to 51% |
| 5:2       |   2.82 |                  2,248 |         7,090 |    to 32% |
| 7:3       |   2.95 |                  4,830 |         5,400 |    to 89% |
| 2:1       |   3.28 |                    207 |         4,368 |     to 5% |

The 7:3 gap is genuinely narrower than the 0.05 AU histogram bin and so reads shallow here — an
honest artefact of the bin width, not a missing gap. Astra's own finer-grained measurement on the
raw elements puts the minima **exactly on** the resonances with far deeper depletion (3:1 at 2.500
AU depleted 100×, 5:2 at 2.825 AU 21×, 2:1 at 3.289 AU 200×), plus the Hilda island (569 objects at
3.87–4.05 AU), a 6-object void across the entire 4.05–5.00 AU gap, and 1,545 Trojans at 5.2 AU.

This structure is emergent from real orbital elements. It is not drawn, and it could not be.

**End-to-end traceability check, run independently of the pipeline.** One shipped physics record
was re-derived from scratch — streaming the raw 150.7 MB catalog for its entry, solving Kepler
again, mapping to world units — and compared against the generated module:

```
raw catalog "heco": epoch 2457384.5, a 403,937,554.8 km, e 0.007140848, i 1.2437752°, ...
re-derived position: [140.389827,  96.080675, -13.068068]
shipped module says: [140.389827,  96.080675, -13.068068]     ← identical
re-derived velocity: [ -1.741961,   2.506646,  -0.066252] → speed 3.0532 world units/s
```

Two things this pins. The generated module is genuinely the pipeline's output and has not gone
stale or been hand-touched. And that speed — **3.0532** for a real 2.700 AU orbit — lands on
Astra's independently-computed 3.053 prediction to four significant figures, which is the
declared time-acceleration arithmetic confirmed against an outside calculation rather than
against itself.

## Part 6 — What was NOT done, stated plainly

- **The visual layer is a static real snapshot.** The 154,662 specks do not orbit; the physics
  subset does. Animating them would need a time uniform and per-vertex orbital elements in the
  shared `ijStar` shader — a real change to a shader four other layers depend on, deliberately not
  smuggled into this phase.
- **Trojan and NEA packs not merged.** `catalog-asteroids-dr3-trojan` (1,545) and
  `catalog-asteroids-dr3-nea` are separate local packs; the main DR3 catalog already contains 1,545
  Trojans and 108 NEOs by Astra's count, so merging risks duplicates without a dedup pass. Out of
  scope, named.
- **Belt spread constants left alone.** Astra notes the real mean inclination of 9.45° gives a
  vertical spread of ~±28 world units against `WARP_FIELD.densitySigmaVertical` = 20, so
  high-inclination asteroids get slightly less warp slowdown than the belt's centre. The belt is
  genuinely a fatter torus than the procedural one was, and that puffiness is authenticity. Retuning
  the density sigmas would move a tuned, E2E-guarded interaction; left as a follow-up.
- **No real-device frame-budget measurement.** See Part 7.

**New unit coverage (+27)** deliberately spans three different kinds of proof rather than 27
variations of one:

1. The streaming reader against the cases a real 150 MB pretty-printed catalog contains — records
   split across chunk boundaries (fed a chunk at a time, because a whole-string test proves none of
   the cross-chunk state machine), braces and quotes inside asteroid names, the wrapper object's
   trailing `}`, truncated input, and a non-catalog input. One of these is a **real regression**:
   the first implementation ran past the array's `]` into the wrapper's own `}` and reported brace
   depth −1, caught by the first smoke run and now pinned.
2. The Kepler solver against **textbook physics, not itself** — circular-orbit vis-viva speed
   matching 18.126 km/s at 2.7 AU, and specific angular momentum |r × v| = √(GM·a(1−e²)), which is
   the single strongest check that the analytic velocity derivative really is tangent to the ellipse
   the position sits on.
3. The declared scene mapping against the constants `babylon-asteroids.ts` actually uses. These are
   duplicated across a `.mjs` build script and a `.ts` runtime module by necessity (the script
   cannot import TS); this test is the only thing keeping them honest, and without it a belt-radius
   tweak would silently desynchronize the shipped asset.

### The E2E flake investigation — done properly, because the count went up

The full run was **78/83** with **the new C3 spec passing**. But the failure count rose from
TR-073's 2 to 5, and C3 adds 154,662 additive billboards to a scene the software rasterizer is
already struggling with. Asserting the established cumulative-load SwiftShader flake class by
assumption would have been exactly the move this repo's history says not to make, so the A/B
TR-071/072/073 established was run instead: `_loadAsteroidVisualLayer` temporarily disabled, full
suite re-run at `--workers=1`.

| Run                    | Result    | Non-C3 failures                                                                                           |
| ---------------------- | --------- | --------------------------------------------------------------------------------------------------------- |
| C3 enabled (14.0 min)  | **78/83** | craft 2k · craft auto-resolve P4 · GAP-03/04/05 console-clean · nebula destination-gate · GAP-17 sequence |
| C3 disabled (15.8 min) | **78/83** | craft P5 rollout · B5 quality tiers · GAP-17/GAP-08 free-look · distance-scaled travel                    |

**Identical pass count, and the two failure sets do not overlap at all.** Every failure in the C3
run passed in the A/B, and every failure in the A/B passed in the C3 run — TR-052's documented
"rotating phantom failures" signature, reproduced cleanly in one sitting. All five C3-run failures
were additionally confirmed passing on re-run. There is no evidence C3 caused a regression, and
the pre-A/B suspicion that it might have was worth an hour to settle rather than assert.

The A/B also proves the new C3 spec is **not vacuous**: it is the fifth failure in the disabled
run, because `asteroidVisualCount` is 0 when the layer it asserts on is off. A test that passes
whether or not the feature exists proves nothing; this one does not.

### Live-browser check, and what it did and did not show

A real preview session (`npm run preview`, WebGPU backend, console **clean** — the TR-045-class
check that actually matters after a shader change) confirms the **physics tier end-to-end**:

```
physicsMode:         "havok"        asteroidCount: 20 (lite tier)
asteroidRealSource:  "gaia-dr3"     asteroidCatalogSize: 154662
asteroidRealEpoch:   "2026-07-20"
asteroidSample:      [140.39, 96.08, -13.07]
```

That sample position is the real `heco` record — the same one independently re-derived from the
raw 150.7 MB catalog in Part 5, now confirmed arriving at a rigid body in a live browser. The
whole chain from raw catalog byte to Havok body is verified.

**The visual layer was not confirmed by eye.** In the embedded browser pane the post-`cosmos:ready`
bulk fetches never ran — SDSS (pre-existing, unmodified by C3) sat at 0 records alongside the new
asteroid layer, and the pane's renderer eventually stopped responding to screenshot requests. The
asset itself serves correctly (HTTP 200, 2,084,121 bytes), and the E2E spec running in a real
Chromium proves the full path with the exact real record count and mesh readiness — plus the A/B
above proves that assertion is not vacuous. But an instrument that fails to load the layer cannot
be used to judge how the layer looks.

**So: the belt's appearance is owner-eyes-outstanding.** Specifically worth looking at, since none
of it is machine-checkable — whether 154,662 specks at the format's dimmest magnitude read as rock
dust rather than a second star field, whether the warm-grey byte 173 looks like asteroids after
Astra's correction, and whether the belt's real (and genuinely fatter) inclination spread reads
better or worse than the procedural torus it replaces.

**⚠️ WHAT THIS PASS DOES NOT PROVE.** C3's exit criterion is frame-budget-gated: "frame budget
holds on every device class." **That has not been measured, and CI cannot measure it.** TR-067
established that Playwright's bundled Chromium (SwiftShader) renders this scene at ~3 fps against
~50 fps on real Chrome/GPU hardware — a ~17× gap. C3 adds 154,662 additive billboards to a scene
that already carries 3.6M SDSS galaxies, so this is precisely the measurement CI's instrument is
confirmed unrepresentative for. **C3 is code-complete, not budget-cleared.** The real-device pass
(desktop / iPad / mid-Android, on the owner's now-available hardware) should run in one session
with C2's, since both are waiting on the same instrument and would be measuring the same scene.
